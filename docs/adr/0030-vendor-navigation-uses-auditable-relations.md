# ADR-0030：厂商导航使用可审计关系，而不是任意实体提及

- 状态：接受
- 日期：2026-08-13
- 关联：AHR-PRD-100 §2/§3、AHR-DATA-300 §1/§7、AHR-FE-600 §3、ADR-0005、TASK-M5-015

## 背景

主题地图的“公司与模型”入口原来直接联结 `vendor_entity -> entity -> item_entity`。这会把
`subject`、`object` 和 `mention` 三种实体角色等价处理：只要正文提到 OpenAI，一篇主要讲
Anthropic、NVIDIA 或通用研究的文章也会进入 OpenAI 页面。页面再按发布时间排序，最新的
弱提及会占据前 40 条；API 又只返回数组，前端把数组长度误写成总数。

`item_entity` 是模型抽取事实，不能丢弃弱提及，因为 RAG、搜索和分析仍可能需要它。但
“文章提到某实体”与“文章是某厂商的核心动态”不是同一个业务关系，不能继续由查询临时猜测。

## 决策

1. PostgreSQL 新增 `item_vendor_relation`，保存内容到受控厂商入口的派生关系：
   `primary|related|mention`、分数、命中实体、原始角色/置信度、原因码、分类器版本和计算时间。
   PostgreSQL 继续是唯一事实源；Redis 只缓存聚合结果。
2. 关系由确定性数据库函数从已通过 schema 校验的 `item_entity`、标题和摘要派生。首版规则为：
   - 高置信 `subject` 且厂商实体出现在标题或摘要开头：`primary`；
   - 其余高置信主体、对象或标题命中：`related`；
   - 仅在正文出现：`mention`。
   每个内容/厂商只保留最强的一条关系及其理由。
3. 内容重新结构化成功时，在同一事务中替换旧 `item_entity`、`item_topic` 和厂商派生关系；
   模型或数据库失败时事务回滚，上一份完整事实不会被半成品覆盖。
4. 厂商卡片的 `total` 改为核心动态数，并附带相关、提及、近 7 日核心数和最后计算时间。
   原 `/vendors/{slug}` 数组接口暂时保留兼容；新增 `/vendors/{slug}/feed` 游标接口，返回真实
   总数、关系证据和下一页游标。Web 只读取新接口。
5. 默认厂商详情只展示 `primary`；读者可以显式切换到“相关与对比”或“顺带提及”。每条内容
   展示进入该分层的原因，不把模型内部置信度伪装成用户评分。
6. 主题维度仍保留全部 `item_topic` 作为加工事实；公共聚合只使用置信度不低于 0.60 且每篇
   排名前 3 的主题，避免一次模型输出占满多个主题入口。阈值后续必须用人工黄金集逐主题校准。

## 备选方案

- **只在查询中加 `ie.role = 'subject'`**：改动小，但无法解释、版本化和回填；错误主体也无法
  与标题证据区分。
- **删除所有 mention**：会破坏搜索、RAG 和分析用途，丢失真实的弱关系事实。
- **再次调用 LLM 判断厂商关系**：增加费用、延迟和非确定性；现有实体角色和标题信号足够
  完成首版分层，后续只有在黄金集证明收益后才引入。
- **引入图数据库或 Elasticsearch**：当前约两千篇内容、十五个受控厂商，没有容量证据。

## 后果

- 厂商页面默认精度显著提高，弱关联仍可访问且可解释；历史内容可由同一版本规则回填。
- `item_vendor_relation` 是派生事实，可以从 `item_entity` 重建；备份恢复仍以 PostgreSQL 为准。
- 标题/摘要启发式可能漏掉没有直接点名厂商的核心文章，因此发布后要抽样评估
  `primary precision@20` 与核心召回，再调整规则版本，不能凭页面观感调阈值。
- 新 feed 是新增接口；旧接口在单独弃用周期前不删除，避免破坏未知调用方。

## 回滚

Web 可切回旧 `/vendors/{slug}`；Core 可停止读取新表；加工管线可停止调用刷新函数。
`item_vendor_relation` 为派生数据，回滚代码后可保留，不影响 `item_entity`、RAG 或内容读取。
