# ADR-0015：稀疏检索通道复用 Postgres 既有索引，不引入 Elasticsearch / Neo4j

日期：2026-08-03
状态：已接受
关联：`AHR-RAG-400` §5 `KEYWORD_FTS`、`AHR-PRD-100` §102、V001、V005

## 背景

M4 检索底座（4140 分块全部向量化）跑通后的实测冒烟测试暴露一个失败：

```
问 "MXFP4" → 稠密检索召回的是 "NVFP4"
```

这是稠密向量的固有特性：两个字符串语义邻近（都是低精度浮点格式），但它们指的是**不同厂商的不同规格**。`AHR-PRD-100` §102 早已写明「精确产品名、版本号、缩写不得只依赖向量检索」，因此稀疏通道不是可选优化，是必需项。

参考的外部企业级 RAG 方案在此处用 **Elasticsearch + IK 分词**，并额外用 **Neo4j** 做结构图投影。问题是：本项目是否需要新增这两个中间件。

### 实测证据

先量了现状，而不是先假设需要新组件：

| 事实 | 数据 |
|---|---|
| `content_chunk.search_vector` GIN 索引 | **V001 baseline 就已存在** |
| `content_item` 的 tsvector + trigram 索引 | **V005 已存在** |
| 语料规模 | 959 篇 / 4140 分块 |
| `MXFP4` 在 FTS 索引中的精确命中 | **30 个分块** |
| `NVFP4` 在 FTS 索引中的精确命中 | **67 个分块** |

**答案本来就躺在已有的索引里。** 稠密通道找错了，而精确命中 30 条一次 `@@ plainto_tsquery` 就能取出。修这个失败需要写一条查询，不需要加一个容器。

CJK 分词能力也实测了，没有靠猜：

```sql
SELECT to_tsvector('simple', '智谱发布 GLM-5 模型，支持 MXFP4 量化');
-- '-5':3 'glm':2 'mxfp4':6 '支持':5 '智谱发布':1 '模型':4 '量化':7
```

Postgres 默认 parser 按**空白与标点**切分 CJK，不按词切分：`智谱发布` 是一个 token，查询 `智谱` 命中不了它。这是真实存在的能力缺口，下面在「后果」里明确记录。

## 决策

1. **不引入 Elasticsearch**。`KEYWORD_FTS` 通道直接查 `content_chunk.search_vector`（GIN，`simple` 配置），`content_item` 层用 V005 已有的 tsvector + trigram。
2. **不引入 Neo4j**。`AHR-RAG-400` §13 已判定 GraphRAG 先做 Graph-lite；`entity`/`story`/`story_relation` 三张关系表足以支撑邻接扩展，且 Graph-lite 本身排在 RAG-V1，不在本次范围。
3. **融合用 RRF 而非归一化分数**。Postgres 的 `ts_rank_cd` 不是 BM25，与向量余弦分不可比。`AHR-RAG-400` §6 的公式 `Σ w/(60+rank)` 只吃**排名**不吃分数，这一约束正好使跨通道分数不可比变得无关紧要。
4. **trigram 作为 tokenizer 失配时的兜底**：`GLM-5` 被切成 `glm` + `-5`，此类查询走 `gin_trgm_ops` 子串匹配。

## 备选方案

- **Elasticsearch + IK 分词**：否决。理由不是"太重"，是**收益指向错了地方**——稀疏通道的职责是精确稀有 token（模型名、版本号、仓库名、量化格式），这些压倒性是 ASCII，IK 的中文分词对它们毫无作用；而中文语义召回本来就该由 bge-m3 的稠密侧承担。代价则是确定的：一个新容器、一条双写同步路径、一类新的「PG 有 ES 没有」不一致缺陷，以及 4140 分块规模下完全不必要的运维面。
- **改用 ParadeDB / `pg_search` 拿真 BM25**：否决。需要替换 postgres 镜像，为了一个 RRF 根本不使用的评分函数承担迁移风险。
- **用 bge-m3 自带的 sparse / ColBERT 输出**：否决（技术上不可得）。bge-m3 原生支持稠密 + 稀疏 + 多向量三种输出，但硅基流动暴露的是 OpenAI 兼容 `/embeddings`，**只返回稠密向量**。若后续自托管 FLAG Embedding，可重新评估。
- **引入 zhparser / pg_jieba 做中文分词**：暂缓，不否决。需要重新构建 postgres 镜像。触发条件写在下面。

## 后果

- **零迁移成本**：稀疏通道不需要任何 Flyway 迁移，索引已经在库里。
- **中文精确检索存在已知缺口**：`智谱` 查不到 `智谱发布`。缓解措施是稠密通道 + trigram 兜底；**必须在黄金集中专门设置中文精确匹配题**来量化这个缺口，而不是假设它不重要。若评测显示中文精确题 Recall@20 显著低于英文精确题（差距 > 10 个百分点），则触发引入 zhparser 的评估。
- **`simple` 配置无词干还原**：`released` 与 `release` 不互相命中。这是 V005 刻意的选择（`english` 词干会破坏 `v2.52.0` 这类版本串），代价由稠密通道吸收。
- 中间件数量维持 2 个（Postgres、Redis），与 ADR-007「用数据库 Outbox 替代 MQ」的取向一致。

## 回滚

无需回滚——本决策不改变任何表结构或数据。若日后确需 ES，`KEYWORD_FTS` 是一个独立通道接口，替换其实现即可，属于**增量**变更；届时需按规格新开 ADR 说明双写一致性方案。

## 后续证据（2026-08-03，B2 实测）

以上决策正文保持原样，本节记录通道实现后测到的数据，并**修正一条触发条件**。
完整报告见 [B2](../status/m4-rag-eval-B2.md)。

### 决策被证实的部分

MXFP4 那道题（RAG-GOLD-048）在稀疏通道下 Recall@20 从 **0.33 → 1.00**、排名从第 4 → 第 1，
`fact_check` 类整体 Recall@20 达到 **1.0000**。不引入 Elasticsearch 而复用既有 GIN 索引，
确实修好了这一类失败。

### 决策正文没写、实现时才发现的部分

`plainto_tsquery` 把词全部 AND 起来，自然语言问句这样查**命中 0 条**。通道必须 OR；
而全部 OR 又会被常见词淹没，因为 `ts_rank_cd` 没有 IDF。
最终实现按**语料实测的文档频率**筛词（默认丢弃 df > 15% 的词）。
这个办法的附带好处是不需要停用词表，一条规则同时服务中英文。

### 触发条件修正

原文：「若中文精确题 Recall@20 显著低于英文精确题（差距 > 10 个百分点），
则触发引入 zhparser 的评估。」

实测差距是 **52.1 个百分点**（稀疏通道：含 ASCII 专名 0.5798，纯中文 0.0588），
15 道题稀疏检索零命中且全部是纯中文。按字面读，触发条件已满足。

**但这条触发线写错了层。** 同一组题在稠密通道上的差距只有 **4.9 个百分点**
（0.8984 / 0.8490）——中文语义召回本来就由 bge-m3 承担，这正是本 ADR「决策」第 1 条
的分工设计。稀疏通道在纯中文上得 0.0588，是在做设计上让它做的事，不是它坏了。
按通道分数触发，等于用一个组件的设计边界去触发架构变更。

**修正后的触发条件（系统级）**：出现**中文近邻实体互相污染**的检索失败，
即中文专名版本的 MXFP4/NVFP4 现象——两个语义相近、事实不同的中文实体，
稠密通道分不开，而稀疏通道因分词缺口也补不上。届时重新评估 zhparser / pg_jieba。

当前语料不满足这个条件：稀有可区分 token（模型名、版本号、量化格式、仓库名）
压倒性是 ASCII。若中文一手信源占比上升、中文专名成为主要区分特征，须重测。
