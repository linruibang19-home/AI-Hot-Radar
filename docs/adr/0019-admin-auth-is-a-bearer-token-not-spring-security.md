# ADR-0019：管理端鉴权用带角色的 Bearer 令牌，不引入 Spring Security

- 状态：已接受
- 日期：2026-08-08
- 相关：`AHR-QSO-700` §3（管理端最小权限 RBAC，关键操作二次确认）、`AHR-API-500`（所有 `/admin/**` 需要 RBAC + CSRF/同源保护）、ADR-0005（Redis 只做缓存/限流）

## 背景

`SourceHealthController` 从 M1 起就是只读的，类注释里写着原因：

> 规格要求最小权限 RBAC 与二次确认，而鉴权尚不存在；现在暴露启停/重跑
> 会造成一个无鉴权的写入面，因此推迟到 M5。

这条推迟一直成立，但它同时**卡住了三件事**：信源启停（M1/M2）、
后台任务重跑（M2）、Story 人工合并/拆分/锁定后台（M3）。
三个待办各自独立，前提是同一个。

而且现状比注释描述的更糟一点：**`GET /api/v1/admin/sources` 对任何人开放**，
而 `AHR-API-500` 写的是「所有 `/admin/**` 需要 RBAC」，`GET/PATCH /admin/sources/{id}`
就在它的清单里。也就是说，这不只是「还没做写入」，而是**读取这一半已经违反了锁定契约**——
和 §3.18 的信源状态机是同一种形状：实现悄悄偏离规格，且没有任何测试会发现。

## 决策

**一、令牌存哈希，按哈希查库。**

`admin_principal(label, token_hash, role, disabled_at)`，令牌以 SHA-256 十六进制存储。
查询是 `WHERE token_hash = ?`，因此应用层**没有任何字符串比较**，
定时攻击的问题不是「用了常量时间比较」而是根本不存在。

**不用 bcrypt/argon2**，这是有理由的取舍而不是偷懒：慢哈希的存在意义是让**低熵、人选的**
口令扛得住离线爆破。这里的凭据是运维用 `openssl rand -hex 32` 生成的随机值，
没有字典可跑，加盐拉伸买不到安全性，却要在每个管理请求上付一次代价。
**这个论证只在令牌确实高熵时成立**，所以 `BOOTSTRAP_MIN_LENGTH = 32` 是硬失败而不是告警——
一条启动日志里的 WARNING 不是控制措施。

**二、两个角色，且都真的在用。**

`VIEWER` 只能读，`OPERATOR` 可以读写。写成两个而不是一个 `ADMIN`，
是因为**最小权限只有在「读不蕴含写」时才是一条性质**，否则只是文档里的一个词。

它落地成了一条可演示的性质：**web 容器持有的是 VIEWER 凭据**。
信源后台是服务端渲染的，web 层只读不写，于是它拿到的令牌**就是写不动的那种**——
拿下 web 容器不等于拿下采集管线。实测：同一个令牌 `GET` 返回 200（125 行），
`PATCH` 返回 **403**。

**三、按路径前缀拦截，不按注解。**

`AdminAuthFilter` 挂在 `/api/v1/admin/*` 上。新加的管理端点**因为它在哪儿**而受保护，
不是因为有人记得加注解。反过来做——白名单已知路径，或让每个 controller 自己 opt-in——
恰好会在「赶时间加的那个端点」上失效。

**四、二次确认在服务端，不在浏览器。**

改动必须回显目标 id（`X-Confirm-Target`），否则 428。
确认对话框是**某一个客户端**的性质，而端点绕开它照样可达；
回显 id 拦的是真实会发生的那种事故：一个格式完全正确、但打在错行上的请求。

**五、每次尝试都留痕，包括被拒的。**

`admin_audit` 区分 `DENIED_NO_TOKEN` / `DENIED_BAD_TOKEN` / `DENIED_ROLE` /
`DENIED_UNCONFIRMED`。「令牌不对」和「令牌对、角色不够」是两种完全不同的事件，
只记成功的审计日志看不到有人在拿密钥试门。

**六、不引入 Spring Security。**

这是本 ADR 里最容易被质疑的一条，所以写清楚：
这个面是「一个 Bearer 令牌查一张表」，没有会话、没有 Cookie、没有表单登录、没有 OAuth。
引入 starter 会带进一大套默认配置，而接下来要做的第一件事是把其中大部分关掉，
最终的 filter chain 比它替代掉的六十行更难读。
**一旦出现用户账号或第二种认证方式，这个判断就翻转**，那时再引入，而不是现在。

**七、CSRF 明确按「不可达」处理，而不是假装做了。**

契约要求 RBAC 之外还有 CSRF/同源保护。CSRF 防的是**环境凭据**：
Cookie 会被浏览器自动附加到跨站请求上。这里用 `Authorization` 头，
跨源的表单或 `<img>` **设不了这个头**，也没有会话给浏览器自动带上。
再加一个 CSRF 令牌等于给一扇不会自己开的门配第二把锁。
如实记在这里，因为「我们实现了检查项」和「这个攻击路径不可达」是两句不同的话，
只有后一句是真的。

## 备选

1. **Caddy 层 basic auth。** 零应用代码，但服务端不知道是谁做的、
   没有审计、没法做二次确认，而且「RBAC」就只剩一个门禁。
2. **完整用户表 + 口令登录 + 会话。** 看起来最像模像样，
   但系统里只有一个运维，口令存储是净负债，而且会引入 CSRF 这个本来不存在的问题。
3. **令牌写在环境变量里比对。** 省一张表，但吊销要重新部署，
   审计行没法指向具体凭据，多一个凭据就要多一个变量。

## 后果

- 三个被卡住的待办解锁：信源启停已实现并实测，任务重跑与 Story 合并的前提已具备。
- **多了一个必填密钥**：`AHR_ADMIN_BOOTSTRAP_TOKEN` 未设置时不注册任何凭据，
  管理 API 拒绝一切请求——缺密钥必须失败成「锁上的门」而不是「敞开的门」。
  生产 compose 用 `:?` 让它在启动时就报错，比一个谁也进不去的后台更吵。
- **`source.configured_enabled` 不再是轮询依据**。它由 `config/sources.yaml` 同步覆盖，
  运维在后台关掉的源会被下一次注册表导入重新打开。改动写进独立的 `operator_enabled`，
  轮询依据改为生成列 `effective_enabled = COALESCE(operator_enabled, configured_enabled)`。
  用生成列而不是在五处 SQL 里各写一遍 `COALESCE`：这个项目已经栽过一次
  「两处状态不一致导致内容对检索不可见」（§3.12）。
- 浏览器里还**没有**改动 UI。写操作目前走 API，凭据在运维手里；
  把 OPERATOR 令牌放进 localStorage 需要单独想清楚 XSS 面，不在本次范围。
