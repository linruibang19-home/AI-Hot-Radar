# ADR-0016：父块自适应阶梯，且由查询派生而非物化落表

日期：2026-08-03
状态：已接受
关联：`AHR-RAG-400` §7、§13、`AHR-DATA-300` §6、V001

## 背景

`AHR-RAG-400` §13 已锁定「Parent/Child 采用简化版，已纳入 MVP」，§7 规定命中 passage 后做**父块提升**与**兄弟扩展**。现在要把这条规格落成实现，必须先回答：**父块到底是什么。**

参考的外部方案给的是固定双层——PDF 章节为 parent、段落为 child，并落 `document_structure_node` 实体表存章节树。照抄之前先量了本项目语料：

| 指标 | 实测（2026-08-03） |
|---|---:|
| 文档数 / 分块数 | 959 / 4140（均 4.32 块/篇）|
| **整篇 ≤ 2000 token 的文档占比** | **69.3%** |
| 文档 token p50 / p90 / max | 1034 / 5139 / 31147 |
| 顶层小节数 | 1435（均 2.89 块/节）|
| 多块小节占比 | 45.8% |
| 小节 token p50 / p90 / max | 483 / **3519** / 30602 |
| **`heading_path` 为空的分块** | **1386（33.5%）** |
| 分块 heading 最大深度 | 4 |

三个数字直接否决了固定双层：

1. **69.3% 的文档整篇就装得下预算**——对这些内容，「小节」这一层是多余的抽象；
2. **小节 p90 = 3519 token**——"命中就提升整节"会撑爆证据预算，长尾必须封顶；
3. **1/3 的分块根本没有 heading**——固定的「小节 = 父块」对它们直接退化为无定义。

### 为什么这一步排在分块修复之后

父块依赖 `heading_path`，而 `heading_path` 在 commit `0b27628` 之前是错的：`heading_path[:level-1]` 把**列表位置当成了标题层级**，多数正文从 `##` 开始，导致路径沿文档单调累积。若先做父块提升，命中 `Patch Changes` 会被提升到一个**文档里并不存在的父节**，而且**不会报任何错**——只会静默喂错上下文。先修分块再建父块，顺序由此确定。

## 决策

### 1. 父块是三级自适应阶梯，不是固定一层

按 token 预算自上而下选择第一个装得下的粒度：

```
① 整篇 revision ≤ PARENT_BUDGET        → 父块 = 整篇        （覆盖 69.3%）
② 否则 命中块所在顶层小节 ≤ PARENT_BUDGET → 父块 = 该小节
③ 否则                                  → 父块 = 命中块 ±1 兄弟块，硬封顶
```

`heading_path` 为空的分块直接从 ① 掉到 ③，不存在未定义状态。

### 2. 父块由查询派生，不落表、不额外嵌入

`content_chunk` 已有 `content_revision_id`、`ordinal`、`heading_path`、`token_count`，父块是一条按 `ordinal` 排序的区间查询。

- **不新增表**：没有 `document_structure_node`，就没有它与 `content_chunk` 的同步路径，也就没有那一类不一致缺陷；
- **不额外嵌入**：只有 child 进向量索引。父块若也嵌入，成本翻倍，且两层分数混在一起会污染 RRF 的排名语义。

### 3. 检索单元与引用单元分离

- **检索 / 引用 = child**：`rag_citation.content_chunk_id` 指向 child，粒度精确到段；
- **生成上下文 = parent**：喂给 LLM 的是父块，保证语义完整。

这一分离能成立，是因为上下文增强前缀**只加在嵌入输入、没有写进 `body_text`**（见 `AHR-RAG-400` 落地记录）。因此可以断言一条硬不变量：

> 每个被引用分块的 `body_text` 必须是其 `content_revision` 正文的**逐字子串**。

违反即说明证据被合成过，直接判定生成失败。

### 4. 父块提升同时是多样性约束

冒烟测试中 llama.cpp 单篇占满 top-3。这三块同属一个 revision，提升后**塌缩成一个父块**，释放两个证据位。因此 §7 的事件折叠与父块提升是同一次去重的两个层级：父块折叠**同文档**，Story 折叠**同事件**。

## 备选方案

- **固定双层 + 物化 `document_structure_node`（照抄外部方案）**：否决。它服务的是用户上传 PDF、需要页面/版式/表格定位的产品形态；本项目语料是 HTML/Markdown 资讯，且 1/3 的分块无 heading，物化一棵三分之一为空的树，换来的是一条必须维护的同步路径。
- **父块 = 永远取整篇**：否决。p90 = 5139、max = 31147 token，长尾会直接击穿上下文预算，且把整篇 changelog 塞进证据会稀释相关段落。
- **父块也做嵌入，双层召回**：否决。嵌入成本翻倍；更实质的问题是父子两层的相似度分布不同，混入同一次 RRF 会让排名失去意义，而 §6 的融合公式恰恰只吃排名。
- **只做兄弟扩展（±1 块），不做整篇/小节提升**：否决。对 69.3% 能整篇装下的文档，这会人为丢掉本来免费的完整上下文。保留为阶梯的第 ③ 级。

## 后果

- 父块逻辑是纯查询 + 纯函数，**可单元测试**，无迁移、无回填、无重新嵌入；
- `PARENT_BUDGET` 成为一个必须由评测标定的参数，不是常量——`AHR-RAG-400` §5 明确要求「实际参数必须用评测集调优，不能作为永恒常量」；
- 提升到整篇时，单条证据可能接近 2000 token，`AHR-RAG-400` §8 的证据选择必须在 token 预算内做覆盖优化，不能简单取 top-N；
- 语料结构变化（例如未来接入长篇论文全文）会改变 69.3% 这个比例，阶梯的分支占比需要定期复测。

## 回滚

删除父块提升步骤即可退回「只用 child 生成」，无数据变更、无迁移回退。

## 后续证据（2026-08-04，B5 实现后）

阶梯已落地为 `rag/parent.py`，纯查询派生，未新增任何表。补一条口径修正。

### 按分块统计与按文档统计差别很大

本文「背景」一节的 69.3% 是**按文档**算的。实现后按**分块**统计（`tier_distribution`，
预算 2000 token，4500 个分块）：

| 层级 | 按分块 |
|---|---:|
| ① 整篇 | 32.4% |
| ② 顶层小节 | 10.1% |
| ③ 命中块 ±1 | **57.5%** |

两者不矛盾——长文档贡献的分块数多，所以按分块加权后长尾占比自然抬高。
但**检索返回的是分块**，所以按分块的口径才是实际生效的那个：
超过一半的命中会落到第 ③ 级，而不是原先设想的少数长尾。

这不改变决策（固定单层依然对 33.5% 无 heading 的分块无定义），
但把「第 ③ 级是兜底」修正为「第 ③ 级是主力」。提高预算能线性搬运占比
（3000 → 40.2% / 4000 → 47.5% / 6000 → 60.2%），代价是单条证据更长而一次 prompt 有十条，
因此预算仍应由端到端 token 成本与答案质量共同标定，不能只看这张表。

### 实现时发现的一个缺陷

字符上限一度独立取值为 4000，而阶梯按 2000 token 判定「整篇装得下」。
2000 token 的正文约 6000 字符，于是**第 ① 级刚被选中就被截掉三分之一**，
阶梯的判断被静默作废。现在字符上限由 token 预算按 3 字符/token 换算得出。
