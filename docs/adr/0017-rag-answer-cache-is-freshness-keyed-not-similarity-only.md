# ADR-0017：RAG 答案缓存按语料指纹键控，而不是只按相似度

- 状态：已接受
- 日期：2026-08-07
- 相关：ADR-005（Redis 仅作缓存/限流/短锁）、`AHR-RAG-400`、`AHR-ARCH-200` §7

## 背景

延迟评测（LAT）给出的分布很极端：**一次问答 99% 的时间花在三次外部 API 往返上**
（generate 53% / rerank 28% / embed 18%），本地检索、融合、父块展开合计不到 1%。
而 RAG 链路此前**没有任何缓存**——同一个问题问两次，两次都付全款。

同时 `/ask` 即将公开。限流已经把单个调用者的用量框住了，但框不住"很多人问同一个
热门问题"这种完全正常的流量形态。

行业上这类问题的标准答案是"上语义缓存"：把问题向量化，新问题去找最相似的缓存问题，
超过阈值就直接返回缓存答案。**对这个项目直接照搬是错的**，理由是语料本身的性质。

## 决策

分三层，每层的失效规则由它自己的过期风险决定，而不是统一给一个 TTL。

### 1. 嵌入缓存——精确键，长 TTL

键 = `sha256(模型 + 规范化问题)`，TTL 7 天。

嵌入是输入的纯函数：同样的文本、同样的模型，向量永远一样。**没有过期概念**，
所以这一层可以放心地长期缓存。

### 2. 答案缓存——精确键，且键里含**语料指纹**

键 = `sha256(规范化问题 + prompt 版本 + 语料指纹)`，TTL 1 小时。

这是"freshness-aware"的落点。资讯语料的答案**只对它当时所依据的那份语料成立**：
「本周 DeepSeek 有什么动态」昨天的答案今天不是"稍旧"，是**错的**。
所以语料指纹进键，新内容一落地，所有旧条目**按构造失效**，
而不是靠"TTL 但愿设得够短"。

指纹 = `count(已向量化分块)` + `max(published_at)`。取已向量化分块而不是条目数：
没切块没嵌入的条目检索不到，改变不了任何答案，让它去失效缓存是白白扔掉条目。

### 3. 语义近邻——同一想法放宽一档，但**阈值取 0.97**

用本次查询已经算出的问题向量，去一个**有界索引**（最近 200 条）里找近乎同义的问题。

三条约束缺一不可：

- **阈值 0.97，不是演示常用的 0.85。** 「DeepSeek 发布了什么」与
  「OpenAI 发布了什么」在嵌入空间里比直觉近得多。阈值放松的后果**不是**返回一个
  差一点的答案，而是**自信地回答了另一家公司的问题**。
- **必须同一语料指纹。** 否则近邻命中会让答案绕过第 2 层的失效规则活下来。
- **只吃已算出的向量。** 未命中的代价是每条缓存做一次点积，零 API 调用。

### 4. 拒答永不缓存

拒答的含义是"语料里**还**没有这个答案"，这是本系统能说出的**最依赖时间**的一句话。
缓存它等于在答案到货之后继续说"没有"。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 只上语义缓存，靠 TTL 控制过期 | TTL 是在赌"语料多久变一次"。采集每 120 秒一轮，赌不赢 |
| 阈值 0.85（常见默认值） | 见上：本语料里不同公司的同形问句距离很近，代价是答错而不是答差 |
| 引入 RediSearch 做向量索引 | ADR-005 把 Redis 限定为缓存；200 条的线性扫描是毫秒级，不值得加一个组件 |
| 不做缓存 | 99% 的延迟和几乎全部成本都在可缓存的那三次往返上 |

## 后果

- 重复问题从约 10.8 秒降到读一次 Redis，且**不产生任何 provider 调用**。
- 语料一更新，全部答案缓存失效——这是刻意的，代价是热点问题在采集后要重算一次。
- 缓存命中率、语义命中率、索引占用都记进计数器并在 `/ops` 展示：
  **一个不能被评判的缓存不该被信任**。
- 缓存命中的答案会带上标记下发，读者能看到自己拿到的是缓存。

## 回滚

删掉 `rag/cache.py` 的调用点即可，或把 `CACHE_VERSION` 改一个值让全部旧条目失效。
Redis 里没有任何事实源（ADR-005），清空只损失延迟与成本，不损失正确性。
