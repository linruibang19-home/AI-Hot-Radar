# ADR-0018：中文全文检索用字符 bigram，不引入分词器

- 状态：已接受
- 日期：2026-08-07
- 相关：ADR-0015（稀疏通道不需要 Elasticsearch）、`AHR-RAG-400` §4

## 背景

B2 那一轮量出了一个**从未被修的**缺口：稀疏通道对中文基本不工作。

Postgres 的 `simple` 配置按空白与标点切词，而中文词之间没有分隔符，
于是一整段中文变成**一个** lexeme：

```sql
to_tsvector('simple', '智谱发布新模型 GLM-5')
  -> '-5':3 'glm':2 '智谱发布新模型':1

... @@ plainto_tsquery('simple', '智谱')   -> false
... @@ plainto_tsquery('simple', 'GLM-5')  -> true
```

后果是这条通道**只对含 ASCII 专名的问题有用**。黄金集上的差距：
含 ASCII 专名的问句 Recall@20 = **0.5798**，纯中文只有 **0.0588**——
差 **52.1 个百分点**，15 道零命中题**全是纯中文**。

ADR-0015 当时记了「zhparser 的触发条件修正为系统级」，但一直没做。
这轮把它做掉。

## 决策

**用字符 bigram，不引入分词器。**

`智谱发布` → `智谱 谱发 发布`。查询 `智谱` 因此能命中。

一个 `IMMUTABLE` 的 SQL 函数 `ahr_cjk_bigrams(text)`，
**索引侧与查询侧共用同一个函数**：

- 存储：`content_chunk.search_vector` 与 `content_item.search_vector`
  的生成表达式里各加一份 bigram 向量；
- 查询：`select_query_terms` 对问题同样调用它。

共用是刻意的。原设计的注释写着「tokenisation is delegated to Postgres so
query and index agree by construction」——这是个值得保住的性质，
而在 Python 侧写一个分词器会在两边任意一边改动时**悄悄破坏它**。

### bigram 会过度产生，而这不是问题

`谱发` 不是词。但**已有的文档频率过滤器**会处理掉它：
跨词边界的 bigram 要么在语料里极其常见、要么根本不存在，两种都会被丢弃。
那个过滤器当初是为了「不需要停用词表」而写的，结果正好也覆盖这一类。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| zhparser / pg_jieba | 需要把扩展编进镜像。ADR-0015 已经定了稀疏通道**不得**换来一个新组件；bigram 只要一个函数 |
| Elasticsearch | 同上，且 ADR-0015 已专门否决过：正确答案本来就躺在 V001 建好的 GIN 索引里 |
| 在 Python 侧分词后写入另一列 | 破坏「索引与查询按构造一致」这条性质，且 5616 个分块要额外回填一列 |
| 不做 | 52.1 个百分点的缺口，且它只影响中文——本项目语料与用户都是中文为主 |

## 后果

- 索引体积增加：每段中文正文多出约 (n−1) 个 bigram lexeme。
  当前 `content_chunk` 的 FTS 索引 15 MB，预计增长到数十 MB 量级，可接受。
- 生成列表达式变更需要**重建列与索引**（V014 里 DROP + ADD）。
  当前 5616 分块 / 1473 条目，秒级完成。
- 站内搜索同时受益：读者搜「智谱」此前搜不到，搜「GLM-5」可以。
- **收益必须由 B13 量化**，不得只看一两个例子就宣布有效
  （`AHR-ROADMAP-800` TASK-M4-001 的原话）。

## 回滚

删掉 V014 引入的 bigram 项，把两个生成列改回 V001/V005 的表达式即可；
函数留着不影响任何东西。
