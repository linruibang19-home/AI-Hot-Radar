# 08｜简历表达与 STAR 故事
## 项目标题

**AI Hot Radar｜可追溯 AI 行业情报与时效 RAG 平台**

Next.js · Spring Boot · FastAPI · PostgreSQL/pgvector · Redis · Docker Compose

## 简历项目描述

独立设计并上线面向 AI 行业的时效情报平台：统一调度 151 个配置化公开信源，完成全文回源、
内容结构化、跨源事件聚类与日/周/月报告；自研带服务端原文引用、支持度门控和检索解释的混合
RAG。以不可变镜像部署于 2C4G 单机，HTTPS、邮件订阅、RBAC/审计、告警与备份恢复均已闭环，
且逐项验证过可用而非仅配置存在。

> 写法说明：原句是三个逗号串起来的长句，招聘方三十秒扫过去解析不了。现在用冒号引出范围、
> 分号切开三个领域（采集 / RAG / 交付），每段一个主语。

## 建议四条 bullet

每条的结构都是**主张 + 证据**，不是功能清单。堆七个名词的那种写法读起来像 JD 复制，
而不像"我干成了什么"。

- 设计配置化多信源增量采集管线（登记 151 源 / 允许调度 139），统一 Feed/API/HTML/GitHub/arXiv
  五类发现方式与 canonical 全文回源，落地 SSRF 防护、限速、幂等版本与按连续失败推进的信源
  状态机；PostgreSQL 为唯一事实源，生产 4600+ 篇内容、2.4 万+ 向量分块。
- 构建 pgvector HNSW + PostgreSQL FTS/CJK + 时间/实体约束的三路混合检索，经 RRF 融合、
  bge cross-encoder 重排、同源配额与事件折叠、父块扩展和服务端引用绑定；固定 90 题发布集
  Recall@20 89.9%、MRR 0.861，生成侧引用覆盖 98.8%、段落支持度 93.4%、诱导题错误断言 0/12。
- 将 RAG 轨迹、固定发布评测与运行指标产品化，保留 B2/B8/B13 负实验结论；通过抓取原始模型
  响应定位解析失败导致的 7.69% 误拒，加入带守卫回退且不放松引用不变量，误拒回落至约 4%
  ——同配置连跑四轮实测为 2/1/1/3，据此判定该指标是随机量而非回归信号，将硬门禁改为阈值
  门禁，仅对"编造假前提"保留零容忍。
- 完成 GitHub Actions → GHCR 不可变 SHA 镜像 → 2C4G Docker Compose/Caddy 生产链，建立双确认邮件、
  管理 RBAC/审计、故障/恢复告警、校验和异机备份与隔离恢复。

数字必须加"固定 90 题发布集 / 2026-08-11 批次"等口径；动态内容量答辩前重查。
**误拒一项不要写 0%**，理由见下面的禁区一节。

**两条可替换项**（按岗位换掉上面任意一条）：

- *偏后端 / 数据一致性*：定位并修复一类静默数据丢失——12 个 changelog 信源各自恰好 1 条内容，
  根因是同页锚点在 URL 规范化时被丢弃导致唯一索引冲突，而异常被"单条失败不拖垮整轮"的兜底
  吞掉、采集任务仍报 SUCCESS；修复后该档位内容 11 → 325 条，并补齐游标按实际提交回收的缺陷
  与回归测试。
- *偏基础设施 / 安全*：将生成供应商地址与 API Key 从环境变量迁入数据库：AES-256-GCM 信封加密、
  SHA-256 指纹用于免解密展示、写库前先向供应商验证一次、逐字段回落环境变量、保留一键重置；
  迁移上线时为 no-op，生产行为零变化。

## STAR 1：解析器造成生成误拒

- **S**：生成侧可答题误拒从 1.28% 上升到 7.69%。
- **T**：判断是检索退化、模型能力变化、语料竞争，还是解析/校验出口问题。
- **A**：先把“语料增长导致位竞争”写成待验证假设；下一轮保存六道失败题原始模型响应，发现答案和
  引用完整，只是偶发直接 Markdown 或把编号只放 `claims[].evidence_ids`；解析失败分支清空正文。
  加入有守卫回退，但仍复用编号绑定、支持度与四条不变量，逐题和全量回归。
- **R**：2026-08-11 批次误拒 0/78、诱导题错误断言保持 0/12；更重要的是证伪了听起来合理的
  初始归因。
- **反思**：可观测性要覆盖模型原始出口和解析阶段，不能只看最终业务指标。
- **后续修正（2026-08-30）**：上面那个 0/78 是**一次采样，不是系统属性**。后来用同一镜像、
  同一提示词连跑四轮，失败题数是 2 / 1 / 1 / 3，且每轮失败的题目都不同——单题误拒概率约
  2.24%，78 题全过的概率只有约 17%。也就是说 08-11 那轮是运气好。我当时据此说过"门禁失败
  是代码回退不是模型问题"，那句话是错的：**把噪声当成了信号**。现在的写法是"误拒约 4%
  （最新批次 3.85%）"，门禁也从"必须为零"改成阈值门禁。答辩时主动讲这个修正，比守着一个
  0% 有说服力得多。

## STAR 2：混合检索不是“加通道就提升”

- **S**：B2 加入 sparse 并集后 Recall/MRR 比纯 dense 更差。
- **T**：确定 sparse 本身无价值，还是融合/排序破坏了候选质量。
- **A**：保留负 run；引入按名次的 RRF 与统一 cross-encoder，记录逐题通道排名；B8 再扫 42 组权重。
- **R**：型号类问题得到真实提升，旗舰证据 dense 14 → sparse 1 → fusion 3；但接上 reranker 后
  权重差距只剩 0.0004，因此决定不改生产权重。
- **反思**：组件价值应看端到端和问题切片，调参没有显著收益就停止。

## STAR 3：跨服务限流接缝

- **S**：匿名 RAG 按 IP 限流看似实现，实际 Next 未正确传递客户端地址，生产请求共用一个桶。
- **T**：找到为什么 Web 与 AI 各自单测通过、端到端行为却错误。
- **A**：沿 Caddy → Next → AI 检查 forwarded header 契约，定义可信代理边界，在接缝添加测试。
- **R**：恢复客户端粒度限流，避免单个用户拖累全站；形成“跨语言边界必须测接缝”的工程规则。
- **反思**：安全 header 不能无条件相信公网输入，修复功能同时要限定信任链。

## STAR 4：信源状态机误隔离

- **S**：一次 DNS 抖动使多个一手源过早进入隔离且无法自然恢复。
- **T**：恢复规格中的失败阶梯，同时保留历史错误和人工控制。
- **A**：按连续失败推进 DEGRADED/QUARANTINED，加入 probe 恢复与审计，不再单次失败永久封禁。
- **R**：一手源恢复且后台能解释最近成功、失败次数与状态变化；全局流水线未因单源停止。
- **反思**：错误状态不是异常字符串，而是需要恢复路径的业务状态机。

## STAR 5：精选被 arXiv 和伪 12:00 占满

- **S**：生产当天 12 条精选全部来自 arXiv，且都显示 12:00，用户误以为信源和时间坏了。
- **T**：区分采集故障、选择偏置和发布时间精度问题，不能改写原始时间掩盖现象。
- **A**：核对数据库来源和发布时间字段，确认 arXiv 只有批次/日期精度；在选择层加入来源族、
  内容类型和研究类配额，UI 按 precision 显示“日期/批次”而不是伪分钟，重跑当天批次。
- **R**：12 条分布到 8 个来源族，arXiv 仅 2 条；精确时间来源仍保留时分。
- **反思**：多样性是产品目标，不能只靠模型相关度；时间精度属于数据语义而非 CSS。

## STAR 6：邮件订阅从按钮变成可靠业务链

- **S**：早期页面只有“输入邮箱”视觉，用户不知道会收到什么，也缺少确认、退订和防重发闭环。
- **T**：在没有账号体系和消息队列的单机架构中，实现可解释、可审计的周期报告投递。
- **A**：设计 request/ACTIVE subscription/delivery 三层事实；确认 token 版本化；只选 PUBLISHED
  报告；`subscription + report` 唯一键、`SKIP LOCKED` 和有限重试；UI 明确确认、时区和内容。
- **R**：完成真实受控邮箱确认和一期报告投递，失败可重试、退订可停止，邮件不重新调用 LLM。
- **反思**：外部副作用无法靠一个事务“绝对 exactly once”，要用状态、幂等和可观察补偿。

## STAR 7：页面按钮慢的分层排查

- **S**：用户感觉左侧按钮卡顿，直觉容易归因于 React 渲染。
- **T**：确认等待发生在浏览器、Next SSR、Core API、数据库还是外部模型。
- **A**：按导航链计时，补 Link 预取、active/pending 即时反馈、独立数据并行和稳定读缓存；RAG
  展示阶段而不是让页面静默等待，同时保留真实请求，不用假数据伪加速。
- **R**：常用内容路由点击有即时反馈，重复读减少；模型首请求仍如实展示外部 API 长尾。
- **反思**：性能优化首先是测量和反馈语义，loading 动画本身不是性能提升。

## STAR 8：Outbox 架构叙述纠偏

- **S**：早期规格和 README 图把 `outbox_event` 描述成 Core Publisher → AI Consumer，但代码中没有
  consumer；面试材料会把预留表讲成已完成功能。
- **T**：在不擅自删除表或重构生产的前提下，让规格、恢复手册和教材与真实运行一致。
- **A**：全仓搜索表读写和 Compose 命令，确认采集是 Python `SKIP LOCKED`、处理是 advisory lock
  轮询、Java Scheduler 仅邮件；先写 ADR-0028，再校准架构/采集/runbook 和文档校验。
- **R**：当前/目标边界统一，Outbox 保留为事件日志和未来传输点，不再作为简历卖点。
- **反思**：架构图不是愿望板；每条箭头都应找到生产者、消费者、积压指标和重放测试。

## STAR 9：生成模型热切换而不破坏向量索引

- **S**：模型只存在 `.env`，页面看不到，切换需重启；用户希望比较生成模型，又误以为 embedding
  也能随意切。
- **T**：让生成模型可审计切换，同时保护既有向量空间和历史可追溯性。
- **A**：建立 PostgreSQL allowlist/current config/price snapshot；VIEWER 读、OPERATOR 确认写；
  Python 每次建客户端读版本；usage 快照配置；明确 embedding/reranker 固定。
- **R**：DeepSeek Flash/Pro 可无重启切换，只影响后续生成，历史结果和 1024 维索引不重写。
- **反思**：可配置不是“允许任意字符串”，能力兼容、回滚和成本版本都要进入设计。
- **后续（2026-08-18，V027）**：模型可切了，但决定能不能调通的供应商地址和 API Key 仍只在
  `.env` 里，换一把要 SSH 上机器改文件再重启三个容器。补做成页面可编辑：单行表存地址 +
  AES-256-GCM 信封密文 + SHA-256 指纹（指纹让控制台能显示"现在装的是哪一把"而不必解密）；
  **写库前先拿这把 key 去请求一次供应商，通了才落库**；地址与密钥各自独立回落环境变量，
  所以迁移种子写的是 `env://LLM_BASE_URL` 占位符，上线当天是 no-op。见 ADR-0032。

## STAR 10：Docker 磁盘增长定位

- **S**：本地 Docker 占用数十 GB，担心是 PostgreSQL 业务数据失控。
- **T**：在不删除卷和用户数据的前提下定位来源并建立长期边界。
- **A**：分别测镜像、BuildKit、volume 和容器可写层，确认主要是历史构建产物；为所有服务设置
  local 日志轮转，维护脚本限制 BuildKit、清理未引用旧镜像，明确永不自动 prune volume。
- **R**：增长来源可解释、日志有上限、维护可重复，数据库/Redis 卷和备份未受影响。
- **反思**：清理前先分类“可再生缓存”和“唯一事实”，磁盘数字大不等于数据库泄漏。

## STAR 11：接入中转站——做完了又整套删掉

这条是**主动收窄范围**的例子，比任何"我把它做出来了"更能体现判断力。面试官问"有没有做过
后来发现不该做的事"，答这条。

- **S**：模型配置页只能在预置模型之间切换。目标是做成通用连接管理器，像 CC Switch 或 Cline
  那样接入任意 OpenAI 兼容的第三方中转站——能显著降低调用成本。
- **T**：让用户填一个地址就能用，同时保证填错时有明确反馈。
- **A**：实现了连接表、模型列表拉取、按供应商类型推导端点路径的规则。**用户实测三次都失败。**
  自己去探测那家中转站才发现：只有 `/v1/messages` 和 `/v1/chat/completions` 是 API，`/` 和
  `/chat/completions` 返回 `200 text/html`。也就是说——
  1. 中转站之间**没有统一的路径约定**，"用户填的是根地址还是完整端点"做成开关后两个答案都可能错；
  2. 我写的推导规则**第一条（OpenAI）就是错的**；
  3. 最糟的是失败长这样：`200` + 一个 HTML 页面，**看起来像成功**。
- **R**：判断收益（省点模型钱）撑不起成本（一套无法离线验证的路径推导 + 连接启停、模型列表、
  thinking 开关一串配套状态），**整套删除**，回到只接官方兼容端点。保留了其中一样东西：
  HTML 响应检测——它在官方端点上同样能挡住"填错地址却返回 200"这类。
- **反思**：三点。第一，"用户填的对不对"不该做成让用户二选一的开关，两个答案都错的开关等于
  没有。第二，`200 + HTML` 这种**长得像成功的失败**必须显式识别，否则排查方向从一开始就是错的。
  第三，做到一半发现前提不成立时，删掉比硬撑便宜——负结果写进 ADR-0032 之后，它反而成了
  这个项目里我最愿意讲的一段。

## STAR 12：每个信源恰好 1 条内容

被问"讲一个你排查过的复杂问题"时答这条。它的价值在于**所有常规监控信号都是绿的**——
这类问题才真正区分排查能力。

- **S**：12 个一方 changelog 信源（OpenAI、Anthropic、Gemini、Mistral、DeepSeek、Kimi、百度、
  智谱）在库里各自**恰好 1 条内容**。采集任务连续 SUCCESS、HTTP 200、健康检查全绿、
  错误日志为空、`consecutive_failures = 0`。
- **T**：判断是这些站点本来就更新少，还是采集链路有结构性缺陷。
- **A**：先看分布而不是看日志——"每个都恰好 1 条"这种整齐的数字不可能是内容稀少。抓页面
  实测：trafilatura 能切出 21 个段落，说明解析没问题。再查游标，发现它存着 381 个段落哈希
  声称都见过，而库里只有 11 条。顺着往下挖出两个缺陷：
  1. **fragment 被当装饰丢掉，而它就是身份**。changelog 每条更新是同一页面的一个 `#锚点`，
     `canonicalize_url` 按通用规则丢弃 fragment——这条规则对文章是对的，对 changelog 是错的。
     26 条更新哈希成同一个 URL，唯一索引留下第一条、拒绝其余；`UniqueViolation` 被"一篇坏
     页面不能拖垮整轮"的兜底 catch 吞掉，run 依然报 SUCCESS，`discovered_count` 还是真实
     段落数——**每一个计数都是对的，只有内容不在**。
  2. **注释描述的规则只对一个分支实现了**。保存游标那段的注释写着 "only content that
     actually committed is treated as seen"，实现却是 `isinstance(adapter, HtmlListingAdapter)`,
     七个适配器里只对一个成立。changelog 适配器返回整页段落、主循环每轮只入库 5 条，
     游标却把全部哈希存了回去。
- **R**：改为让适配器自己回答"哪些该算已见"（可选协议方法而非调用方列举类型）；URL 规范化
  增加 `keep_fragment`，只对 changelog 档位开启，通用规则不动。该档位内容 11 → 325 条
  （生产 11 → 250），全库 2816 → 4113。补了 7 条回归测试。上线后又发现纯中文标题 slug 为空
  时 `candidate_url` 仍回退到裸 URL，等于从后门绕回同一个 bug，当天补修并发版。
- **反思**：三点。第一，**空结果和"安静的一周"长得一模一样，而系统默认信后者**——
  `SUCCESS + discovered 0` 不该算健康。第二，通用规则要检查它在每个档位是否都成立，
  "fragment 不标识独立文档"对文章成立、对 changelog 不成立。第三，注释里说"每个 X 都…"
  而代码里是 `isinstance` 单分支，基本就是缺陷现场。

## 简历与面试禁区

- 不说"所有登记源都实时正常"；登记、允许调度与 ACTIVE 数不同且动态变化
  （2026-08-31 实查：151 / 139 / 116，另有 7 个 QUARANTINED）。
- 不说"实现了消息队列"；outbox 当前没有消费者。
- 不说"引用正确率 100%"；自动段落支持度是 93.4%（最新批次 94.25%），还需人工高风险审查。
- **不说"误拒率 0%"**；那是一次采样。同配置四轮实测 2/1/1/3，最新批次 3.85%。说"约 4%"，
  并准备好解释为什么不报 0——这个解释本身是加分项。
- **不说"拒答准确率 100%"**；不可答题的拒答率实际是 0.50。真正硬的是**假前提断言率 0.0**
  （12 道诱导题一次没编造），它从不编造，只是不总是显式说"我不知道"。用后者，并讲清区别。
- **不说"扩展黄金集至 109 题"**；新挖的 19 题是模型标注、未经人工复核，文件头写着
  `method: model_assisted`。要讲就讲方法：设计了从真实流量挖掘评测题的链路，并排除了
  评测自身回放造成的污染（247 行 rag_query 中 71 行是黄金集回放）。
