# 03｜RAG 深入：从问题到可验证答案

## 设计目标

资讯 RAG 的难点是时间、事件、来源与可核验性，不只是“找语义相似段落”。系统必须知道
“最近一周”对应什么日期、几篇报道是否是同一事件、哪条是一手来源，以及答案中的每个事实
究竟由哪个原文段落支持。

## 离线知识构建

```text
canonical 正文 → revision → 结构/语义切块
→ text hash 与定位 → bge-m3 1024 维向量
→ pgvector HNSW + tsvector/GIN + CJK bigram
→ entity/topic/story/time/source 元数据
```

Embedding 记录模型与版本；重建索引先写新版本、验证后切换。Story 摘要可以帮助组织答案，
但不能成为唯一最终证据。

### 原文切块到底怎样发生

1. RSS/API/列表只负责发现；适配器回到 canonical 页面取得正文，全文门通过后写 revision；
2. 切块任务读取**当前 revision 的 `body_text`**，不是 `summary_zh` 或 discovery snippet；
3. 解析 Markdown heading、段落、列表、代码块，目标 400 token、60 overlap、普通上限 700；
4. 单个超长结构最多 1200 token；长表格按行切，异常无换行正文按预算和标点继续切；
5. 保存原文 passage、heading path、ordinal 和字符定位；
6. bge-m3 的输入是“标题/来源/日期/heading + 原文 passage”，数据库引用仍只保存原文 passage；
7. 新 revision 会重新切块；Dense、Sparse、重排和引用都只 join `current_revision_id`。

正文版本和切块版本是两个生命周期。`content_revision` 只在来源正文改变时新增；切块算法升级
不会伪造一版正文，而是在同一 revision 下生成新的不可变 `chunk_set_id`。线上检索、向量回填和
健康统计只读 active set；历史 citation 继续指向 retired set 的物理 chunk，parent expansion 也
限定在同一 set。这个设计来自一次真实生产发现：定向重切试图删除已引用块，PostgreSQL 外键
拒绝删除并回滚事务。正确修复不是级联删除证据，而是版本化派生物。

这不是设计稿：2026-08-13 生产审计在修复前看到 2,098 篇当前非空正文、2,095 篇已有当前块、
7,912 个当前块全部有 bge-m3 向量，0 个块等于中文摘要；同时发现 14 个历史单行块超过硬上限，
由本轮修复和定向重建收口。动态数字不写成永久事实，完整查询见
[`../status/rag-corpus-audit-20260813.md`](../status/evidence/rag-corpus-audit-20260813.md)。

## 在线执行契约

### 1. Query Planner

规则规划器输出冻结的计划：问题类型、标准化问题、子问题、实体、主题、绝对时间窗、内容类型、
来源层级、回答形式和是否需要澄清。相对时间按用户时区解析；新时间表达覆盖旧时间窗，
“它/那家公司”可继承上一轮实体。通用 LLM 改写默认关闭，因为它增加延迟且未证明 Recall 收益。
2026-09-24 在发布快照配置上复测：LLM 规划器 Recall@20 0.8908 对正则 0.8998，逐题 0 升 2 降，
每问多 0.8 s——分类更准不等于召回更好，继续关闭。

### 2. 多路召回

| 通道 | 擅长 | 典型缺陷 |
|---|---|---|
| Dense pgvector/HNSW | 自然语言、同义改写、语义相似 | 型号与精确词可能排后 |
| Sparse tsvector/GIN | 版本号、缩写、模型名、精确术语 | 改写或跨语言表达较弱 |
| Temporal SQL | 绝对时间窗、已发布状态、来源级别 | 不独立判断语义相关性 |
| Entity temporal | 目标公司/模型在时间窗内的内容 | 实体消歧错误会漏召回 |
| Story/Graph-lite | 事件级聚合、关系与时间线 | 摘要不能替代原文证据 |

生产常用 dense 60、sparse 40，再按明确时间/实体启用结构通道。真实旗舰题的正确证据
dense 第 14、sparse 第 1、融合第 3，证明两种召回解决不同问题。

两个通道在生产上都踩过执行计划的坑（2026-09-24）：

- **稠密**：无时间窗时不用 HNSW 近似——实测 `ef_search=100` 与精确结果的重合最低只有 0.65。
  改为「先在分块表按距离排序、再 JOIN 条目」，生产 11.3 s → 约 2 s，结果逐条一致；
- **关键词**：规划器把「条目⋈版本」估成 1 行（实际 7,521），走嵌套循环逐版本取全部分块再测全文
  匹配，GIN 索引没用上，读盘 48,521 页、13.4 s。用 MATERIALIZED CTE 固定「先走索引再 JOIN」后
  0.8 s（v0.1.31）。本地内存装得下整张表，所以两次都只在生产上暴露。

### 3. RRF 融合

向量相似度、全文 rank 和时间分数不同量纲，直接线性相加不稳定。RRF 使用各通道名次：

```text
score(d) = Σ weight(channel) / (60 + rank(channel, d))
```

权重不是凭感觉永久固定。B8 扫描 42 组权重，在统一 reranker 后差距缩到 0.0004，因此生产
保持简单默认值，没有为了离线中间分做无收益改动。

### 4. 交叉编码器重排

`bge-reranker-v2-m3` 同时读取 query 与 passage，得到统一相关性；随后施加有限、可解释的
directness、source_fit、temporal_fit 调整。每一项调整必须落检索轨迹，不能隐藏成“神秘分数”。

### 5. 证据集选择

目标是在 token 预算内最大化子问题覆盖、来源多样性、事实直达度和一手来源比例，同时降低冗余。

- 同一文档限制占位；
- 同一 Story 保留主来源和少量提供增量信息的独立来源；
- 比较题为各对象保留接近的证据预算；
- fact check 至少需要一手直接证据或两个独立权威二手来源；
- 每个被淘汰候选记录“同篇超额 / 同事件折叠 / 预算已满”等具体原因。

### 6. Parent/Child 上下文

命中 chunk 后按问题类型做三档扩展：只补标题与 heading、补前后相邻块、或补更大父级上下文。
扩展帮助模型理解语境，引用仍落到一个原始 chunk。模型常从父块里的**兄弟段落**取事实，所以在
整篇/章节层级内，引用锚点按「引用它的每一句」重选到真正支撑的那段（ADR-0035/0037）：悬停
段落的支持率 0.8613 → 0.8993。

### 7. 受约束生成

DeepSeek 只看到带稳定编号的证据 `[E1]…[En]`，输出 answer Markdown、claims/evidence_ids 和
limitations。生成模型可以在 `deepseek-v4-flash` 与 `deepseek-v4-pro` 白名单内由 OPERATOR
切换；Embedding/reranker 固定，切换生成模型后历史内容和向量不自动重算。当前配置名
`deepseek-v4-flash` 已由 DeepSeek-V4.1-Flash 提供服务——供应商静默升级，调用方收不到通知。

### 8. 服务端引用绑定与四类防线

模型输出不被信任：

1. 解析编号，只接受当前证据集内的 ID；
2. URL、标题、passage 和定位全部从 PostgreSQL 重新取得；
3. 先评支持度、删除弱引用，再删除所有无服务端引用的事实句并重编号；
4. 引用越界、零引用非拒答、空正文非拒答、无法绑定等不变量失败时返回部分答案或拒答。

模型偶发不输出 JSON 时可以走带守卫的 Markdown/claims 回退，但回退不绕过绑定与校验。

含两个以上数字且有比较措辞的答案，再过一次**数值审计**（ADR-0023/0034/0036）：审计只核数字之间
的关系；无需修改时只回 `{"verdict":"ok"}`，草稿仍须通过算术不变量——同一子句里的每个百分比都
必须能由其中一对价格算出——两次不过就 fail closed。

### 9. 支持度审计

同一个交叉编码器对「每条引用所配的一句 claim × 模型读到的父块」打支持度：弱引用剔除，失去引用的
句子删除。注意这是**每条引用一句，不是每一句**——一个 `[n]` 常被多句共用（FROZEN 基线 272 条引用中
155 条）。逐句补测 685 对：按父块 0.9168、按悬停段落 0.8613。逐句删除实测后被否决：要删的 23 句里
至少 14 句原文里有，交叉编码器是相关性模型、不是蕴含模型（ADR-0037）。自动支持度也不擅长
“整组证据都没有提到某事实”的否定结论，因此高风险数字、单位、主体和分母仍需人工 P0 审查。

### 自动门禁与人工复核的真实边界

本作品集保留自动发布门、原始 artifacts、候选抽样与人审校验工具，但**没有完成主题地图 1,995 条
候选的双人盲审，也不声称关系分类 precision/recall 已由人工证明**。如果是团队产品，人审流程会是：

1. 按厂商 `primary/related/mention/unmatched` 和主题 `public/suppressed/unmatched` 分层抽样；
2. 样本绑定 revision id、正文 hash 和定位，审核界面隐藏生产预测；
3. 两位审核者独立标注，分歧交第三位裁决者；
4. 校验器拒绝空层、重复样本、revision 漂移和缺审核元数据；
5. 按总体分层权重估计 precision/recall，并给 bootstrap 95% 置信区间；
6. 指标达标后才校准阈值或训练 v2，旧规则与负结果继续版本化。

简历面试的正确说法是“我把可复现的人审基础设施和 fail-closed 门禁做完了，但个人作品没有伪造
双人/三人标注结果，因此没有把待审核候选数包装成准确率”。RAG 的 90 题自动评测与主题关系人审
是两套问题，不能混为一谈。

作品集明确省略真实人工阶段后，线上不会把“未审核”伪装成“人工通过”：主题关系继续由可重放
的确定性规则与公共置信门输出；`/eval` 继续展示自动回归；人审候选、隐藏预测、校验器和评估器
仅作为团队化方案与工程能力证明。简历可以陈述“设计并实现人审基础设施”，不能陈述“完成双人
盲审”或引用不存在的人工精度。

这不会阻塞当前作品集发布：人审评估的是“主题/厂商关系分类器的外部效度”，不是每篇资讯入库、
日报生成或 RAG 在线查询的同步审批。若未来真正产品化，审核产物应形成版本化 label set，用来
校准下一版规则与离线发布门，而不是让审核员逐篇批准实时资讯；高风险数字/许可/安全结论才进入
单条 P0 复核队列。这样既保持资讯时效，也不把自动分类结果冒充人工事实。

## 检索轨迹与可观测性

每次问答写 `rag_query_id`，记录计划、语料 cutoff、Embedding/reranker/generation 版本、各通道
候选与名次、RRF、重排、元数据调整、选证/淘汰、父块策略、token、缓存、耗时、答案与引用。
`/ask/{id}` 可以解释为什么选这几条；`/ops` 汇总真实请求的延迟、token 和估算成本。

缓存键包含标准化问题、计划、模型/Prompt/索引版本与语料新鲜度。命中缓存可以把重复提问从
14171ms 降至 211ms，但新内容到达后必须失效，不能用性能换过期事实。

## 发布评测

90 题黄金集覆盖近期变化、时间线、比较、事实核验、原理解释、不可答/诱导六类各 15 题。
`/eval` 展示固定 run：语料、模型、Prompt、算法或切块变化后重跑并生成新快照，旧 run 永不覆盖。

两条 2026-09 的机制变化：

- **生成评测按每题提问时间冻结语料**（`corpus_cutoff=asked_at`）。此前检索评测早已冻结，生成评测
  却能看到提问日之后的内容；冻结后引用准确率 0.5673 → 0.6888（逐题配对 +0.124）——泄漏让旧数字偏低；
- **门禁在 CI 里执行**（ADR-0038）：门槛在 `release-gate.json`，页面与 `check_release_gate.py` 共用；
  CI 从 `data/eval-runs/` 重建汇总并比对（手改会失败），7 项条件逐项校验，不达标不出发布镜像。
  CI 不重跑评测（付费、约 40 分钟），改了代码却忘了重跑仍靠发布纪律。

| 指标 | 关注问题 | v0.1.30 快照 |
|---|---|---:|
| Recall@20 | 相关证据找到了吗 | 0.8998 |
| MRR | 第一条相关证据是否靠前 | 0.8741 |
| nDCG@10 | 前十多级相关性排序 | 0.8243 |
| 引用完整性 | 事实句有没有证据 | 1.0000 |
| 段落支持达标（每条引用） | 证据是否支撑陈述 | 0.9900 |
| 逐句支持（悬停段落 / 父块） | 每一句是否被支撑 | 0.9319 / 0.9382 |
| 可答题误拒 | 有答案却拒答 | 1/78（随机量，见下） |
| 诱导题错误断言 | 无证据时是否顺着编 | 0/12 |

上表为 v0.1.30 发布快照（2026-09-24；检索重排 40 候选，与生产一致）。**误拒一项不能报 0**：
同一镜像、同一提示词连跑四轮是 2 / 1 / 1 / 3 且每轮失败的题目都不同——单题误拒概率约 2.24%，
78 题全过的概率仅约 17%。本轮 1/78 的原因是模型漏标引用、整句被删，属于模型侧随机原因，不阻断
发布。诱导题错误断言 0/12 则是稳定复现的，可以直接报。

区别在于：**一个是随机量的一次抽样，一个是被反复验证的系统属性。** 简历和答辩里
只报后者，前者要带方差说明。

## 失败实验与根因修复

- **B2**：dense/sparse 直接并集比纯 dense 差，证明“多一路”不等于“更好”。
- **B8**：RRF 权重扫参在 reranker 后无实质差异，结论是不改。
- **B13**：CJK bigram 对 RAG 端到端 ±0，但站内中文搜索提升 10–32 倍；同一优化对不同产品出口价值不同。
- **GEN-FIX**：误拒从 1.28% 升到 7.69%，原假设是语料增长造成证据竞争；抓原始响应后发现
  答案完整正确，只是 JSON/claims 偏离被解析失败分支清空。修复出口后 08-11 批次误拒为 0，
  原假设被证伪。
- **误拒指标本身是随机量**（2026-08-30 补测，也是这套评测里我自己被证伪的一次）：上面那个
  "修复后为 0" 是一次采样。同配置连跑四轮为 2/1/1/3，我此前据此说过"门禁失败是代码回退
  不是模型问题"——那句话错了，**把噪声当成了信号**。门禁遂从"误拒必须为零"改为阈值门禁
  （≤5%），只对"编造假前提"保留零容忍，因为那一项实测确实稳定为 0。
- **数字关系审计**：引用支持度接近 1 仍可能把百分比分母与单次价格混淆，新增受控数字关系审计并 fail closed。
  2026-09-23 它反过来把算术正确的「$0.50 → $0.20，下降 60%」判为不安全、整份拒答——规则看的是版面
  （一句里有百分比和两个价格）而不是算术。改为「每个百分比须能由同句价格算出」（ADR-0034）；
  审计无需修改时只回 ok，配对 31 次耗时均值 3.9 s → 1.0 s、无漏纠（ADR-0036）。
- **FROZEN（评测泄漏）**：见上文「发布评测」。直觉以为泄漏会让分数虚高，实测方向相反。
- **ZH（中文去碎片）**：bigram 让纯中文题的关键词通道 R@20 从 0 到 0.34，但跨词碎片（如 `近在`、`新动`）
  稀有，在 IDF 排序下压过专名。去碎片修法在 P0 厂商专项上退 1 题，未上线。
- **SENTENCE（逐句删句）**：见上文「支持度审计」，否决删句，改为按句选锚点。
- **本地快、生产慢**：见上文「多路召回」，两次执行计划问题都只在生产暴露。
- **引用阻止重切**：生产定向重切被 `rag_citation → content_chunk` 外键拒绝，证明物理 passage
  是审计证据而非可随意覆盖的缓存。事务回滚避免数据损坏，随后用 immutable chunk set 把“正文
  revision”和“处理规则版本”拆开，并让 current retrieval 与 historical audit 同时成立。

## 成熟度与剩余风险

当前已具备成熟 RAG 的主要骨架：混合召回、元数据过滤、重排、父块、证据多样性、引用绑定、
拒答、轨迹、缓存、固定回归集和线上运行指标。线上无时间窗问题仍要 11–20 s（2C4G 库内存装不下
918 MB 分块表），删除无依据句需要蕴含级裁判，黄金集纯中文题只有 8 道、未标注时间窗。
仍缺少更广的别名/错别字/跨语言/同名实体噪声集、
自动 citation precision 的大样本人审校准、真实用户反馈闭环、知识快照版本选择，以及私有语料场景
才需要的账号/租户/ACL。一个 SLA 专项问题目标原文稳定第 27，当前选择安全拒答而非无限加候选。

### 面试定位

它足以支持“公开资讯时效 RAG/AI 后端”作品集面试，但不应包装成通用企业知识库：真正完成的是
原文回源、结构切块、全量向量、混合检索、可验证生成、自动评测和生产运维；未完成的是人工
citation precision 大样本校准、多租户 ACL、私有文件解析、用户反馈学习和高并发容量验证。面试时
先说业务边界，再给生产数据与失败实验，最后主动说这些缺口，比宣称“成熟企业级 RAG”更可信。
