# Agent 与 RAG 深挖问答

这份材料用于压力面试。回答顺序固定为：先给边界，再讲链路，然后给代码/数据证据，最后承认尚未完成项。

## 一、RAG 全链路口述

### Q1：从一篇文章到能够回答问题，完整流程是什么？

1. registry 中的 adapter 发现 URL，回 canonical 页面取得原始正文；
2. 经过全文门、URL 规范化、幂等与 `content_revision` 版本化；
3. LLM 结构化摘要、实体和 claims，但 schema 失败不污染原文；
4. `chunk_document()` 对 `body_text` 按标题/段落/列表/代码边界切块，保存字符定位；
5. Embedding 输入在原文块外增加标题、来源、日期和 heading 上下文，bge-m3 写 pgvector；
6. 查询侧解析意图、实体和时间；dense/sparse/temporal 多路召回；
7. RRF 融合、bge-reranker 交叉编码器重排、父段预算展开；
8. `answer-v6` 只能基于编号证据生成；服务端绑定引用、审计数字和段落支持；
9. 完整答、部分答或拒答，查询、trace、答案和引用入 PostgreSQL。

### Q2：真的切了原始文章吗？怎么证明？

是。数据链为 `content_revision.body_text → chunk_document → content_chunk.body_text → load_evidence`；摘要字段
不参与。可以用 `char_start/char_end` 回切 revision 与 chunk 比对。Embedding 的输入会附加上下文以提高召回，
但引用展示和证据验证使用原文块。2026-08-13 本地库有 9,184 个活动块且全部有 Embedding；其中 5 个是
旧算法遗留超长块，当前算法重跑可降到 1200 token 内。生产 V026 版本集审计活动超长块为 0。

### Q3：切块参数为什么这样定？

目标约 400、最小 120、通常最大 700、重叠 60、硬上限 1200。400 在完整语义和检索粒度间平衡；短块合并
避免上下文不足；重叠保护跨段事实；硬上限处理超长列表/无标点文本。参数必须通过黄金集和超长审计调整，
不是通用最佳值。token 目前是稳定估算而非 provider 精确 tokenizer，这是边界。

### Q4：为什么用 pgvector，不用 Elasticsearch/Milvus？

当前万级块、低并发、过滤依赖内容状态/时间/实体，PostgreSQL 能在同一事务和查询中完成 dense、全文与
业务过滤，备份恢复简单。专用向量库会增加一致性和运维成本。触发迁移条件应是百万级、独立扩缩容或经过
索引调优仍达不到 Recall/P95，而不是“RAG 项目都应该用向量库”。

### Q5：混合检索怎样融合？

dense 处理语义同义，PostgreSQL sparse 守型号/版本，时间/实体解析形成过滤或附加通道。RRF `k=60`，主权重
dense 1.0、sparse 0.6、temporal 0.15，之后对前 20/40 使用交叉编码器。小幅元数据 boost 不能替代 rerank。
B2 说明简单交错会退化，B8 说明盲扫权重无收益，所以每个策略都由黄金集决定。

### Q6：什么时候拒答？

不是只看 cosine。候选经过重排后，生成 claims 必须绑定存在的 evidence ids，正文必须被证据段支持，数字
还要独立审计。支持不足时删弱断言；核心问题仍可答则部分回答，否则拒答。固定 90 题包含 12 道不可回答题，
当前发布快照误拒 0/78、诱导题误断言 0/12，但高风险数字仍需要人工抽审。

### Q7：黄金集会自动刷新吗？

不会跟每日采集一起自动变化。黄金集是版本化标注资产；新增问题或修正标注需要审阅。每次改检索、模型、
Prompt、chunk/index 版本才重跑并产生新 run。线上内容数和信源健康是动态指标，`/eval` 是发布实验记录。

## 二、Agent 与记忆

### Q8：项目为什么算 Agent，又为什么不是通用 Agent？

它具备感知、受限规划、工具调用、短期记忆和验证，因此可称 workflow agent；但没有自由工具选择、任意
Shell/SQL 或无限 ReAct loop。执行图由代码固定并有超时、预算和重试，更符合可信资讯场景。

### Q9：多轮记忆怎么做？

Redis transcript TTL 约 2 小时，只取最近约 6 轮；改写器看历史问题和已绑定引用标题，不看旧模型答案。
PostgreSQL保存查询、答案和引用用于审计。Redis 丢失只损失对话便利，不损失业务事实。

### Q10：怎样处理“它/那家公司”这样的指代？

查询改写器结合最近问题和引用标题生成独立 query，同时保留原始 query；planner 再解析实体/时间。若改写失败
或没有历史，直接用原问题，不让模型改写成为单点故障。

### Q11：是否有规划推理？

有确定性 query planning：分类最近动态、时间线、比较、事实核查、原理和不可答，并解析日期/实体。也有可选
LLM planner 代码，但不是生产唯一依赖；规则是安全地板。不要声称使用了完整 CoT Agent，系统也不存模型隐式
思维链。

### Q12：工具调用有哪些？

采集适配器、全文回源、Embedding、SQL 检索、rerank、生成、SMTP 都是代码受控工具。模型不会返回一个
工具名后获得任意执行权；工具参数由 Pydantic 和 allowlist 构造，外部 URL 还过 SSRF 与 registry 策略。

### Q13：为什么不使用 LangChain/LangGraph？

当前步骤有限，核心价值是自定义 SQL、RRF、引用校验和评测；直接 Pydantic/httpx 更透明。框架不会自动
解决检索质量、事实一致性或容量。如果出现可暂停恢复的长流程、多工具并行和人工审批，才评估 LangGraph，
并以可观测性、恢复性和依赖成本做 A/B。

## 三、Prompt、成本与安全

### Q14：系统 Prompt 如何写？

不是一个全局万能 Prompt。enrich-v2、recommend-v2、report-v3、answer-v6、rewrite/planner 分开版本化。
共同结构是：角色边界、输入是数据非指令、允许的字段/枚举、证据要求、拒答条件、长度和 JSON schema。
输出都被当作不可信输入校验。

### Q15：如何防止文章里的 Prompt injection？

正文明确作为不可信数据；模型没有管理凭据或任意工具；抓取 URL 和工具集合在代码中；输出 schema 和引用
由服务端验证。该方案降低 blast radius，但不能宣称完全防御所有模型攻击，因此敏感操作不经过 RAG。

### Q16：成本怎么控？

revision/content hash 避免重复处理；Embedding 7 天缓存、答案 1 小时缓存；rerank 20/40 候选，证据约 10 段，
父段 2000 token 预算，会话只取最近轮。`llm_usage` 分操作记录 token、缓存、延迟和模型。压测外部模型用
mock/replay，生产以预算告警和有界重试控制突发费用。

### Q17：生成模型和 Embedding 能否任意切换？

生成模型由数据库配置并需重跑生成门；Embedding 不能直接热切换，因为新旧向量不在同一空间，必须版本化
重嵌入和索引切换。reranker 也要重跑排序黄金集。三个模型职责解耦不是三个随便的下拉框。

## 四、反问与陷阱

### Q18：你最大的技术亮点是什么？

不要回答“用了 RAG”。应回答：把采集原文、版本化 chunk、混合召回、引用绑定和固定黄金集连成可追溯闭环；
并保留 B2/B8 等负实验、GEN-FIX 解析故障和回滚条件。亮点是可证伪的工程方法。

### Q19：当前最明显的不足是什么？

主题关系仍是弱监督规则，尚无真实双人标注准确率；本地旧数据需要显式 re-chunk maintenance；2C4G 尚未做
隔离容量曲线；没有账号体系和长期个性化。这些都应给出触发条件，不要把作品项目包装成大规模商业系统。

### Q20：如果面试官要求现场证明怎么办？

按以下证据走：

1. 打开一条问答，看句级引用和原文回跳；
2. 指向 `processing/chunking.py`、`rag/retrieval.py`、`rag/answer.py`；
3. 展示 V026 版本化 chunk 与 90 题 eval artifact；
4. 展示 B2/B8/GEN-FIX 的逐轮记录；
5. 若网络异常，使用仓库脱敏截图和状态文档，不现场伪造模型结果。
