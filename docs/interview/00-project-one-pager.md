# 00｜项目一页纸
## 一句话定位

AI Hot Radar 是一个面向 AI 行业的可追溯时效情报平台：从配置化公开信源持续采集正文，
完成结构化、去重、事件聚合、精选与日/周/月报告，并在同一份原文证据库上提供可解释 RAG。

## 30 秒介绍

> 我做的不是简单新闻聚合，而是一条从公开信源到可核验答案的完整数据链。系统用 Python
> 采集和处理正文，用 PostgreSQL 保存内容、事件、向量和发布事实，用 Java 提供内容、订阅与
> 管理 API，用 Next.js 交付网站。RAG 同时做语义、关键词和时间/实体召回，再重排、折叠事件、
> 绑定原文引用。项目已经在 2C4G 单机上线，90 题发布门禁接入 CI，另有备份恢复、告警和邮件订阅。

## 3 分钟介绍

先讲业务：AI 信息散落在博客、GitHub、论文和媒体中，用户需要及时发现、减少重复、按事件组织，
并能核验总结。信源登记数与运行状态会动态变化；RSS/列表只做发现，必须回 canonical 页面通过全文门；
正文经版本化、schema 校验的 LLM 结构化、切块、向量化、去重与 Story 聚类后，同时驱动精选、
热点、主题、报告、邮件与 RAG。

再讲架构：Next.js 负责 SSR 和同源代理；Spring Boot Core API 负责稳定读接口、报告发布、
双确认订阅、RBAC 与审计；FastAPI AI Service 负责采集、加工、Embedding、Rerank 和问答；
PostgreSQL + pgvector 是唯一事实源，Redis 只做可丢缓存、限流和短锁。模型推理外置，因此
Docker Compose 在 2C4G 上足以承载当前低并发作品集。

最后讲差异：RAG 不是黑盒。每次问答保存多路召回名次、RRF、重排、元数据调整和淘汰原因；
模型只能引用编号证据，后端重新绑定真实 chunk 和 URL，并删掉弱支持或无引用事实。当前发布
快照（v0.1.30，2026-09-24）Recall@20 0.8998、事实句引用完整性 1.0、段落支持 0.99（逐句 0.93）、
诱导题错误断言 0/12，门禁接入 CI，不达标就发不出版本。项目还公开保留了负实验、一次被原始
模型响应证伪的根因假设、一次**把噪声当成信号的自我纠正**（误拒同配置四轮 2/1/1/3，硬门禁
改成阈值门禁），以及一次**评测自身的未来信息泄漏**——冻结语料后发现旧数字把引用准确率
低估了 12 个百分点。

## 10 分钟展开顺序

1. 业务问题与用户出口；
2. 采集、全文、幂等、Story 与报告链；
3. Java/Python/PostgreSQL/Redis 的职责边界；
4. RAG 的 Dense + Sparse + Temporal → RRF → Reranker → 选证 → 引用校验；
5. 固定评测与动态运行数据为什么分开；
6. 评测泄漏、生产慢查询（本地 0.15 s / 生产 13 s）、GEN-FIX 任一真实故障；
7. 不引入 Kafka、独立向量库和 Kubernetes 的证据与触发条件；
8. 生产发布、备份恢复、SMTP 与未来迁移。

## 三个最能体现工程判断的点

- **事实源单一**：内容、向量、状态、检索与投递都在 PostgreSQL，避免业务库/向量库双写漂移。
- **输出不信任模型**：schema、服务端引用绑定、删除无引用句、不变量与支持度共同守住回答出口。
- **负结果可见**：混合召回退化、权重无收益、中文分词只改善站内搜索等结果都留下证据。
- **评测先被怀疑**：给评测找出未来信息泄漏，先测裁判的准确率再用它做决定（逐句删句因此被否决），
  门禁放进 CI 而不是只在页面上显示。

## 主动承认的边界

- 自动支持度不是高风险陈述的人审；一个 SLA 专项问题仍安全拒答；
- 支持度按**每条引用一句论断**打分，逐句是 0.93；交叉编码器测相关性不测蕴含，所以不据此删句；
- 线上无时间窗的问题要 11–20 s：2C4G 上数据库内存（`shared_buffers` 128 MB）装不下 918 MB 的分块表；
- 信源后台是数据库快照，不是实时告警控制台；
- 管理写 API 已有安全边界，浏览器 UI 尚未补齐；
- 个人 SMTP 只适合验证，正式投递需自有域名、SPF/DKIM/DMARC 和退信处理。

## 30 分钟深挖目录

1. 业务：发现、事件、报告、追问为什么必须共用事实层；
2. 数据：source → raw → item → revision → chunk → story → report/query；
3. 运行：Caddy、Next、Java、Python 三角色、PostgreSQL、Redis；
4. 采集：配置化 adapter、回源全文、SSRF、游标、幂等；
5. 内容：schema、去重、Story、精选多样性；
6. RAG：计划、三路召回、RRF、rerank、parent/child、生成出口；
7. 评测：黄金集、冻结语料、指标与 CI 门禁、B2/B8/B13/GEN-FIX 与评测泄漏；
8. 业务可靠性：报告发布、双确认订阅、投递重试；
9. 交付：CI、SHA 镜像、Caddy、备份恢复和回滚；
10. 边界：Outbox 未消费、单 embedding、单机、Bearer 管理认证。
