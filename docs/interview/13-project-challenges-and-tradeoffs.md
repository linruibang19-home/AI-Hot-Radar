# 项目困难、失败实验与技术取舍

面试官真正关心的不是“用了哪些组件”，而是遇到什么不确定性、如何拿证据、为什么没有选择看起来更高级
的方案。本章将项目中最能深挖的场景整理成“问题—错误直觉—定位—修复—验证—仍存边界”。

## 场景一：RSS 有内容不等于拿到了原文

**问题。** 很多 Feed 只有标题和一两句摘要；有些列表页混入导航、cookie 和推荐卡。如果直接把 excerpt
当正文，摘要、切块和引用都会围绕不完整文本运行，页面看似有内容但 RAG 无法提供原文证据。

**错误直觉。** “Feed 能解析就算采集成功”或者“让 LLM 扩写摘要”。前者污染语料，后者制造不存在的原文。

**解决。** source registry 只负责发现，adapter 回到 canonical URL，经过 SSRF、类型/大小、正文密度、
占位/截断和长度门；原文失败时记录 discovery metadata 与状态，不进入可引用正文。正文、摘要、来源和抓取
状态分表/分字段保存，避免两份状态漂移。

**验证。** replayable fixture、fulltext gate、`/admin/sources` 的全文率和最近成功时间。关键规范：
`docs/spec/09-source-registry-fulltext.md`、`docs/spec/10-source-adapter-implementation.md`。

**追问。为什么不用浏览器爬虫全部兜底？** 浏览器成本、失败面和法律/robots 风险更大，只应对已授权且
普通回源无法处理的来源定向启用，不能为了数量绕过全文门。

## 场景二：切块既要适合检索，又要保留可引用原文

**问题。** 固定字符切割会把标题、列表、代码和一句事实拆开；超长段落可能突破模型输入；短段太碎又让
Embedding 缺乏语义。更隐蔽的问题是算法升级后，数据库里旧活动块不会自动重切。

**当前实现。** `processing/chunking.py` 从 `content_revision.body_text` 读取原始正文，按 heading、段落、列表、
代码边界切分，目标约 400 tokens、最小约 120、通常最大 700、重叠约 60，并用 1200 token 硬上限兜底。
每块保存正文、heading 和字符定位；Embedding 输入额外拼标题/来源/日期上下文，但最终引用仍返回块内原文。

**版本化困难。** V026 把 chunk set 版本化：重切时同一事务退休旧集合并插入新集合，历史 query 仍能找到
当时引用；但是 `_unchunked_revisions` 只发现“没有活动块”的 revision，不会因算法版本变化自动处理已有块。
2026-08-13 审计发现本地旧数据仍有 5 个超过 1200 token 的活动块，当前算法重跑同一正文可落到上限内；
生产 V026 后活动超长块为 0。正确演进是显式 re-chunk maintenance job，而不是启动时偷偷覆盖。

**如何证明切的是原文而不是摘要。** 调用链是
`content_revision.body_text → chunk_document() → content_chunk.body_text → load_evidence()`；摘要字段不在这条
链上。可以抽样比对 chunk 的 `char_start/char_end` 与 revision 正文，并审计 active chunk 的 Embedding 覆盖率。

**为什么不用“语义切块模型”。** 当前约万级块，结构化正文边界已经稳定、成本为零且可重放；模型切块会
增加费用、不可重复和版本管理。若未来对表格/长 PDF 有明确检索损失，再以黄金集对照，而不是先换技术名词。

## 场景三：加入 sparse 通道后整体检索反而下降

**问题。** 理论上 dense + sparse 应互补，但 B2 中先用简单轮转交错合并，型号题改善，整体 MRR/Recall 却下降。

**定位。** 稀疏候选在英文型号查询很强，在中文同义问法很弱；无条件分配半数名额挤掉了 dense 的优质候选。

**解决。** 保留负实验；用 RRF 统一名次量纲，再用交叉编码器重排，并对 query type、实体和时间语义做受控
权重。B3 说明时间窗过滤贡献大于单独时间通道，B4 才证明 reranker 达门。

**验证。** 固定 90 题黄金集按六类查看 Recall@10/20、MRR、nDCG，不只盯总分；每轮保留 run id、代码、
索引与逐题结果。B8 扫 42 组融合权重收益近零后结论是“不改”，而不是隐去。

## 场景四：生成侧误拒被误认为检索质量问题

**问题。** 一轮生成评测误拒率升到 7.69%。初看像语料竞争或召回失败。

**定位。** 抓取原始模型响应后发现，六题答案内容完整：一种失败是直接返回 Markdown，没有 JSON；另一种是
只把证据编号放在 `claims[].evidence_ids`，正文不标号。解析器清空正文并判成拒答。

**解决。** 在失败分支加入受限正文回退，再执行同样的证据编号、支持度和禁止项校验；不是跳过 schema，
也不是“有字就放行”。

**结果。** 误拒率恢复到 0，诱导题误断言仍为 0/12。这个案例说明 RAG 排障必须保存 retrieval trace、原始
模型响应和解析结果，不能只看最终页面。

## 场景五：主题页关键词命中导致“看起来都相关”

**问题。** 一篇文章只是在对比段提到 OpenAI，却被放进 OpenAI 核心动态；用户看到数量很多但信任下降。

**解决。** V025 将 entity role、confidence 和正文位置共同投影为 primary/related/mention，并显示关系标签、
命中实体和刷新时间。primary 要求主体角色和标题/摘要前部强命中；比较、合作、影响归 related；顺带提及
归 mention。公共主题再用最低分和 top-N 限制噪声。

**边界。** 这仍是弱监督规则，不可宣称人工准确率。正式人工审核应从边界样本分层抽样，双人独立标注，
用冲突仲裁计算 precision/recall，再调阈值。作品项目省略真实人力阶段时，应把它写成待执行验证而不是假数据。

## 场景六：邮件“能发出去”不等于订阅闭环

**问题。** 直接保存邮箱并定时群发会造成误订阅、重复发送、无法退订和报告尚未发布就被发送。

**解决。** Core API 拥有订阅事实：申请 → 一次性确认 token → ACTIVE；退订即时失效。调度只选择
`PUBLISHED` 报告，`email_delivery` 使用唯一业务键幂等，失败可重试并记录状态。SMTP 密码只在部署环境，
Web 通过同源代理，不直接持有凭据。

**追问。为什么不引入 Kafka？** 当前单机、低发送量且 PostgreSQL 状态足以重试，Kafka 会增加运维面但不
解决双确认和幂等。若发送规模、消费者数量和削峰压力达到阈值，再启用 outbox consumer/队列；当前
`outbox_event` 只写不读，不能包装成完整消息系统。

## 场景七：页面卡顿不能只看数据库

**问题。** 用户点击主题和 SSR 页面感觉慢。只看代表 SQL 的亚毫秒平均值会误判。

**定位。** 2026-08-13 本地混合读压测中 Core P95 41.62 ms，而 Web SSR P95 510.15 ms；Web/Core 峰值 CPU
先超过一个逻辑核，Redis 远未饱和。瓶颈更可能是 SSR 请求瀑布、序列化和首个冷请求，而不是 Redis。

**解决方向。** 并行无依赖请求、避免同页重复聚合、使用稳定缓存键和骨架屏；用 k6 标签分别守 Core 与 Web
P95。不能因为开发机约 124 req/s 就声称生产 2C4G 有同样容量。

## 技术取舍速查

| 选择 | 采用原因 | 何时重新评估 |
|---|---|---|
| PostgreSQL + pgvector | 万级块、强事务过滤、全文/向量/业务状态同库，运维简单 | 百万级向量、独立扩缩容或召回延迟达不到 SLO |
| Redis 仅短状态 | 缓存/限流/会话可丢失，避免双事实源 | 仍不应成为业务事实；只调整集群与淘汰策略 |
| Java Core + Python AI | 稳定业务边界与 AI 生态分离 | 服务间写语义冲突或团队/负载要求进一步拆分 |
| Docker Compose | 2C4G 单机可控、恢复简单 | 多节点、高可用、独立扩容和团队运维成熟后 |
| 显式编排而非 LangChain | 步骤有限、强审计和自定义检索，依赖更少 | 多工具、可暂停恢复、长流程补偿成为主要复杂度 |
| 规则精选 + LLM 理由 | 冷启动可解释、低成本、多样性可控 | 有足量真实反馈可训练 LTR 后 |

## STAR 讲法

不要一次讲七个。优先选“GEN-FIX 误拒归零”或“B2 sparse 反退化”：

- **S**：固定黄金集/用户页面暴露异常；
- **T**：判断问题在检索、生成还是解析，且不能降低引用安全；
- **A**：保存逐步 trace，构造最小复现，修改一个变量，重跑同一数据集；
- **R**：给出带环境和样本量的指标，并说明仍未解决的边界；
- **反思**：最大的价值不是某个数字，而是建立“假设—实验—门禁—回滚”的工程方法。
