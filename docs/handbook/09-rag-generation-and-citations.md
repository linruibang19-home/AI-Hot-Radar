# 09｜RAG：生成、引用、安全校验与拒答

## 1. 模型看到什么

服务端把最终 evidence 组成带稳定编号的上下文，包含来源、标题、发布时间、原文段落和必要 parent
上下文。系统 prompt 明确只用给定证据、逐项引用、证据不足拒答。外部正文被当作不可信数据，
不能覆盖系统指令。

## 2. 为什么结构化输出仍然会失败

LLM 可能返回：合法 JSON、Markdown 正文、JSON 外壳加正文、截断 JSON、错误编号或把引用只写进
claims。早期生成评测把完整 Markdown 当作 JSON 失败并清空答案，误判为拒答。GEN-FIX 增加了
受控失败分支：先解析结构化 envelope；若模型给出完整正文，则抽取正文和证据编号；只有真正
无可发布正文时才拒答。

原则是“兼容输出形态，不放松证据约束”。不能因为 fallback 就允许任意 URL/编号。

## 3. 引用绑定

1. 候选证据在服务端获得临时 `E1...En`；
2. 模型只能引用这些编号；
3. 解析器丢弃越界或不存在的编号；
4. 服务端将编号绑定真实 `content_chunk_id`；
5. API 根据 chunk → revision → item 解析标题、来源、canonical；
6. 前端渲染服务端 citation DTO，不解析模型 URL。

这保证模型即使编造 `[E99]` 或恶意 URL，也无法产生可点击的伪引用。

## 4. 主张级支持检查

引用存在不代表引用支持主张。系统把答案拆成可验证主张，计算被引段落对主张的支持程度。弱支持
主张被移除或触发拒答；高风险数值关系走受控 LLM 审计。最终发布正确性还需要人工 PO 审计，
自动 citation precision 不能替代人工 entailment 判断。

## 5. 拒答和过度拒答

两类错误都要测：

- **该拒不拒**：语料没有答案，却给出推测；
- **不该拒而拒**：已经有充分证据，却因为解析、阈值或候选不足返回“无法回答”。

黄金集包含 answerable 与 unanswerable。拒答不是异常，也不应进入答案缓存；但过度拒答会直接
伤害产品可用性。

## 6. Prompt Injection 与敏感输出

- 原文中的“忽略之前指令”只是证据文本；
- provider key、内部 prompt、管理 token 不进入上下文；
- 输出做禁止词/敏感模式检查；
- 输入、模型输出、引用和 trace 的日志有长度/字段边界；
- 速率限制在调用昂贵 provider 之前执行；
- 第三方错误不把完整响应或密钥回显给浏览器。

## 7. 流式输出

增量流不能先把未经校验的幻觉展示出去再撤回。实现会缓冲到首个可解析引用或结构化正文片段，
过滤越界编号，并保证最终存储答案与用户看到的文本一致。连接中断时不缓存未提交答案。

## 8. 模型选择与成本

DeepSeek 生成模型目录和当前配置存 PostgreSQL，管理页面只能在 allowlist 中切换。每次调用记录
operation、model、config version、input/cached/output tokens、延迟与当时价目快照。成本页是按
价目估算，不冒充供应商账单。

SiliconFlow embedding/reranker 保持固定，因为更换 embedding 意味着全库重算、索引版本切换、
检索黄金集回归和缓存失效，不是普通生成模型切换。

## 9. 关键代码

- `rag/support.py`：支持度；

- `rag/incremental.py`：流式正文与引用；
- `rag/service.py`：端到端编排；
- `rag/api.py` / `router.py`：HTTP/SSE；
- ADR-0020/0021/0023/0024/0027。

## 10. 面试可讲的关键案例

GEN 到 GEN-FIX 不是“调 prompt”，而是定位评测出口：检索命中和正文都正确，失败发生在解析模型
响应时。修复后误拒答归零，同时保留支持度下降的真实代价。这说明 RAG 排障必须拆检索、生成、
解析、绑定和裁剪，而不能只看最终答案。
