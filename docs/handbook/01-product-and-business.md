# 01｜产品与业务架构

## 1. 项目解决的不是“新闻太少”，而是信息判断成本太高

AI 行业信息分散在公司新闻、产品文档、GitHub Release、模型卡、论文、技术博客和媒体中。
用户真正付出的成本包括：逐站查看、辨别是否一手、回源阅读全文、把同一事件的转载合并、
理解变化、保存证据，以及在几天后重新找回结论。

AI Hot Radar 把这些动作组织为一条可追溯情报链：

```text
发现公开更新
→ 回源拿到可验证正文
→ 规范化、去重、结构化
→ 把多篇报道聚成一个事件
→ 生成精选和日/周/月报
→ 用同一原文证据回答追问
```

“同一证据库服务多个出口”是业务核心。网站、报告、邮件和 RAG 不能各自维护一套摘要，
否则更新、下架和事实纠错会漂移。

## 2. 用户与使用场景

### 读者

- 快速浏览今日高价值动态；
- 按模型、公司、产品、论文等主题过滤；
- 查看同一事件的主来源和补充来源；
- 阅读日报、周报和月报；
- 提问“最近发生了什么”“两者差异是什么”“这个数字是否真实”。

### 邮件订阅者

- 选择日报、周报或月报；
- 通过确认链接证明邮箱所有权；
- 在本地时区约定时间收到已发布报告；
- 从邮件退订，不需要账号体系。

### 运营者

- 查看信源是否 ACTIVE、PROBING、QUARANTINED 或 METADATA_ONLY；
- 审核报告发布，而不是让模型输出直接群发；
- 查看生成模型、成本延迟、RAG 发布门和审计记录；
- 对高风险操作提供 Bearer Token、目标确认、幂等键和审计日志。

## 3. 业务能力地图

| 领域 | 用户能力 | 系统产物 | 事实来源 |
|---|---|---|---|
| 资讯 | 精选、全部动态、热点 | `content_item`、`selection_record` | 原始正文 + 结构化字段 |
| 事件 | 看同一事件的多源报道 | `story`、`story_item` | 多篇 content item |
| 主题 | 按公司/模型/技术浏览 | `entity`、`topic` 关系 | 受控分类 + 实体抽取 |
| 报告 | 日/周/月报阅读 | `report`、报告条目 | 已发布事件与精选 |
| 订阅 | 邮件确认、投递、退订 | subscription/delivery 表 | PostgreSQL |
| 问答 | 多轮 RAG、逐条引用 | `rag_query`、`rag_citation` | `content_chunk` 原文段落 |
| 工程 | 质量、运行、模型、信源后台 | 评测快照 + 动态聚合 | 版本文件 / 运行库 |

## 4. 业务规则中最重要的四个“不等于”

1. **发现摘要不等于正文**：RSS/search/listing 只能告诉系统“有这篇”，不能直接进入 RAG。
2. **文章重复不等于事件相同**：转载可压缩；不同来源报道同一事件仍要保留独立证据。
3. **AI 摘要不等于事实证据**：最终引用必须落到原文 `content_chunk`。
4. **生成完成不等于可以发布**：报告有状态机，邮件只发送 `PUBLISHED` 报告。

## 5. 商业与产品取舍

项目当前定位是内容情报产品和工程作品集，不是大规模 SaaS：

- 无账号体系，减少隐私和认证面；
- 邮件采用双重确认而非“填入即发送”；
- 单机 2C4G 使用 Compose，不为简历引入 Kubernetes；
- PostgreSQL 同时承载业务与 pgvector，先获得事务一致性和低运维成本；
- 模型切换只开放受控 DeepSeek 生成目录，不允许用户随意填写供应商和模型名；
- embedding 固定，避免不同向量空间混库。

## 6. 成功标准如何落到产品

| 成功问题 | 产品层回答 | 工程证明 |
|---|---|---|
| 内容新不新 | P0 来源采集延迟 | source/crawl 运行指标 |
| 内容真不真 | 一手来源、原文链接、发布时间语义 | canonical、source tier、原始响应 |
| 是否重复 | 同文压缩、同事件聚合 | hash/近重复、story relation |
| RAG 是否可靠 | 支持段落、拒答、引用发布门 | 90 题黄金集 + 人工审计 |
| 邮件会不会乱发 | 确认、发布状态、唯一投递键 | subscription/delivery 状态机 |
| 系统能否恢复 | 备份、锁、幂等、旧版本镜像 | runbook、CI、恢复证据 |

## 7. 面试时怎么讲业务价值

不要说“我做了一个 AI 新闻网站”。更准确的表达是：

> 我做的是一个时效性 AI 情报平台。它从 140 个配置化公开信源发现更新，但只有回源正文
> 通过质量门禁后才进入事实库；同一事实库同时驱动资讯、事件、日报邮件和带原文引用的
> RAG。项目重点不是多接几个模型，而是让采集、生成、引用、发布和恢复都有可追溯边界。

进一步追问时，应能解释为什么“新闻聚合”和“情报系统”的数据模型不同：后者必须保存
来源、原文 revision、证据段、事件关系、处理版本、发布状态与审计。
