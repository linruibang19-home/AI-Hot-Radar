# LLM、Prompt、排序与阈值：从模型调用到可审计决策

这一章回答四个经常被混为一谈的问题：系统在哪些地方调用大模型、Prompt 如何约束输出、
推荐与检索排序究竟由谁决定，以及页面上的“置信”到底是不是一个模型概率。所有数值均以
当前代码和迁移为准；模型返回值不天然可信，也不把经验阈值包装成统计概率。

## 1. LLM 在系统中的位置

| 场景 | 输入 | 输出 | 是否直接决定公开结果 |
|---|---|---|---|
| 内容结构化 | 标题、来源和正文头尾窗口 | 摘要、内容类型、实体、claims、技术深度等结构化字段 | 否；先过 Pydantic/JSON Schema，再进入确定性流水线 |
| 推荐理由 | 已被确定性算法选中的内容及正文摘录 | “为什么值得读”的短文案 | 否；它解释选择，不负责决定是否入选 |
| 日/周/月报 | 已发布候选集合与证据 | 主题、提要和分组的 JSON | 否；仍要校验、落版本、审核状态和发布状态 |
| RAG 查询改写 | 当前问题、最近问题和引用标题 | 面向检索的独立查询 | 受控；原始查询始终保留，改写不能覆盖用户语义 |
| RAG 查询规划 | 问题 | 意图、时间窗、过滤条件 | 默认不依赖 LLM；当前生产以确定性解析为底线 |
| RAG 回答生成 | 查询与编号证据段 | 带证据编号的结构化回答 | 否；服务端重新绑定、支持度审计和拒答策略决定出口 |
| 数字审计 | 数字型 claims 与证据 | 支持/不支持判断 | 否；只用于移除高风险断言，不会创造新事实 |

主要入口：

- 结构化与重试：`apps/ai-service/src/ahr/processing/enrichment.py`；
- 精选与推荐理由：`apps/ai-service/src/ahr/processing/selection.py`；
- 报告：`apps/ai-service/src/ahr/processing/report.py`；
- RAG 生成：`apps/ai-service/src/ahr/rag/answer.py`；
- 确定性规划与可选 LLM 规划：`apps/ai-service/src/ahr/rag/planner.py`、
  `apps/ai-service/src/ahr/rag/llm_planner.py`。

生成模型由数据库配置选择，迁移见 `database/migrations/V024__deepseek_generation_model_selection.sql`；
Embedding 与 reranker 保持独立供应链，避免切换生成模型时破坏索引空间。

## 2. Prompt 不是一段随意的自然语言

每类 Prompt 都有版本号、输入上限、输出模型和失败路径。通用防线如下：

1. **角色和边界**：只能根据给定正文或证据回答，不允许补充模型记忆；
2. **输出契约**：明确字段、枚举、长度和证据编号，要求 JSON；
3. **不可信解析**：先 `json.loads` 和 Pydantic 校验；模型偶尔输出 Markdown 时允许受限正文回退；
4. **一次修复机会**：结构错误可带校验错误重试一次，仍失败则拒绝该阶段结果；
5. **下游再校验**：RAG 的引用、数字和支持度不相信模型自报，由服务端重算；
6. **可观测性**：记录 provider/model、Prompt 版本、token、耗时、错误和 trace id，不记录密钥。

### 2.1 结构化 Prompt

`enrich-v2` 要求模型从原始正文提取摘要、内容类型、实体和 claims。系统传入的是正文头部与尾部，
而不是只传 RSS 摘要；长文保留尾部是为了避免结论、限制和发布日期只出现在文末。输出先经过
schema，再写入版本化内容记录。

困难在于模型会多包一层 Markdown、漏字段或生成不在枚举中的值。解决不是“调高温度再试”，
而是温度保持低、错误可定位、最多一次契约修复，并让失败内容仍能保留原文而不污染结构化字段。

### 2.2 推荐理由 Prompt

`recommend-v2` 的输入已经是精选算法选出的候选。Prompt 只要求从正文证据解释价值、限制和适用人群。
这避免了一个常见反模式：让 LLM 同时评分、选稿和写理由，最后既无法复现也无法解释配额为何失效。

### 2.3 RAG 回答 Prompt

`answer-v6` 给每个证据段分配服务器编号，要求每个事实性句子引用编号。模型输出后，服务端会：

- 删除不存在的编号；
- 将编号绑定到数据库 chunk 和原文 URL；
- 对段落执行支持度检查；
- 对数字型断言做额外审计；
- 对不可回答问题拒答，而不是用模型常识填空。

因此“模型在正文里写了 `[E1]`”不等于引用成立；引用成立必须同时满足编号存在、证据段可取回、
正文支持断言和公开 URL 可回跳。

## 3. 精选推荐算法

精选不是协同过滤，也没有用户画像。它是面向公共情报流的、可解释的内容级评分加多样性约束。
当前综合分位于 `processing/selection.py`，主要权重为：

```text
score = 0.34 * quality
      + 0.17 * source_authority
      + 0.17 * content_type_value
      + 0.09 * freshness
      + 0.08 * body_depth
      + 0.15 * corroboration
```

随后施加每日最多 12 条、单一 source 最多 3 条、同一 source family 最多 3 条、研究类最多 4 条等
约束。确定性选择完成后才调用 LLM 写推荐理由。

为什么不用“端到端 LLM 打分”：当前没有足够点击/收藏/停留反馈训练个性化排序；LLM 评分成本更高、
可重复性更差，而且很难证明来源配额和一手来源优先真的生效。当前方案适合冷启动公共产品；如果未来
拥有真实用户反馈，可在不移除质量门的前提下加入 learning-to-rank。

## 4. Story 融合与热点排序

同一事件可能有官方稿、媒体解读和转载。系统先进行规范 URL、内容哈希和近重复压缩，再构建 Story。
当前聚类特征是可解释代理特征，而不是声称已经使用全量语义图：标题、实体、动作/对象、时间和主题，
权重分别约为 `0.35/0.25/0.15/0.10/0.05`，缺失特征会重新归一化。合并阈值为 `0.52`，候选建议阈值
为 `0.42`，窗口 72 小时；同源和版本冲突存在 veto。

这个模块最容易被夸大。正确说法是：当前版本以高可解释、可回滚的规则形成事件骨架，语义向量是后续
可验证增强项；不是“已经实现知识图谱自动聚类”。

## 5. RAG 融合排序

### 5.1 召回层

系统并行使用：

- pgvector dense retrieval：处理同义表达和语义匹配；
- PostgreSQL full-text/sparse retrieval：守住型号、版本号和专有名词精确命中；
- 时间/实体过滤：把“最近”“某厂商”“某时间段”变成结构条件；
- 父段展开：子块命中后在预算内补上下文，不改变原证据块身份。

### 5.2 融合层

RRF 采用 `k=60`，当前主要权重为 dense `1.0`、sparse `0.6`、temporal `0.15`；实体型时间通道可到
`1.0`。RRF 使用名次而不是直接相加不同量纲的相似度，降低了 dense 与 sparse 分数不可比的问题。

融合后还有可解释的小幅元数据调整：主题主体、一手来源、时间窗命中获得有限加分；重复转载、事实核查
问题中的观点文本受到扣分。这些只是 tie-breaker，不能把无关候选“抬进来”。

### 5.3 重排层

前 40 个候选进入交叉编码器；部分简单查询为控制延迟只重排 20 个。重排后再加入 directness、
source-fit、型号/标识符精确匹配等小权重。B2 实验证明盲目加入稀疏通道会使整体 MRR 下降；B8 证明
扫描大量权重组合收益近乎为零。因此系统保留失败实验，并通过固定黄金集决定是否采纳，而不是看到一题
变好就上线。

## 6. “置信度”和阈值分布在哪些地方

| 环节 | 当前阈值/信号 | 含义 | 不是什麽 |
|---|---|---|---|
| 全文门 | 字数、正文密度、占位/截断模式 | 是否允许进入正文语料 | 不是 LLM 概率 |
| Story | merge `0.52`、suggest `0.42` | 是否自动合并或只列候选 | 不是聚类准确率 |
| 厂商关系 | entity role/confidence + 标题/摘要位置 | primary/related/mention 的可解释规则 | 不是“文章属于厂商”的统一概率 |
| 公共主题 | 关系分数至少约 `0.60`、每条最多 3 个 | 控制主题页噪声 | 不能代替人工标注准确率 |
| RAG 支持度 | 段落支持阈值约 `0.30`、弱支持比例约 `0.50` | 过滤低支持断言并选择部分答/拒答 | 不是检索 cosine 阈值 |
| RAG 语义缓存 | 相似度约 `0.97` | 只复用近乎相同问题的缓存答案 | 不是检索相关性门槛 |
| 发布门 | Recall、引用完整性、段落支持、误拒/误断言 | 固定黄金集是否允许发布 | 不能替代线上人工高风险审计 |

厂商关系的具体规则由 `database/migrations/V025__auditable_vendor_relations.sql` 建立：主体角色且高置信、
标题或摘要前部直接命中才算核心；比较、合作和受影响对象归 related；正文顺带出现归 mention。页面显示
命中实体和关系层级，让用户知道“为什么被收进主题”，不再把关键词出现冒充核心动态。

## 7. 黄金集是什么

黄金集是版本化的问答与期望证据集合，不是模型生成的一批示例。当前 90 题覆盖六类查询，并包含：

- 问题及可回答/不可回答标签；
- 期望命中的原始内容或 chunk；
- 必须出现和禁止出现的事实；
- 查询类别、时间语义和专项噪声样本；
- 每次 run 的模型、索引、代码版本与逐题结果。

它用于计算 Recall@K、MRR、nDCG、引用覆盖、引用精度、段落支持、误拒和诱导题误断言。黄金集只在
新增题、修复标注或语料版本变化时更新；`/eval` 页面不会随每次抓取自动“涨分”。线上动态数据看运行页，
发布质量看固定评测，二者不能混为一谈。

## 8. 面试追问

**Q：为什么不直接按 cosine similarity 设一个拒答阈值？**

A：不同问题类型、Embedding 模型和语料密度的分数不可直接比较。系统用混合召回取得候选，再用重排、
证据覆盖和段落支持决定部分答或拒答；阈值由黄金集校准，而不是拍一个相似度数字。

**Q：LLM 是否参与推荐算法？**

A：参与结构化和推荐理由，但不负责最终精选集合。集合由确定性分数、来源权威性、时效、佐证和多样性配额
产生，这样可复现、可测试、成本可控。

**Q：为什么仍保留规则阈值？**

A：早期数据量和用户反馈不足时，规则是可解释基线；关键是阈值必须有黄金集、负实验和回滚条件。未来有
足够标注后可训练分类器或 LTR，但仍要保留一手来源和安全门禁。

**Q：模型换成更强版本就一定更好吗？**

A：不一定。生成模型切换要重跑生成评测与引用审计；Embedding 模型切换会改变向量空间，需要新索引或
版本化重嵌入，不能只换环境变量。生成、Embedding、reranker 三者因此解耦。
