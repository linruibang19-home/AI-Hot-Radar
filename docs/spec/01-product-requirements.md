# 01｜产品需求与页面验收

文档 ID：`AHR-PRD-100`

## 1. 用户与核心场景

| 角色 | 目标 | 主要入口 |
|---|---|---|
| 普通读者 | 快速知道今天最重要的 AI 变化 | 精选、热点、日报 |
| 开发者 | 追踪模型/API/框架更新及影响 | 主题、时间线、RAG |
| 研究者/分析者 | 按时间和实体比较变化，回到原始证据 | 搜索、RAG、报告 |
| 编辑/管理员 | 管理信源、处理失败任务、修正事件和精选 | 管理后台 |

## 2. 信息架构

| 页面 | 路由 | MVP | 核心结果 |
|---|---|---:|---|
| 精选首页 | `/` | 是 | 热点 TOP5 + 日期分组精选流 |
| 全部动态 | `/items` | 是 | 候选池筛选、搜索和分页 |
| 资讯详情 | `/items/{slug}` | 是 | 摘要、证据、原文、关联事件 |
| 热点列表 | `/stories` | 是 | 按热度和时间排序的事件 |
| 事件详情 | `/stories/{slug}` | 是 | 主摘要、多源时间线、来源差异 |
| 主题页 | `/topics/{slug}` | 是 | 主题简介、近期事件和趋势 |
| 日报 | `/reports/daily/{date}` | 是 | 每日主线和代表事件 |
| 周报/月报 | `/reports/{period}/{key}` | M3 | 周/月变化总结 |
| 搜索 | `/search` | 是 | 全文、实体、日期和来源过滤 |
| Radar 问答 | `/radar` | M3 | 时效 RAG、引用与追问 |
| 收藏 | `/favorites` | 是 | MVP localStorage；登录后可同步 |
| 信源后台 | `/admin/sources` | 是 | 状态、延迟、错误、启停 |
| 任务后台 | `/admin/jobs` | 是 | 运行、重试、死信和追踪 |

## 3. 核心功能需求

### AHR-FEAT-101 精选首页

首页必须展示：

- 当前热点 TOP5：热度、独立来源数、最新更新时间；
- 精选时间线：按自然日分组，支持分类筛选；
- 每项显示中文标题、摘要、来源、发布时间、内容类型、精选理由；
- 一手来源徽标与多源事件徽标；
- 首屏 SSR，后续游标分页；
- 内容撤选后不再出现在新请求中，但旧增量客户端能收到 tombstone。

验收：断网/空列表/接口 5xx/慢请求均有明确状态；手机宽度 360px 无横向溢出。

### AHR-FEAT-102 全部动态与搜索

过滤项必须包括：

- 时间范围；
- 公司/组织；
- 模型/产品；
- 主题；
- 内容类型；
- 来源等级和来源名称；
- 语言；
- 是否一手来源、是否已聚合为事件。

关键词搜索结果必须显示命中片段并高亮；排序支持“最新”“相关”“质量”。不得仅依赖向量检索承载精确产品名、版本号和缩写查询。

### AHR-FEAT-103 资讯详情

详情页必须包含：

- 原始标题、中文标题、原始来源、canonical 链接；
- 发布时间、抓取时间、更新时间和语言；
- AI 摘要、关键点、影响对象、标签；
- 可展示时的正文节选；否则仅摘要与原文入口；
- 所属事件、相关报道和来源时间线；
- “AI 生成内容”标识、错误反馈和版权下架入口。

### AHR-FEAT-104 事件 Story

Story 是平台首要阅读单元，必须支持：

- 事件标题、综合摘要、首次/最新发生时间；
- 主来源和支持来源；
- 事件状态：`emerging|developing|confirmed|corrected|closed`；
- 多来源时间线；
- 来源之间的新增信息或冲突说明；
- 独立信源数与热度构成；
- 人工合并、拆分、更换主来源和锁定。

### AHR-FEAT-105 报告

日报从已发布 Story 生成，不直接拼接全部文章。每个报告需保存：

- 报告时间窗与时区；
- 总述、分类章节和代表事件；
- 所用事件版本、Prompt/模型版本；
- 生成状态、人工修订和发布日期；
- Web、Email、RSS 三种渲染输出使用同一报告事实。

### AHR-FEAT-106 Radar RAG

支持问题：

- “最近 7 天 OpenAI 发生了什么？”
- “Claude 和 Gemini 本月分别有哪些重要更新？”
- “过去三个月 MCP 规范如何演变？”
- “这个说法有官方来源吗？”
- “最近值得 Java/Agent 开发者关注的更新有哪些？”

回答必须显示解析后的时间范围、按事件组织的结论、内联引用、来源列表和检索时间。证据不足时必须明确“不足以确认”，禁止无引用补全。

## 4. 评分解释

平台区分两种分数：

- `quality_score`：单篇内容质量，0–100；
- `hot_score`：事件热度，随时间变化，不限定 100。

建议初始公式：

```text
quality_score =
  0.25 * source_authority
+ 0.20 * ai_relevance
+ 0.20 * information_gain
+ 0.15 * technical_depth
+ 0.10 * evidence_quality
+ 0.10 * editorial_value
- spam_penalty

hot_score =
  freshness_decay
* (primary_source_bonus + log1p(independent_source_count) * 20
   + cross_region_bonus + engagement_signal)
```

分数必须保存分项和算法版本，UI 至少解释三个贡献最大的因素。

## 5. 后台人工控制

管理员可以：

- 启停信源、调整频率和优先级；
- 重跑抓取/解析/AI 加工/索引；
- 查看原始响应摘要与失败原因；
- 合并或拆分 Story；
- 修正实体、时间、分类、标题和摘要；
- 精选、撤选、发布、下架；
- 触发日报预览和发送测试邮件。

所有人工动作写入 `audit_log`，记录 before/after、操作者、原因和 request ID。

## 6. MVP 发布门槛

- 完整导入 140 个采集入口，至少 30 个真实源连续运行 7 天，其中至少 20 个达到全文/完整发布说明解析标准；
- 至少 500 条真实内容和 100 个 Story 完成端到端处理；
- 日报连续生成 7 天且可追溯到 Story；
- 关键页面 Lighthouse Performance/Accessibility/SEO 均 ≥ 85；
- RAG 黄金集至少 80 题，通过 `07-quality-security-ops.md` 的门禁；
- 管理员能从 UI 定位任一失败任务并安全重试。
