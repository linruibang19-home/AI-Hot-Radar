# 主题地图关联质量验收（2026-08-13）

关联任务：TASK-M5-015、ADR-0030、Flyway V025。

## 1. 问题不是“没有刷新”，而是刷新了错误的投影

主题地图一直读取随加工更新的 `item_entity`、`item_topic` 和 `content_type`；生产调度会持续
采集并加工新内容，Core API 的主题聚合缓存为分钟级。因此它并非静态页面。

原问题有四层：

1. 厂商页把 `subject`、`object`、`mention` 等价处理，只要正文出现过厂商名就收录；
2. 最新的弱提及按发布时间排在前 40 条，真正核心动态反而被挤走；
3. 前端把本页数组长度写成总数，没有真实分页；
4. 内容重新结构化时只 UPSERT 新主题/实体，没有删除旧模型留下的关系。

## 2. 当前业务链路

```text
全文通过门禁
  -> LLM 结构化输出（schema 校验）
  -> 同一 PostgreSQL 事务替换 item_entity / item_topic
  -> refresh_item_vendor_relations 生成可审计厂商投影
  -> public_item_topic 选择每篇置信度 >= 0.60 的前三主题
  -> Core API 返回真实总数、游标与原因
  -> Next.js 默认展示核心动态，可切换相关/提及
```

`item_entity` 和 `item_topic` 仍保存完整加工事实，RAG 与内部分析没有被删减。公开导航只读取
更严格的投影；Redis 只缓存读取结果，不保存关系事实。

## 3. 克隆生产语料的迁移基线

在不修改本地运行库的前提下，将 2026-08-13 本地数据库克隆到临时 pgvector PostgreSQL，
执行 V025。迁移成功回填 1,955 个已有实体关联内容。

## 4. 前端语义

- 厂商卡片同时显示核心、相关、提及和近 7 天核心数；`total` 不再代表“出现过几次”；
- 厂商详情默认核心动态，并显示“标题直接命中、摘要核心命中、正文主语、对比对象”等原因；
- 主题详情明确提示公开门槛；厂商与主题详情均返回真实总数并支持游标分页；
- 保留既有排版、颜色和时间线，只增加关系标签与分页，没有重做页面。

合并前异常审计另外发现：`pipeline` 新代码会调用由 Core API/Flyway 创建的 V025 函数，原

表或函数。现在本地与生产编排均等待 Core API 健康；这既代表数据库迁移完成，也避免把一次
部署竞态记成内容加工失败。

## 6. 剩余风险与下一步

确定性首版规则比原“任意提及”精确，但还不能替代人工标注。下一张任务不应继续凭观感调阈值，
而应先建立可复现的分层黄金集。该工程阶段已由 TASK-M5-016 第一阶段完成，实测快照与边界见
[`topic-map-golden-set-20260813.md`](topic-map-golden-set-20260813.md)。当前 1,995 条候选仍待人工复核；
完成标注、分歧裁决与基线冻结后，才计算 `primary precision`、厂商核心召回和 topic
precision/recall，并据此决定是否需要 classifier v2。
