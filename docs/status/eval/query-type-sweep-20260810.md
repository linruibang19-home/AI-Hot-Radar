# query_type 扫描：这个标签几乎不改变检索结果

逐题数据：[query-type-sweep-20260810.json](query-type-sweep-20260810.json)
命令：`rag-eval --variant query-type-sweep`（78 道可答题，无生成调用）

## 起因

B16 留下一个悬案：LLM planner 的分类准确率比正则高 **24 个点**（0.6667 → 0.9067），
检索指标却不升反降。两种解释——收益没有传导，或者判据本身错了。
本轮强制给每道题套上六种 `query_type` 各跑一遍，读它们各自的 Recall。

## 结果

| | |
|---|---:|
| 可答题 | 78 |
| **六种类型 Recall@10 完全相同的题** | **70（89.7%）** |
| 没有唯一最优类型的题 | 77 |
| 平均极差（最好−最差 Recall@10） | **0.0436** |

**九成的题，你把 `query_type` 换成六种里的任何一种，召回一模一样。**

唯一那道"有最优"的题（RAG-GOLD-048）在 Recall@10 上同样是平的，
只是在 @20 上被打破了平局——连它也不是真正的差异。

> 汇总里的 `category_matches_best` 与 `planner_matches_best` 都是 0.0，
> **但这两个数没有意义**：分母只有 1 道题。不要引用它们。

## 结论：B16 的答案是「两者都不是」

不是"收益没传导"，也不只是"判据选错"，而是更基本的一件事：
**被标注的这个东西，对被测量的那个结果几乎没有作用。**

`query_type` 通过三条路径影响管线——时间窗过滤、`source_fit` 取哪一行、
`temporal_fit` 开不开。扫描说明在本语料上，这三条加起来的可测影响是 **0.0436 的平均极差**，
而 B14 实测的跨轮噪声底是 **±0.02**。信号只有噪声的两倍，且集中在 10% 的题上。

### 因此

1. **`AHR-QSO-700` §8 的 planner accuracy 门禁，衡量的是一个不驱动结果的标签。**
   不建议把 `category` 灌进 `expected_query_type` —— 那会把一条测不出东西的门禁固化。
   这条门禁的状态应记为「已量化：在本语料上不可操作」，而不是「未达标」。
2. **LLM planner 确定保持关闭。** 它每问多花一次模型往返，买到的是一个
   九成情况下不改变输出的标签。
3. **不要再在 planner 分类上花力气。** 这轮扫描本身就是这个结论的成本。

## 这一轮没有测的（必须写明）

Planner 做两件事：**分类**和**解析时间**。本扫描只覆盖前者——
六个变体共用正则 planner 解析出的时间窗，只在 `freshness_required` 这一项上分叉。

**时间解析错误是另一类失败，本轮完全没有覆盖。** 而它更可能是真问题：
「现在有什么信源」曾因为不认识「现在」而完全不加时间窗，
那一类错误改变的是**检索哪些天**，不是排序里的一个加权项。

下一步若还要动 planner，应该测的是时间窗而不是分类——
可以用同样的手法：强制若干候选时间窗，看哪个 Recall 最高。
