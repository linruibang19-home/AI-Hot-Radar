## 这组数字推翻了一个假设

我此前判断「B5 父块 / B6 折叠是打磨项，检索是大头」——**数据说反了**。

**本地计算全部加起来不到 1%**：三路检索 74ms、融合 1ms、选证 2ms、父块展开 5ms。
Postgres 这一侧根本不是瓶颈，**99% 的时间花在三次外部 API 往返上**
（嵌入 17.5% + 重排 28.4% + 生成 53.3%）。

直接后果：

- **融合权重网格调优基本不花延迟**。加宽候选集、多算几路融合的成本在毫秒量级，
  之前担心的「调优会不会太慢」不成立。真正的成本在重排的候选数上，
  而 B4 已经量过——40 优于 100，且快 3.2 倍。
- **想压延迟只有三个地方可动**，且都在网络侧：
  嵌入可缓存（同一问题重复提问）、重排与生成可并行化的部分很有限（后者依赖前者）、
  或换更快的模型。**优化本地 SQL 一分钟也省不下来。**
- `parent` 只花 5ms 证明 ADR-0016「父块由查询派生、不落表」是对的：
  物化一张父块表要维护一条同步路径，换来的是 5 毫秒。

## token 成本

| | |
|---|---:|
| prompt p50 | 13 646 |
| prompt p95 | 21 654 |
| completion p50 | 557 |
| 24 题合计 prompt | 349 590 |
| 24 题合计 completion | 15 376 |

prompt p95 达到 21.6k token，说明**父块展开确实在起作用**——十条证据每条最多
6000 字符。这也是生成阶段耗时的直接来源：p95 的 8.7s 对应的正是最长的那些 prompt。

如果要压生成延迟，减少证据条数或收紧 `PARENT_BUDGET_TOKENS` 是最直接的杠杆，
但两者都会动 groundedness（当前 0.8330），**必须连着生成侧评测一起跑**，不能只看延迟。

## 已知局限

- 24 个样本的 p95 是「第 23 个值」，样本量偏小。用最近排名而非插值正是为此——
  插值出来的 p95 是没有任何一次请求真正经历过的数字。
- 单机、单并发测得。并发下嵌入与重排会排队，真实 p95 只会更高。
- 未含 web → ai-service 的一跳与页面渲染，只量了 `answer_question` 本身。
