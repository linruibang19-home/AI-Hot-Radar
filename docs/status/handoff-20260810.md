## 1. 项目是什么

**AI Hot Radar** —— 面向 AI 行业的时效性情报平台。统一采集 140 个公开信源，
清洗、去重、结构化、事件聚合、精选评分，产出网站与日报，
并提供**每句话都能点回原文**的 RAG 问答。

这是一个应届生简历项目，范围是全量的（不是 demo）。

### 它想证明的一件事

RAG 很容易做成一个「看起来会答」的黑盒。这个项目取向相反：
**每个检索决策都要能被追问，每个结论都要有可点开的出处，量出来不好看的结果也留在页面上。**

站内 `/eval` 页公开了全部评测的逐题数据，其中**三轮是负结果**、
**一条写下来的假设被下一轮证伪**。这是项目的核心叙事，不要在优化时把它抹掉。

## 5. RAG 管线（项目最核心的部分）

```
question
  ① Planner（regex）        意图分类 + 时间词 → 绝对区间，冻结成 RetrievalPlan
  ①.5 追问改写             有 conversation_id 时把「它呢」改写成独立问题
  ①.6 元问题路由           「本站有哪些信源」走数据库计数，不走检索
  ② 多路召回               dense（bge-m3, 60）+ sparse（tsvector GIN, 40）
                           时间窗作为过滤器；另加 temporal / subject 限定 entity_temporal
  ③ RRF 融合 + §6 boost    只吃排名不吃分数；boost 施加在归一化分数上
  ④ 交叉编码器重排          bge-reranker-v2-m3，40 候选
  ⑤ directness / source_fit / temporal_fit
  ⑥ 证据选择               每篇 ≤2 段 → 每信源 ≤3 条 → Story 折叠 → 父块阶梯
  ⑦ 生成                   DeepSeek，SSE token 级流式
  ⑧ 引用绑定               **服务端反查真实段落**，模型编的编号被删除
  ⑨ 支持度门控             交叉编码器给（论断 × 段落）打分，低于 0.30 的引用被剥离
  ⑩ 四条不变量校验          → rag_query + rag_citation 落库
```

### 模块位置

`apps/ai-service/src/ahr/rag/`：`planner.py` `conversation.py` `meta.py`
`retrieval.py` `fusion.py` `rerank.py` `temporal.py` `dimensions.py` `parent.py`
`folding.py` `answer.py` `support.py` `incremental.py` `service.py`（编排，约 1300 行）
`api.py` `cache.py` `suggest.py` `llm_planner.py`（默认关闭）`trace.py` `eval/`

### 已经被实测**证伪**的想法（不要重做）

| 想法 | 实测结果 |
|---|---|
| 稠密 + 稀疏并集 | **比纯稠密还差**（B2）；要用 RRF |
| 独立时间召回通道 | 只贡献 +0.004 Recall；有用的是把时间窗当**过滤器** |
| 重排 100 候选比 40 好 | 40 在四项指标上**全部略高**，延迟 4378ms → 1376ms |
| 扫融合权重能提升 | 42 组，接上重排后差距塌缩到 0.0004 → **结论：不改** |
| CJK 分词修好能提升 RAG | 端到端 **±0.0000**（稠密通道一直在兜底）；但站内搜索快 10–32× |
| IDF + 实体加权 | 无可测的端到端效果（B15，在 ±0.02 噪声内）|
| LLM planner 更准就更好 | 分类准确率 +24pt，检索反而略降（B16）|
| planner 的 query_type 很重要 | **78 题里 70 题六种类型 Recall 完全相同**；这个标签几乎不驱动结果 |

### 必须记住的方法论结论

- **跨天的 B 轮对比带 ±0.02 噪声**：`snapshot_window` 钉住了*条目*，
  但没钉住 HNSW *索引*，而它是近似的、会随向量插入变化（B14 实测）。
- **拿一个数去做门控，它就不再是测量**（ADR-0020 / ADR-0021 是同一陷阱的两面）。
- **评测跑过 ≠ 已上线**：B7 评测跑过、报告写过、状态标了完成，却从未接进
  `service.py`。同一形状的错误在这个项目里发生过两次。

### 反复踩过的坑（排查先看这里）

1. **缓存**：改了生成后处理但没 bump `ANSWER_PIPELINE_VERSION`，门禁自带一小时的洞
2. **时区**：全站曾整体渲染 UTC。时间窗解析踩同一个坑会产生**看起来完全正常的错答案**
3. **指针状态没跟上**：采集侧未重开 `enrichment_state`，导致有正文却检索不到
4. **评测跑过 ≠ 已上线**（发生过两次）
5. **psycopg 会扫描整个 SQL 字符串找占位符**，SQL 注释里写 `%` 会 500
6. **Windows/MSYS 路径改写**：`/tmp/x.json` 会被改成 Windows 路径，
   用 `MSYS_NO_PATHCONV=1` + `-w /app` + 相对文件名
7. **限流会打到自己**：本地浏览器和 host 上的 curl 共用同一个网关 IP

## 10. 给接手者的三条建议

1. **先跑一遍再说话。** 这个项目的文档里有陈旧数字（README 的语料快照就是），
   引用任何指标前自己查一次库或跑一次评测。

2. **负结果是资产，不要"优化"掉。** B2、B8、B13、B15、B16 和 query-type 扫描
   都是负结果，它们是这个项目最有说服力的部分。要动它们，先读完对应的报告。

3. **前端不是次要的。** 这个项目栽过一次：多轮对话后端跑通了四次，
   用户四次反馈「没有多轮对话」——因为页面结构里没有第二轮能待的位置。
   **一个跑通但看不见的功能，对使用的人来说与不存在无法区分。**
