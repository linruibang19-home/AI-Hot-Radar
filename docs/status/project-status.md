### 三条需要立刻记住的

**① `support_supported` 曾是唯一在恶化的指标（0.8986 → 0.8952 → 0.9078 → 0.8602），
已于 2026-08-09 由支持度门控处理——但回归尚未跑。**
门控前线上 729 条已打分引用有 **11.11%** 低于阈值：每 9 条展示给读者的来源就有 1 条，
打分器判定它不支持所配论断。产品的核心主张是「每条事实都能核对来源」，
这一条是那个主张的直接反面，而系统**已经知道**（分数算了、徽章也显示了），
仍然把它当作来源呈现。

现在低分引用在下发前被移除并重编号，剥离条数写进 `limitations` 与
`metrics.support_dropped`。**只移除，不升级为拒答**——理由与边界见
[m4-rag-implementation.md §8](../design/m4-rag-implementation.md)。

**90 题回归已跑**（`GEN-20260808T180053Z`，完整报告
[m4-rag-eval-GEN-20260809.md](eval/m4-rag-eval-GEN-20260809.md)）：

| 指标 | 门控前 | 门控后 | Δ |
|---|---:|---:|---:|
| 支持度达标率 | 0.8602 | **0.9596** | **+0.0994** |
| 支持度均值 | 0.8090 | **0.8758** | +0.0668 |
| **`abstention` 类支持度** | 0.6158 | **0.9670** | **+0.3512** |
| **误拒率** | 0.0000 | **0.0000** | **±0** |
| **断言假前提** | 0.0000 | **0.0000** | **±0** |
| citation coverage | 0.9069 | 0.8522 | −0.0547 |
| story coverage | 0.7532 | 0.7282 | −0.0250 |

**收益最大的是设计时判断风险最高的那一类。** `abstention` +35.1pt——
门控前那一类堆着一批挂在否认句上的弱引用（引用精度只有 0.2000），
而 3.29 早就实测过否认句难被蕴含打分认可。移除它们之后两项接近翻倍，
**且一次误拒都没多**——「只移除、永不清空引用列表」这条边界被数据证实是必要的。

覆盖面下降 2.5–5.5pt 是**机械后果**：引用变少，带引用的句子和被引事件自然变少。
这是用覆盖面换可信度的显式交易。`must_contain` 掉的那 1 题（RAG-GOLD-016）
**引用数 3→3 未变**，门控没碰它，是模型两轮之间的抖动。

**打分口径已并列量出，同义反复被实证**（`GEN-20260809T041225Z`）：

| 口径 | 均值 | 达标率 |
|---|---:|---:|
| 父块级（**门控自己的口径**）| 0.9065 | **1.0000** |
| 段落级（门控**没有**强制的量）| 0.8429 | **0.9371** |

**父块级 1.0000 恰恰证明它不能当判据**——门控只放行父块级达标的引用，
这个数只能报告门控自己放行了什么。**拿一个数去做门控，它就不再是测量**，
与 ADR-0020 记的 abstention 是同一个陷阱的两面。
段落级是还能失败的那个，ADR-0021 因此把判据定在它上面。

两个口径现在并列输出（`support_*` / `support_as_read_*`），
**引用任何一个数时必须注明取的是哪个**。

**②bis planner accuracy 的度量已经建好，缺的只剩标注。**
`rag-eval --variant planner` 已落地：`expected_query_type` / `expected_time` /
`expected_entities` 三个可选字段进黄金集，加载时硬校验；
**不连数据库、不调供应商**（Planner 是问句与 `asked_at` 的纯函数），因此免费、可进 CI、断网可跑。
准确率与 `annotation_coverage` **永远并排输出**，标注数为 0 时命令以非零码退出——
把「不可判定」显示成「看起来没问题」是更糟的那种状态。
标注方法见 [data/golden/README.md](../../data/golden/README.md)，
**必须按问句该被理解成什么来标，不能拿 §3 的默认值反推**，否则是让实现和自己对答案。

**② `abstention accuracy` 的定义被换过，但没有 ADR。**
3.23 ① 证明旧指标 `refusal_rate_on_unanswerable` 测的是表面形态（有引用的否认被判成没拒答），
换成 `presupposition_asserted_rate`（**0/12**）是对的。但规格字面没改、没有 ADR，
于是「这条门禁过没过」取决于读者选哪个指标——**0.0000 和 1.0000 都能从库里查出来**。
在 ADR 落地前，它的状态是「定义未定」，不是「通过」。

**③ 用旧数字对这张表会带反结论。** 08-04 的 GEN 会让 completeness 看着差 0.207
（实为 0.043）、abstention 看着是能力不达标（实为指标错），
并且**完全漏掉唯一在恶化的那一条**。门禁对照必须绑定 `eval_run_id`。

### 另有：评测与线上仍不是同一条路径

`TEMPORAL_SQL` 通道 `temporal_search()` 有实现、评测默认启用、

## 3.5 事件聚类（M3）

### 特征与权重

`docs/spec/03 §8` 规定的 6 个特征里有 2 个当前拿不到，**显式处理而不是当成 0**：

| 特征 | 规格权重 | 现状 |
|---|---:|---|
| `title_and_summary_embedding` | 0.35 | Embedding 属 M4，暂用**词法标题相似度**代替（中文按 bigram、英文按词并拆分复合词） |
| `entity_overlap` | 0.25 | ✅ 已实现 |
| `action_object_match` | 0.15 | ✅ 已实现（共享实体覆盖率 × 内容类型是否同类） |
| `url_or_quote_link` | 0.10 | ❌ 采集未抽取外链，**权重重新归一化**而非计 0 |
| `time_proximity` | 0.10 | ✅ 72 小时窗口内线性衰减 |
| `topic_overlap` | 0.05 | ✅ 但 39% 的条目没有主题，此时**丢弃该项并重新归一化** |

一个常数 0 的特征会把所有配对的分数等量拉低，让阈值失去意义——所以缺失特征是
剔除后归一化，而不是记 0。

### 硬规则（无论分数多高都不合并）

- **版本冲突**：两边都带版本号且不相交 → 不合并。`DeepSeek V3` 与 `DeepSeek V4-Flash`
  共享公司、产品线和绝大部分措辞，合并是**事实错误**而不是排序瑕疵。
- **同一信源**：一个信源的两条内容永远不合并。Story 的意义是统计**独立**佐证，
  同源合并既不能提升排序，又实测制造了错误分组（见下）。
- **人工锁定**：`locked_by_editor` 的 Story 及其条目完全排除在重聚类之外。

### 阈值是实测标定的，不是拍脑袋定的

初版阈值定在 0.62，结果**真实语料 508 条产生 0 次合并**——因为全语料最高分只有
0.571，阈值高于所有真实配对。把全部 40761 个配对打分后才发现两个真问题：

1. **Jaccard 用错了**。changelog 条目挂 5 个实体、媒体报道挂 10 个，两边在事件真正
   涉及的 2 个实体上一致——Jaccard 只有 0.15，和"完全无关"没有区别，因为并集被各自
   附带提及的实体淹没。改用**重叠系数**（交集 / 较小集合）后同一对读作 0.40。
   语料里每一个真实事件都长这样。

2. **同源高分是最大的假阳性来源**。分数最高的配对是 OpenAI status 页面的**四次不同故障**
   （措辞高度雷同）和 Together AI 的**六条标题全被抽成 "Read More"** 的条目。
   两者都是同一家的固定句式导致的高相似度。

修完后阈值标定为 **0.52**（复核带 0.42–0.52）。首次得到 7 个多篇事件，随语料增长现为 12 个。

### 人工抽检结果（AHR-KPI-003 要求纯度 ≥ 0.85）

7 个多篇报道的事件**逐个人工核对，纯度 7/7 = 1.00**：

| 事件 | 篇数 | 独立信源 | 核对 |
|---|---:|---:|---|
| Anthropic Claude 测试入侵真实公司 | 4 | 4（量子位、Ars、The Verge、Simon Willison） | ✅ 同一事件 |
| 谷歌地球 AI 深度伪造工具下架 | 3 | 3（The Verge、TechCrunch、THE DECODER） | ✅ 同一事件 |
| Anthropic 发布 Claude Opus 5 | 2 | 2（官方 + Latent Space） | ✅ 同一事件 |
| OpenAI SDK 支持 gpt-5.6-sol | 3 | 1 | ✅ 同一次协同发布，且正确记为 1 家独立信源 |
| Google Gen AI JS/Python SDK 2.13.0 | 2 | 1 | ✅ 同版本协同发布 |
| OpenAI Agents Python/JS（两组） | 2×2 | 1 | ✅ 同版本协同发布 |

注意后三类：同一家公司的多个 SDK 仓库会聚成一个事件，但 `independent_source_count`
按**组织**去重后仍是 1——所以协同发布**不会伪造出"多家信源佐证"**。

**局限**：抽检样本只有 7 个多篇事件，达不到验收要求的「100 个 Story 人工抽检」规模。
其余 550 余个是单条事件，纯度平凡为 1 但不检验算法。要凑够样本需要更长的运行时间或
更多媒体类信源。

### 聚类结果反过来接入了精选与报告

聚类跑通后发现一个更严重的编辑缺陷：**被四家和三家独立媒体分别报道的两个事件
（Anthropic Claude 测试入侵真实公司、谷歌下架卫星图深度伪造工具），入选精选的次数是 0**，
而 87 条单信源的 Release Note 全部入选。

原因是精选算法里根本没有"佐证"这一项：媒体报道属 secondary/expert 档，
在与 primary 档 GitHub Release 的比较中每一项都吃亏。这正是 M3 要解决的问题，
但只做聚类而不接回排序，聚类结果就只是个孤立的展示页。

因此新增 `corroboration` 因子（权重 0.15，`select-v2`）：

- **对数饱和**：第二家信源是"这件事重要"的强证据，第五家增益很小；
- **单信源不扣分**（该项记 0）：大多数发布本来就只公告一次，这个因子是
  **抬高被佐证的事件**，不是打压其余内容。

重跑后：Anthropic 事件 4/4 条入选，谷歌事件 2/3 条入选。

报告侧同步改为 **按事件收敛**：同一事件的多篇报道在报告里只出现一次
（取分数最高的那篇），并标注「另有 N 家信源报道」。周报实测收敛掉 4 条重复条目。

## 3.6 全链路自动化（本次补齐的最大缺口）

采集从 M1 起就一直在跑，但**采集之后的每一个环节都只在手敲 CLI 时才执行**。
后果是网站一直在收内容、却不再展示：8 月 3 日实测有 141 条卡在 `PENDING`，
而精选 / 热点 / 事件聚合 / 日报全部停在最后一次手动运行的时刻。用户看到的
「今天不更新资讯」就是这个原因，不是采集坏了。

新增 `pipeline` 服务（`ahr.cli pipeline`），按依赖顺序跑完采集之后的全部环节：

| 顺序 | 环节 | 依赖上一步的什么 |
|---|---|---|
| 1 | `process` | 原始行 → 中文标题、摘要、实体、主题、质量分 |
| 2 | `cluster` + `heat` | 已结构化的条目 → Story、独立信源数、热度 |
| 3 | `select` | **Story 的独立信源数**（`select-v2` 的佐证因子要读它） |
| 4 | `reasons` | selection_record 行 |
| 5 | `report` | 当期精选 |

**聚类必须排在精选之前**：`select-v2` 读 `story.independent_source_count`，
顺序反了会把所有条目算成"无佐证"，等于悄悄回退 M3 的修复。已有测试锁定这个顺序。

成本与并发控制：

- **Postgres advisory lock**：一趟实测耗时 387 秒，超过间隔时两趟会重叠，
  对同一批条目重复付费。抢不到锁的那趟直接跳过。
- **报告按需重算**：与"最新一条精选的时间"比较，没有新素材就不重新生成——
  固定间隔会让平静的一小时也花钱重写一份一模一样的摘要。
- **LLM 不可用时降级而非停摆**：聚类、精选、热度不需要模型，照常运行。

## 3.7 M4 RAG —— 检索底座（进行中）

### 选型：硅基流动 + bge-m3（1024 维）

**打过真实 API 才定的**，不是照抄教程：bge-m3 与 Qwen3-Embedding 都是 1024 维、都支持批量。
选 bge-m3 是因为本语料**真的是双语**（中文标题摘要 + 以英文为主的正文），
需要多语言检索模型，而不是"能凑合处理中文的英文模型"。

`V012` 把 `vector(1536)` 收窄为 `vector(1024)`，并且**已有向量时直接报错拒绝执行**——
pgvector 无法比较不同维度的向量，混进去不会报错，只会让所有查询静默失效。
索引用 **HNSW 而非 IVFFlat**：IVFFlat 要等数据到位才能建、随语料增长要重调参数，
而这里每小时都在变；HNSW 是增量的，pipeline 刚写入的分块立刻可检索。

### 写检索代码之前先量了分块，发现三个真问题

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 过短分块（<50 token）| 849（22%）| **399（9.6%）** |
| 过长分块（>1200 token）| 362 | **0** |
| 超出嵌入截断（>6000 字符）| 302 | **0** |
| 最大分块 | 24 979 token | **1 200** |
| 中位数 | 147 | **371** |

1. **302 个分块的向量是残缺的**。最大的一个 24 979 token（≈10 万字符），
   而嵌入客户端在 6000 字符处截断——**94% 的内容对检索不可见**。
   原代码对超大块"整块保留"（§6 禁止跨结构切分），这对结构是对的、对检索是错的：
   **一个无法被完整嵌入的分块不是分块，是索引里的一个洞。**

2. **849 个分块是单行 changelog**（如 "- Authenticate skill registry downloads" 9 token）。
   原来只有**末尾**分块会合并，对散文够用，对本语料主力的发布说明完全不够。

3. **heading 路径累积错误（既有缺陷）**。`heading_path[:level-1]` 把**位置当成了层级**：
   多数正文从 `##` 开始（`#` 是标题），于是每个同级小节都被记成前一节的子节，
   路径沿文档单调变长，出现 `Highlights › Changelog › @mastra/next@0.2.4 › Patch Changes`
   这种并不存在的嵌套。改成 **(层级, 标题) 栈**后同级小节才真正是同级。

### 上下文增强嵌入（Anthropic Contextual Retrieval 思路）

短分块单独看没有意义，但**加上它属于哪个发布、谁发的、什么时候、哪一节**就有了。
所以嵌入的输入是 `标题 · 来源 · 日期 · heading 路径` + 正文。

**关键约束：前缀只加在嵌入输入上，绝不写进 `body_text`。**
`rag_citation` 要把分块正文作为证据引用，AHR-SPEC-000 §7 要求引用可回原文核对，
我们合成的文字不在原文里，不能冒充原文。

### 实测检索效果（4135 分块全部向量化）

```
"llama.cpp 最近修复了哪些 bug？"      → 0.726  三条全部命中 b10223 修复版
"Anthropic 的 Claude 安全测试问题？"  → 0.732  三条命中同一事件的三家独立媒体
"vLLM 的贡献者名单"                   → 命中 23/28 token 的碎片（上下文前缀生效的证据）
```

### 这轮实测暴露的、下一步必须处理的三件事

1. **同文档分块霸榜**：llama.cpp 一个版本占满 top-3 → 需要按文档做多样性约束
2. **同事件多家报道重复**：Anthropic 事件三家媒体各占一位 → 用 M3 的 Story 去重，只占一个引用位
3. **精确词检索**：问 "MXFP4" 召回了 "NVFP4" → **稀疏检索（BM25/tsvector）是刚需**，
   这正是混合检索存在的理由

### 语料结构实测（父块设计的输入，2026-08-03）

写父块代码之前先量了语料，结论直接否决了「照抄固定双层」：

| 指标 | 实测 |
|---|---:|
| 文档数 / 分块数 | 959 / 4140（均 4.32 块/篇）|
| **整篇 ≤ 2000 token 的文档** | **69.3%** |
| 文档 token p50 / p90 / max | 1034 / 5139 / 31147 |
| 顶层小节数，多块小节占比 | 1435，45.8% |
| 小节 token p50 / p90 | 483 / **3519** |
| **`heading_path` 为空的分块** | **1386（33.5%）** |

三个数字各否决一种固定方案：69.3% 说明多数文档不需要「小节」这层抽象；
小节 p90 = 3519 说明"命中就提升整节"会撑爆预算；33.5% 无 heading 说明
固定的「小节 = 父块」对三分之一的分块**根本没有定义**。
因此父块改为**三级自适应阶梯**，且**由查询派生不落表**（ADR-0016）。

### B5 父块阶梯 + B6 Story 折叠（2026-08-04）

**B6 折叠实测**，用的正是冒烟测试当初发现问题的那道题：

```
问：Anthropic 那次测试一共引发了几起真实事故？

```

四家媒体报道同一次披露，原本占掉三个证据位；折叠后只占一位主来源 + 两位佐证，
腾出的位置给了别的证据。**独立性按信源计，不按文章计** ——
同一家媒体就同一事件写两篇，不构成两次独立确认。

证据选择是两道而不是一道：**先按文档限流，再按事件折叠**。
两种冗余不同源，谁也替代不了谁 —— llama.cpp 单篇霸榜是**一篇文档的多个段落**，
Anthropic 事件是**四篇不同文档**，文档级限流拦不住后者。

**B5 阶梯在全语料上的实际分布**（`tier_distribution`，预算 2000 token）：

| 层级 | 分块占比 |
|---|---:|
| ① 整篇 | 32.4% |
| ② 顶层小节 | 10.1% |
| ③ 命中块 ±1 | **57.5%** |

和 ADR-0016 记的「69.3% 文档整篇装得下」**不矛盾，是分母不同**：
那是按文档算，这是按分块算，而长文档贡献的分块多。
检索返回的是分块，所以后者才是实际生效的口径 —— 这条已回填进 ADR。

**顺带修掉一个我自己引入的缺陷**：阶梯按 2000 token 判定"整篇装得下"，
随后 `MAX_PARENT_CHARS = 4000` 又把文本截到三分之二 ——
**等于刚选出的第 ① 级被悄悄作废**。现在字符上限由 token 预算换算得出，两者不再打架。

### B8 融合权重网格调优：负结果，但是有价值的那种（2026-08-04）

完整报告 [m4-rag-eval-B8.md](eval/m4-rag-eval-B8.md)。`AHR-RAG-400` §5 要求权重必须用评测集调优。

**结论：42 组网格跑完，保持原权重不变。**

网格确实找到了更好的**融合序**（`sparse=0.2, temporal=0.4`，MRR 0.7362 vs 0.6770，
**+5.9 点**），接上重排再测，两组权重端到端：

| | R@10 | R@20 | MRR | nDCG@10 |
|---|---:|---:|---:|---:|
| 现行 `sparse=0.6, temporal=0.15` | **0.8547** | **0.8923** | **0.8645** | **0.8129** |
| 网格最优 `sparse=0.2, temporal=0.4` | 0.8530 | 0.8838 | 0.8641 | 0.8101 |

**差异从 5.9 个点塌缩到 0.0004**，四个类别逐位完全相同。重排器把两个不同的输入序
收敛到了同一个输出序 —— 这正是 B4 量到的「重排主导排序」，只是从反方向再验证一次。

**这一轮最值钱的一条**：融合前指标是个**会骗人的优化目标**。
网格给出的 +5.9 是真实测量，但它测的是一个马上会被覆盖的中间态。
只跑网格就改权重，会得到一个自信的错误结论。

网格的真正价值是确认现行值**安全**：全网格 R@40 只波动 0.0043（判据指标已饱和），
而 `sparse ≥ 0.8` 才开始伤 R@20（1.2 时掉到 0.8124）。0.6 在平台区中间，不在悬崖边。

三个权重同乘一个常数不改变排序（RRF 对权重是线性的），所以 dense 固定为 1.0
就已经覆盖全部配置，二维网格即可，不必扫三维。

### SSE 流式下发：流的是进度，不是模型 token（2026-08-04）

`AHR-API-500` §4 要求 SSE。`POST /rag/ask/stream` 已实现，并且**刻意不转发模型 token**。

原因是一条硬约束：答案要等生成**结束之后**才安全。`bind_citations` 会删掉模型
编造的 `[n]` 标号并按阅读顺序重编号，`check_invariants` 可能把一段完整流畅的回答
直接判成拒答。转发原始 token 等于先把编造的来源显示出来、再把读者已经读过的段落收回去
—— 这正是 §4「服务端在下发前解析引用」要防的事。

所以流里跑的是**阶段进度**，验证过的答案作为最后一个事件整体到达。实测：

```
[+ 1s] plan      query_type=explainer
[+ 3s] embed     1971ms
[+ 3s] dense     52ms  found=60      sparse 30ms found=30
[+ 3s] fuse      1ms   found=84
[+ 5s] rerank    2453ms
[+ 5s] select    2ms   evidence=10  stories_folded=20
[+ 6s] parent    5ms   {document:2, section:3, neighbours:5}
[+ 6s] generate  开始
[+49s] answer    「使用 MXFP4 量化的是 Kimi K3」
```

那次生成花了 **43 秒**（p50 是 5.7s），恰好说明这个功能的价值：
没有进度反馈的 49 秒，和页面卡死没有区别。

前端把 9 个阶段收敛成 4 步展示（理解问题 / 检索证据 / 重排候选 / 生成回答）——
`dense`+`sparse`+`fuse` 三个加起来 67 毫秒，逐个列出来的进度条是在**谎报时间去向**。

> **token 级流式仍未做**，且这次把原因写清楚了：需要模型先输出 claims 再输出正文，
> 才能增量绑定引用。那是**改 prompt 契约**、要重跑生成侧评测的改动，不是呈现层的调整。

## 3.13 AI 问答界面重做：把已有的机器暴露出来（2026-08-04）

问答页此前只有标题、输入框、三个示例和一段说明。**背后跑着九个阶段的检索链路，
界面上一样也看不到。** 这一轮不是加装饰，是把系统**已经算出来但没告诉读者**的东西接出来。

### ① 引用编号从死文本变成控件（最重要的一条）

`[1]` 此前是段落里的**纯文本**。这个产品的核心主张是「每条事实都能核对来源」，
而读者只能靠肉眼把 `[1]` 和下面的列表对上——**保证存在于服务端，却没有一条路径让读者摸到它。**

现在 `[n]` 渲染成可点击控件：悬停显示标题与信源，点击滚动并高亮对应来源卡片。
服务端本来就保证每个编号都能解析到真实段落（`bind_citations` 会删掉解析不到的），
缺的只是把这个保证变成可达的。

### ② 来源卡片展示排序器用过的信号

| 新增 | 来自 | 为什么读者需要 |
|---|---|---|
| 信源等级徽章（一手/媒体/专家/社区）| `source.source_tier` | §6 就是按它加权的，判断可信度的读者应该拿到排序器拿到的东西 |
| **「N 家独立信源」徽章** | M3 的 `story.independent_source_count` | 这是 M3 全部工作的意义所在，此前在答案里完全不可见 |
| 站内详情页链接 | `citation.itemId` | 详情页有中文摘要、实体、事件时间线；原文链接一步之外，未被替代（ADR-009）|

实测旗舰题：Anthropic 那次事件的 3 条引用**全部标注「4 家独立信源」并链到同一个事件页**。

### ③ 检索计划可见

显示解析出的**问题类型**与**绝对时间区间**（不只是「最近 7 天」，而是具体到日期）。
「最近」被解析成一个真实区间是这个系统区别于通用聊天框的地方，
而读者看到窗口取错了周，可以去改问题，而不是断定系统不行。

### ④ 拒答给出路

拒答此前是死胡同：「没有足够证据回答这个问题」。**而系统清楚地知道自己读了什么。**
现在会列出「检索到但不足以支撑回答的内容」（去重到文档级，最多 5 条，可点进详情页）。

## 3.15 问答体验的四个缺陷:同一个根因(2026-08-04)

## 3.8 全部 AI 动态的分页缺陷（2026-08-04 修复）

三个缺陷叠在一起，表现成同一句话：「加载更多点了没反应，旧日期一直出不来」。

| # | 缺陷 | 为什么没被发现 |
|---|---|---|
| 1 | 「加载更多」是 `<Link href="?cursor=…">`，**替换**列表而非追加 | 8-3 发了 192 条，每页 25 条，所以第 1 页和第 2 页渲染出来**肉眼完全相同** |
| 2 | `<details>` 是非受控元素：折叠后浏览器移除 `open`，React 仍认为是 `true`，**再也不会加回去** | 追加的内容落进一个永远打不开的折叠区 |
| 3 | **分页按条数，页面按天组织** | 8-3 的 192 条要点 **8 次**才能翻到 8-2，每次点击看起来都像没反应 |

## 3.9 数据库口令与连接方式（2026-08-04）

改口令时撞到两个真坑，都已在配置里根除：

1. **`#` 是 URL 的片段分隔符。** `postgresql://user:pw#@host/db` 会把口令截断，
   表现成"密码错误"。`DATABASE_URL` 改为 psycopg 的 keyword/value 连接串
   （`host=… password=…`），没有需要转义的字符。
2. **`env_file:` 不参与 `${VAR}` 插值。** Compose 只从 compose 文件旁边的 `.env`
   取插值变量，所以根目录 `.env` 里的口令**进得了容器、进不了插值**，
   所有服务静默退回默认值 `change-me`。现由 `ahr/config.py` 从 `POSTGRES_*` 拼装，
   core-api 与 postgres 也改为通过 `env_file` 取值。

根目录 `.env` 里那条会过期的 `DATABASE_URL` 已删除——口令一改它就失效，
而 `POSTGRES_*` 仍然正确，这正是最难排查的那种不一致。

Navicat 连接：`localhost:5432`，**初始数据库与用户名都填 `ai_hot_radar`**
（本项目没有创建 `postgres` 超级用户，用它连必然失败）。

## 3.9.1 Navicat 连不上：宿主机 5432 有两个 PostgreSQL（2026-08-04）

口令改对了、容器内连得上、宿主机连不上。查 `netstat` 发现 **5432 上有两个进程监听**：
Docker 的端口代理，以及本机安装的 `postgresql-x64-16` 服务。
Navicat 连 `localhost:5432` 时被路由到**本机那个 PostgreSQL**，
而 PostgreSQL 出于安全**不会区分「角色不存在」和「口令错误」**，
两者都报 `password authentication failed`——所以看起来像口令填错了。

容器端口映射改为 **`${POSTGRES_HOST_PORT:-5433}:5432`**，不去停用户本机的服务。
容器之间仍走 `postgres:5432`，不受影响。

**Navicat 连接参数：主机 `localhost`，端口 `5433`，初始数据库与用户名均为 `ai_hot_radar`。**

## 3.9.2 日报改为 21:00 结算（2026-08-04）

pipeline 每 15 分钟跑一次，此前**只要有新精选就重写当天日报**——
中午的「今日速览」其实只总结了一个上午，并且每一刻钟自我推翻一次。

改为 `DAILY_CUTOFF_HOUR = 21`：**当天日报在北京时间 21:00 之后才生成**，
在此之前站点显示昨天的（完整的那份）。周报月报不变——
一周或一月的「进行中总计」是合理的，一天的不是。

同时修掉一个时区缺陷：原来用 `datetime.now(UTC).date()` 取"今天"，
而**北京时间凌晨 0:00–8:00 的 UTC 日期还是前一天**，
那段时间 worker 刷新的是错误那一天的日报。现按 `Asia/Shanghai` 取本地日期。

> 库里已有的 08-04 那份半天日报不会自动消失，但 21:00 的那次 pass 会用完整一天重写它。
> 想立刻清掉：`DELETE FROM report WHERE period_type='daily' AND period_key='2026-08-04';`

## 3.10 全部 AI 动态：改为按日期全展示（2026-08-04）

上一版把「加载更多」改成按天推进后仍不够：读者要的是**看见全部日期**。
现在 166 个日期一次全部列出，**前 3 天默认展开，其余折叠**，
某一天的内容在**首次展开时才拉取**。已无「加载更多」按钮。

支撑它的是新的 `GET /api/v1/items/days`——一次 GROUP BY 拿到每个日期的条数。

## 3.12 零分块条目：根因在采集，不在 RAG（2026-08-04 修复）

生成侧评测报出 1.4% 语料对检索不可见时，只记了「待修」。这次追到根因，
发现它**还在增长**（14 → 18），不是一次性的历史遗留。

追下去是**三群完全不同的条目被同一个查询条件盖住了**：

| 群 | 数量 | 实际情况 |
|---|---:|---|
| **`revision_no ≥ 2` 且已 ENRICHED** | 6 | **真正的缺陷**——重新采集后新版正文从未被切块 |
| `PENDING` 且有正文 | 4 | 只是在等下一趟，不是缺陷 |
| `PENDING` 且正文为空 | 8 | 永远出不去 PENDING，无块可切 |

### 根因：指针前进了，状态没跟上

`repository.py` 在正文哈希变化时写入新 revision，然后把 `current_revision_id` 指过去——
**但不动 `enrichment_state`**。而 `_pending_items` 是按 `enrichment_state IN ('PENDING','FAILED')`
取待处理条目的，于是一个已经 ENRICHED 的条目**再也不会被重新访问**：

```
content_item.current_revision_id  →  新 revision（无分块）
content_chunk.content_revision_id →  旧 revision（有分块，但没人 JOIN 到）
```

检索走 `content_chunk → content_revision → content_item.current_revision_id`，
所以这些条目在索引里**根本不存在**，而每一个计数看上去都是健康的。
最严重的一条是「Claude Platform release notes」，5 万字正文，11 个分块全挂在旧版上。

那段代码旁边还有一句注释写着「outbox 保证下游 enrichment 不会漏掉文档」——
outbox 事件**确实写了**，但没有任何消费者用它触发重新加工，`_pending_items` 走的是轮询。
**注释描述的是设计意图，代码实现的是另一回事。**

### 修法：两层，各修各的

1. **采集侧承认自己让数据过期了**。新 revision 落地时把条目重开为 PENDING
   （已知重复条目除外——它们被 `duplicate_of_id` 排除在加工之外，重开会让它们永久卡在 PENDING，
   是同一个陷阱换个地方）。
2. **切块不再挂在 LLM 的生命周期上**。切块是正文的纯函数，却因为写在 enrichment 循环里，
   变成「只有在被 enrich 的那一趟才可能被切」。现在按**它自己维护的不变量**取数据：
   *凡是当前 revision 有正文就必须有分块*。这条同时自动修好了历史存量。
3. **空正文条目终结掉**。`length(body_text) > 0` 让它们匹配不到任何查询，
   却一直挂在 PENDING —— 一个永远归不了零的积压数字，是没人能据以行动的积压数字。

### 结果

| | 修复前 | 修复后 |
|---|---:|---:|
| 有正文但检索不到的条目 | 10 | **0** |
| `revision_no ≥ 2` 且已切块 | 0 | **11** |
| `enrichment_state = PENDING` | 12 | **0** |
| 分块总数 | 4542 | **4596** |
| 未向量化分块 | 0 | **0**（embed 阶段自动跟上）|

剩余 8 条零分块条目全部是 `body_len = 0`，标注为 `no body text extracted`——
无块可切，状态诚实。

**顺带确认**：本轮评测 `--skip-unusable` 排除了 **0 道题**，而 B4/B7 当时各排除 2 道。
那两道题的标注正是指向这些未切块的文档，修完后 90 题全部可用。

## 3.16 token 级流式：那个「必须改 prompt 契约」的前提是错的（2026-08-06）

`api.py` 的注释此前把 token 级流式记为「需要模型先输出 claims 再输出正文」，
所以列为待办。**这个判断从没验证过，而它是错的。**

拆开看，流式真正需要的三件事里有两件早就成立：

1. **引用重编号本来就是左到右的。** `bind_citations` 按首次出现顺序编号，
   一个标号拿到几号只取决于它前面的文本，不需要看后面。
2. **证据集在生成开始前就已确定。** `[E7]` 是真是假，读到的那一刻就能判定，
   不必等到结尾。

真正需要文末信息的**只有一条不变量**：*零引用的回答必须是拒答*。
先流出正文再发现它一条都没引，就得把读者已经读过的段落收回去——
这正是 §4「服务端在下发前解析引用」要防的事。

**闭合方式：首个能解析的引用出现之前，一个字都不下发。**
一旦有了第一条引用，第 3 条不变量永远不会再触发，其余三条则是构造保证的：

```
#1 每个 [n] 都有引用记录   ← 只下发能解析的标号
#2 每条引用都在证据集内     ← 引用由证据集构造
#3 零引用必须拒答          ← 首个引用出现前不下发
#4 空回答必须拒答          ← 空文本没有标号，因此从未下发过
```

代价是开头那句话要等它的引用一起出现（prompt 要求每个可核实陈述后紧跟编号，
实测就是一句话的延迟）。换来的是**没有任何已显示内容会被撤回**。

**实测**（`使用 MXFP4 量化的是哪个模型？`）：

```
41 个 delta 事件
流式文本 == 落库文本：True   ← 逐字符相同
```

另一题实测**首字 9.7s / 完整答案 13.3s**，抹掉 3.6 秒空白屏（等待时间的 27%）。

实现在 `rag/incremental.py`：`AnswerStream` 复刻 `bind_citations` 的规则做增量绑定，
`JsonStringExtractor` 从 JSON 响应里增量取出 `answer_markdown`。
**测试直接拿两者对拍**——同一答案按 1/3/7/1000 字符切分喂进去，
结果必须与 `bind_citations` 逐字符相同。写这个模块时被自己的测试抓到一个真缺陷：
`\uXXXX` 转义被切在两个 delta 之间时丢掉前缀（`中` 变成 `87`），
原因是第一版只记「是否在转义中」的布尔标志，够 `\n` 用、不够 `中` 用。

> **前端 `.ask-draft` 不是 `.ask-body`。** 第一版流式预览复用了 `.ask-body`，
> 于是「答案到了」和「第一句到了」在 DOM 里无法区分——三个原本等待 `.ask-body`
> 的浏览器用例开始对着一个还没有引用区的页面断言。半成品和成品必须长得不一样。

## 3.18 信源失败状态机：一次 DNS 抖动隔离了 18 个一手源（2026-08-06 修复）

例行核对时发现 ACTIVE 从 105 掉到 91，**19 个信源处于 QUARANTINED**，
其中 18 个 `consecutive_failures = 1`、错误是 `dns resolution failed`：
Anthropic、Hugging Face、arXiv、vLLM、OpenAI 的四个 SDK 仓库、
量子位、Simon Willison、Latent Space、DeepMind、GLM、xAI……

在容器里逐个解析这些域名**全部正常**——是一次抖动，而且早就过去了。

### 根因：实现违反了锁定规格

`AHR-SOURCE-900` §5 写得很明确：

> 连续 3 次失败或正文成功率 24 小时低于 80% 时进入 `DEGRADED`；
> 连续 24 小时失败进入 `QUARANTINED`

而 `ingestion/pipeline.py` 对**任何**非 `RATE_LIMITED` 的错误一律直接置
`QUARANTINED`，两级阶梯一级都没走。V003 的注释其实已经把道理写过一遍
（「treating it as QUARANTINED permanently sidelines a working source」），
只是当时只对 `RATE_LIMITED` 落实了。

### 修法

新增 `ingestion/health.py`，规则消费 `errors.py` 已有的 `retryable` 判定
（`AHR-INGEST-1000` §12 就是干这个的），而不是重新按状态码猜：

| 情况 | 结果 |
|---|---|
| 不可重试（404 / 登录墙 / SSRF / 解析失败）| 立刻 `QUARANTINED` |
| `RATE_LIMITED` | 保持自有状态，不进阶梯（V003 的决定）|
| 可重试，失败 < 3 次 | **保持原判定**，错误照常记录 |
| 可重试，失败 ≥ 3 次 | `DEGRADED` |
| 可重试，且已连续失败 ≥ 24 小时 | `QUARANTINED` |

**「连续 24 小时失败」两个条件缺一不可。** 只看 `last_success_at` 会误伤：
一个 3 小时轮询一次、25 小时前成功过的信源失败一次，时间窗立刻越界——
但它只失败了一次。必须同时要求失败次数达标，时间才有意义。

### 结果（重启后一趟轮询内）

| | 修复前 | 修复后 |
|---|---:|---:|
| ACTIVE | 91 | **107** |
| QUARANTINED | 19 | **2** |

剩下 2 个是真该隔离的：`The Batch` 连续 13 次 `NOT_FOUND`（不可重试），
以及一个尚未等到成功轮询、保持着旧判定的条目——它会在下次成功时自愈。

> 顺带修掉 `scheduler` 的统计口径：它按 `outcome.state` 判断成败，
> 而阶梯下的信源失败时**保持 ACTIVE**，于是失败会被记成成功。改为按
> `error_code` 是否为空判断。

## 3.19 匿名限流把整站算成了一个人（2026-08-06 修复）

`/ask` 的配额是 3/分钟、20/天，`ratelimit.py` 从 `X-Forwarded-For` 第一段取调用者，
这段逻辑本身正确且有测试。**问题在两者之间的那一跳。**

`apps/web/src/app/api/ask/route.ts` 把请求转发给 ai-service 时**没有带上这个头**，
于是 ai-service 看到的永远是 web 容器自己的地址：

```
ahr:rl:172.21.0.8:d:20671     ← 唯一的桶，全站共用
```

后果是**整站每天只能问 20 个问题**，且同一分钟内第 4 个访客必然被拒。
两边各自都没写错，错在接缝上——所以两边的测试都是绿的。

**这是被 E2E 抓出来的**：`ask.spec.ts` 一趟发 11 次提问，
第 4 次起随机失败，表现成「引用区没出现」，看起来像断言写错了。
两次运行失败的用例还不一样，正是配额而非逻辑的特征。

修复三处：

1. 转发 `X-Forwarded-For`（没有则退回 `X-Real-IP`），**原样透传保住首段**；

3. E2E 每个用例带一个 TEST-NET-2 地址，各自一个桶。

修完 **33 个 E2E 全绿**，整套耗时从 4.2 分钟降到 2.0 分钟——
之前那 2 分钟是在被限流。

## 3.20 信源后台表格：状态列显示不出状态（2026-08-06 修复）

只展示赢的那几轮，这页就不是评测记录而是宣传页。

### ③ 成本与延迟 `/ops`

`llm_usage` 换算金额 + 从 `rag_query.metrics` 实时算 p50/p95。
**顺带补上一个真缺口**：RAG 问答生成此前**从不写 `llm_usage`**——
只有 enrich 和 recommend 写。也就是说任何基于 `llm_usage` 的成本报表，
都悄悄漏掉了**唯一对公网开放、且单次最贵**的那个操作。

线上实测（122 次真实提问）：p50 **10.8s** / p95 **15.5s**，
外部 API 占 **99.4%**，本地合计 64ms。比离线那次 24 题基准更慢也更真实。

### ④ 服务期 groundedness（T2-4）

每条引用用**与离线评测同一个交叉编码器**打「论断 × 被引段落」的支持度，
填进一直为 NULL 的 `support_score`，UI 上每条来源给一个徽章。
用同一个方法是刻意的：换方法会让页面上的数和报告里的数不可比。
并发发起，实测 4 条引用只加 **1514ms**（一次往返，不是四次）。

### ⑤ Redis 语义缓存（ADR-0017）

RAG 链路此前**零缓存**，而 99% 的延迟在三次外部往返。三层：

| 层 | 键 | 失效规则 |
|---|---|---|
| 嵌入 | 模型 + 规范化问题 | 纯函数，无过期概念，TTL 7 天 |
| 答案 | 问题 + prompt 版本 + **语料指纹** | 指纹进键，新内容按构造失效 |
| 语义近邻 | 复用已算出的问题向量 | 阈值 **0.97**，且必须同一指纹 |

**第一版的语料指纹用精确语料状态，可证明正确、且完全没用**：采集每 120 秒一轮，
同一个问题隔一分钟再问，指纹已经从 `92e5b821` 变成 `b8518432`，必然未命中。
改为**按 planner 的 `freshness_required` 分两档粒度**：
「最新动态 / 时间线」绑精确语料（这类问题的旧答案是**错的**不是旧的），
其余按天——「Kimi K3 用什么量化格式」不会因为来了三篇无关文章而改变。

实测：

```
同一问题重复      14171ms → 211ms      精确命中，零 provider 调用
换个标点再问      semantic 0.9941      4649ms，省掉重排与生成
换成 DeepSeek 问  miss                 正确地各答各的
```

最后一条是这套设计的关键验证：**同样的句式、不同的公司**，
0.97 的阈值挡住了它。演示常用的 0.85 会**自信地回答另一家公司**。
**拒答永不缓存**——它的含义是「语料里还没有」，是最依赖时间的一句话。

### ⑥ 自适应路由（B12）

**先死掉两个直觉规则，才找到能站住的那个。**

1. 「简单事实题跳过重排」——B3→B4 实测 `fact_check` 从重排拿到 **+0.2195 MRR**，
   是收益第二大的类别，**直觉完全反了**。唯一不受重排影响的是 `abstention`，
   而 B1 已证明不可答题无法事先识别（相似度区间重叠 0.14）。
2. 「候选少时跳过重排」——逻辑上成立，但 128 次真实查询里融合候选数
   **从未低于 60**，规则永远不触发。

成立的是**深度**不是**有无**。B12 实测 depth 20 vs 40：

| 类别 | d20 MRR | d40 MRR | Δ |
|---|---:|---:|---:|
| comparison | 0.8244 | 0.8244 | **±0.0000** |
| recent_updates | 0.7522 | 0.7522 | **±0.0000** |
| timeline | 0.9111 | 0.9467 | −0.0356 |
| fact_check | 0.8407 | 0.9000 | −0.0593 |
| explainer | 0.9035 | 0.9667 | −0.0632 |

只对前两类把重排候选减半，其余保持 40。形状与 B7 一致：在测过有效的地方生效。
**样本量写在明处：每类 15 题。**

### ⑦ 验证阶段又抓到两件事

**a. 缓存命中时检索计划丢了。** `_replay` 把 `plan` 置空，于是问答页的
「问题类型 / 时间区间」两个 chip 在缓存命中时直接消失——而那两个 chip 正是
「最近被解析成一个真实区间」这件事的**唯一可见证据**。E2E 的
`the resolved retrieval plan is shown` 抓到的。已加 `plan_from_dict` 让计划
完整往返，坏数据降级为「不显示计划」而不是报错。

**b. 想用「问题加随机后缀」强制绕过缓存，被语义层挡住了。**
给一个长问题追加 `（#1754…）`，两个嵌入仍然在 0.97 阈值之上，
语义缓存照样命中。这本身是缓存有效性的证据，但也说明
**靠改文本无法可靠地强制未命中**。改为支持标准的
`Cache-Control: no-cache`——这不是测试钩子：运维看到一个可疑答案时，
需要的正是「拿实时链路重跑一次」，而「再问一遍」在缓存命中时毫无作用。
实测 命中 → 绕过未命中 → 命中，三次符合预期。

> 这一轮又验证了一次本项目的老规律：**直觉给出的优化方向有一半是反的，
> 而评测集每次都能在上线前把它拦下来。**

## 3.23 补齐 RAG 的五处缺口（2026-08-07）

### ① 生成侧重跑：**先修指标，再读结果**

管线改过（自适应路由、缓存、支持度）之后 groundedness 从未重测。重跑第一件事
是发现**评测自己会走缓存**——那样测的是存储的答案不是管线；`persist=False` 的评测
还会往缓存里塞 90 条 `queryId=null` 的条目，后来的真实访客命中就会拿到一个
指向空的永久链接。已修：缓存写入移进 `if persist:`，两个评测都强制绕过。

重跑结果里 `refusal_rate_on_unanswerable` **66.67% → 8.33%**，看着像核心能力崩了。
查下去是**指标测错了东西**：

- 拒答被定义为「文本为空或零引用」，而 3.13 刻意把死胡同式拒答改成了
  **有据可查的否认**——「证据里没有提到罚款，也没有任何监管机构开出罚单的记载」
  并列出检索到的内容。这类回答**有引用**，于是被判成没拒答。
- 另一个信号 `must_not_claim` 是子串匹配，它自己的注释就写着「否认时提到该词也算命中」，
  而且只覆盖 15 题里的 4 题。

**两个信号都在测表面形态。** 新增受控二值判官（只看回答与假前提，不看证据，输出一个词），
并把假前提写进黄金集。实测：

| | 08-04 | 08-07 |
|---|---:|---:|
| 支持度均值 | 0.8330 | 0.8313 |
| 支持度达标率 | 0.8986 | **0.9078** |
| 引用覆盖率 | 0.7431 | **0.8680** |
| **断言假前提的比例** | —（测不了）| **0.0000（12/12）** |

**拒答能力没有退化，退化的是衡量它的方式。**

> **仍然存在的真问题，不藏**：误拒率 **1.28% → 7.69%**（1 题变 6 题）、
> Story 覆盖 **−8.2pt**。两者在加 bigram 之前就已出现，最可能的机制是语料从
> 1125 涨到 1473 条后证据位竞争加剧——**但这是假设不是结论**，
> 需要用语料快照单独跑一轮才能定。已记为下一张任务卡。
>

而那个系统已经和产出报告时不是同一个了。

### ② 支持度回填：14.6% → **100%**

667 条引用全部打分（均值 0.7459，89.21% 达标，与离线评测的 0.8986 吻合）。
回填按**它维护的不变量**取数（有论断有正文就该有分数），不按日期——
这样答题时打分失败的条目下次会被捡回来，而不是因为不在原始积压里就永远为 NULL。

### ③ 中文分词（B13）：**修好了通道，系统没动**

`simple` 配置把 `智谱发布新模型` 切成**一个**词元，所以 `智谱` 匹配不上、`GLM-5` 可以。
B2 量到的差距是 52.1 个百分点。改用 **CJK 字符 bigram**，索引与查询共用同一个
`IMMUTABLE` 函数（ADR-0018），不引入分词器扩展。

结果：**端到端没动**（MRR ±0.0000，R@10 −0.0043，六类里五类逐位相同）。
原因 B2 自己就写过、当时没被当回事：「稠密通道对中文只低 4.9 个百分点——
缺口在通道设计边界内，不在系统层」。**稀疏通道的中文失败一直被稠密通道兜住了。**

但**站内搜索只有 FTS、没有稠密兜底**，那里的收益是真的：

| 查询 | 修复前 | 修复后 |
|---|---:|---:|
| 开源 | 4 | **130** |
| 量化 | 5 | **48** |
| 融资 | 2 | **18** |
| 智谱 | 0 | **2** |
| GLM（ASCII 对照）| 15 | 15 |

改动保留，RAG 侧记为负结果，代价是 FTS 索引 15MB → 18MB。

### ④ `/ask` 示例问题

此前 0 个，读者面对空输入框。补 4 个，每个**标注它在演示什么**：
精确型号（混合检索）、多信源佐证、时间解析、以及**故意的拒答题**——

Noise Sensitivity **诚实标注为未测**。

两条路都需要先做别的事，不该顺手挑一条塞进来。

## 3.24 误拒率回归：不是语料竞争，是答案在出口处被丢掉（2026-08-07 修复）

3.23 留了一条没解释的回归：误拒率 1.28% → 7.69%，Story 覆盖 −8.2pt，
当时的假设是「语料从 1125 涨到 1473，证据位竞争加剧」。

**这个假设是错的，而且错得挺离谱——六道题一道都不是检索问题。**

### 先看数，再猜机制

被判成拒答的六题里，**五题的 `answer_markdown` 有正文**，而且内容是对的：

> RAG-GOLD-019：「Claude Opus 5 自发布以来，主要后续包括：成为 Claude Max 的默认模型、
> 在多个基准测试中表现优异、引发社区评测与争议……」——共 89 字，`citations = 0`。

一个「有话说、但零引用」的答案，说明证据早就检索到了。
`refused = not text or not citations`，所以零引用直接等于拒答。
问题在于**引用是怎么没的**。

### 复现：把原始模型输出抓出来

拿 `service._generate` 打桩，用 `bypass_cache=True, persist=False` 重跑这六题，
打印模型的原始响应。两个各自独立的失效路径，都不在检索侧：

**A. 模型直接用 markdown 回答，没套 JSON（RAG-GOLD-020、034）**

```
raw_head: "DeepSeek V4-Flash 从发布到被产品接入，中间经历了**发布（7月31日）
→ 开源权重与API公测（同日）→ ……** 的快速链条 [E1][E2][E3]。"
```

答案是完整的，`[E1][E2][E3]` 一个不缺，只是没包在 JSON 里。
`parse_model_output` 走 `json.loads` 失败分支，返回 `answer_markdown: ""` → 拒答。
**读者被告知「语料里没有」，而语料里有，模型也已经答出来了。**

**B. 模型把编号只写进 `claims`，没写进正文（RAG-GOLD-088）**

```
prose_chars: 62      markers_in_prose: []
claims: 4            claim_evidence_ids: [E1,E2,E3,E5,E6,E7, E1,E5,E7, ...]
```

`claims[].evidence_ids` 正是契约要求填写证据编号的地方，模型**填了**。
而 `bind_citations` 只扫正文里的 `[En]`，`claims` 仅用来给已找到的编号补 claim 文案。
于是四条论断、六个证据编号，绑定出**零条引用**。

两条路径都是**模型偶发地偏离输出契约，而每一次偏离都赔上整个答案**。
重跑六题时 019/029/068 又正常了——所以这不是某类问题的固定缺陷，
是随机的契约脱靶，这也解释了为什么两轮之间会从 1 题跳到 6 题。

### 修法：两个口子各堵各的，验证一寸不放

`parse_model_output`：JSON 解析失败时，若正文**不像 JSON**（不以 `{`/`[` 开头）
且**至少带一个 `[En]`**，就按正文解析，并记一条 limitation。
两个条件缺一不可——截断的 `{"answer_markdown": "…` 是另一种故障，
把它当正文渲染等于把 JSON 语法喂给读者；没有编号的自由发挥就是 §10 禁止发布的无据输出。

`bind_citations`：正文里**一个可解析编号都没有**时，才回退到 `claims[].evidence_ids`。
模型自己标了锚点的，那是更精确的信号（它指明了哪句话依赖哪条证据），
再从 `claims` 补齐等于替它把来源挂到它从没挂过的句子上。

**核验没有任何放松**：两条路径都照常走 `bind_citations` → `check_invariants`，
编号一律回查真实证据集，编造的照样剥掉（`claims` 里写 `E9` 也进 `dangling`）。
回退触发时在 limitations 里明说「来源取自 claims、未锚定到句子」——
降级要看得见，否则它和正常答案在页面上长得一模一样。

### 结果：90 题重跑

| | 08-04 | 08-07 判官轮 | **08-07 修复后** |
|---|---:|---:|---:|
| **误拒率** | 0.0128 | 0.0769 | **0.0000** |
| Story 覆盖 | 0.7797 | 0.6976 | **0.7532** |
| 引用覆盖率 | 0.7431 | 0.8680 | **0.9069** |
| must_contain 命中 | 0.9091 | 0.9091 | **1.0000** |
| 平均引用数 | 4.03 | 3.47 | 3.90 |
| 断言假前提 | —（测不了）| 0.0000 | **0.0000** |
| 支持度均值 | 0.8330 | 0.8313 | 0.8090 |

**78 道可答题零误拒**，比 08-04 的基线还低一档；Story 覆盖收回 5.6pt。
先前那个「−8.2pt 是语料竞争」的判断可以正式作废：把六道误拒排除后，
判官轮的 Story 覆盖本来就是 0.7558——**8.2pt 里 4.8pt 就是这六个零引用的 0.0**。

拒答判定同时确认**这个放宽没有换来幻觉**：12 道诱导题断言假前提仍是 **0**。

### 支持度 −2.2pt：说清楚它是什么

`support_mean` 0.8313 → 0.8090 是这轮唯一下行的指标，两部分构成，都不藏：

- **被救回的六题本身分数偏低**（0.7046，其余题 0.7707）。这符合预期——
  它们正是模型自己写得最不稳的那几题。但它们的 **Story 覆盖是 0.8889，
  远高于全体的 0.7419**：救回来的是覆盖面更宽的实质答案，不是边角料。
- **剩下的 72 题自己也动了 −2.0pt**（0.7908 → 0.7707），而这 72 题的代码路径逐字未变。
  那就是同一模型两轮之间的抖动，不是这次改动的账。

一句话：**多发表了六个答案，均值被它们拉低一点，这是正确的代价**——
拒答率和支持度必须一起看，全拒答的系统在支持度上是满分。

### 顺手发现：永久链接把答案的限定条件全丢了（V015）

验证时点开刚生成的 `/ask/{id}`，那条「模型未按约定输出 JSON」的说明不见了。
查下去：`rag_query` **根本没有 limitations 列**，`_as_conversation` 里硬写着 `"limitations": []`。

于是实时响应有限定条件、页面也渲染（`.ask-limitations`），
而**永久链接——那个用来分享和引用的副本——展示的是同一个答案去掉全部限定后的版本**。
「证据只来自一篇论文报道」「证据未提供确切日期」这类话，恰恰是可信度的一部分；
少了它们，存下来的那份比生成的那份更自信。这个方向错得最不该。

V015 加列、写入、读回，实测：实时两条限定 → 永久链接两条都在。
这也让上面那条降级说明真正可追：**声明降级但只在内存里声明，等于没声明。**

### 值得记住的一条

这是本项目第三次栽在同一个形状上：**上游做对了，接缝上丢了东西**
（限流丢 `X-Forwarded-For`、分块挂错生命周期，见 3.19 / 3.12）。
这次的接缝是「模型的输出格式」与「服务的解析假设」之间。
**契约解析器的失败分支值得和主干一样认真对待**——
主干处理的是模型守约的情形，而失败分支处理的是它不守约的情形，
后者才是线上真正会掉答案的地方。

## 3.25 管理端鉴权：一个前提卡住了三件事（2026-08-08）

`SourceHealthController` 的类注释从 M1 就写着：规格要求最小权限 RBAC，而鉴权不存在，
所以不能暴露启停/重跑。这条推迟一直成立，但它同时卡住**三个互不相干的待办**：
信源启停（M1/M2）、后台任务重跑（M2）、Story 人工合并后台（M3）。

### 先发现的是：读的那一半已经违规了

`AHR-API-500` 写的是「**所有** `/admin/**` 需要 RBAC」，清单里就有 `GET /admin/sources/{id}`。
而 `GET /api/v1/admin/sources` 对任何人开放。
和 3.18 的信源状态机同一种形状：**实现悄悄偏离锁定契约，且没有任何测试会发现**。

### 做法（ADR-0019）

| | |
|---|---|
| 凭据 | `admin_principal`，令牌存 SHA-256，**按哈希查库**——应用层没有字符串比较，定时攻击不是「用了常量时间」而是根本不存在 |
| 角色 | `VIEWER` / `OPERATOR`。两个而不是一个 `ADMIN`：**最小权限只有在「读不蕴含写」时才是性质** |
| 拦截 | 按路径前缀 `/api/v1/admin/*`，**不按注解**——新端点因为它在哪儿而受保护 |
| 二次确认 | 必须回显目标 id，否则 428。**服务端做**，因为确认框只是某个客户端的性质 |
| 审计 | 每次尝试一行，**含被拒的**，且区分「令牌不对」与「令牌对角色不够」 |

**不引入 Spring Security**，理由写在 ADR 里：这个面是一个 Bearer 令牌查一张表，
没有会话/Cookie/表单登录，引入 starter 后第一件事是把大部分关掉。
**CSRF 如实按「不可达」处理**——`Authorization` 头跨源设不了，没有会话给浏览器自动附加。

### 落地成了一条能演示的性质

web 容器持有的是 **VIEWER** 凭据。信源后台是 SSR 的、只读不写，
于是它拿的令牌**就是写不动的那种**：拿下 web 容器不等于拿下采集管线。

实测同一个令牌：`GET /api/v1/admin/sources` → **200**（125 行），
`PATCH .../agno-releases` → **403**。

完整矩阵实测：无令牌 401 / 错令牌 401 / OPERATOR 读 200 / 未确认 **428** /
关掉后 `effective_enabled=false` / 对已关闭的源 run → **409**（不谎报已排期）/
清空覆盖后 run → **202**。审计表六行齐全，含 `DENIED_BAD_TOKEN` 与 `DENIED_UNCONFIRMED`。

### 顺带修掉一个会被静默覆盖的坑

`configured_enabled` 由 `config/sources.yaml` 同步**覆盖写**（`registry.py:120`），
所以运维在后台关掉的源会被下一次注册表导入重新打开。
改动写进独立的 `operator_enabled`，轮询依据改为生成列
`effective_enabled = COALESCE(operator_enabled, configured_enabled)`。

用生成列，而不是在 scheduler/pipeline/probe/admin 五处 SQL 里各写一遍 `COALESCE`——
这个项目已经栽过一次「两处状态不一致 → 内容对检索不可见」（§3.12）。

### 还没做的（如实）

浏览器里**没有**加写操作 UI。写操作目前走 API，凭据在运维手里；
把 OPERATOR 令牌放进 localStorage 需要单独想清楚 XSS 面，不在本次范围。

**另外发现一处死配置**：`INTERNAL_SERVICE_TOKEN` 在两个 compose 文件里都声明了，
**任何代码都没有读过它**。要么接上，要么删掉，不该留着假装有一道防线。

## 3.28 把评测与看板的优化项做掉（2026-08-08）

### ① 线上检索行为聚合：黄金集结构上答不了的那一半

`/eval` 是**离线基准**：90 题固定黄金集，手动跑，与真实对话无关。
`/ask/{id}` 的轨迹是**每次真实提问的过程再现**。两套数据此前完全不通——
1438 条轨迹只能一条条点开看。

现在 `/ops` 增加「线上检索行为」，聚合 35 次真实提问的 1438 个候选。
**第一次读出来的结果就不好看，照登：**

| | |
|---|---|
| 仅稠密通道找到 | 108 |
| **仅关键词通道找到** | **0** |
| 两个通道都找到 | 33 |

混合检索的理由一直是那道 NVFP4 题（稠密 #14 / 关键词 #1 / 融合 #3）。
那是真的，但**它是一道题**。在 141 条被引证据里，关键词通道**没有一次**是唯一找到它的通道。
这与 B13 的结论一致：稠密通道一直在兜底。
**轶事不是比率，而这一节存在的意义就是把它变成比率。**

同一份数据给出一条正面结论：被引证据的融合名次**中位数 8、最深 39**，
其中 **56/141 在融合后排 10 名之外**——如果被引的都已经在前三，
交叉编码器就不值它占的 28% 延迟。

### ② 黄金集有效性检查

标注是按 2026-08-03 的语料做的。`rag-eval --validate` 现在同时检查三件事：
标注的 item **还在不在**、**当前 revision 上还有没有可检索的分块**（§3.12 那种失效）、
以及**标注之后语料涨了多少**。

实测：127 个标注 item **全部仍然有效**，但
**语料自标注日起新增 602 条、增长 61.6%**，`reviewRecommended: true`。
第三条自动检不出来——「本周有什么动态」今天的正确答案已经不同了，
而每一个 id 都还是好的。所以它只报数字并请人复核，不假装能判断。
有 item 失效时退出码为 1，可以直接挂进定时任务。

### ③ 三处页面诚实性

- **价目表是占位默认值**，不是任何 provider 的真实费率。页面现在明说，
  并点名要设的三个环境变量——**一个看起来精确的错数字，比没有数字更坏**。
- **答案缓存命中率 0% 是设计结果不是缓存坏了**：键含语料指纹、采集每 120 秒写一次，
  时间型问题几乎必然未命中。页面在**有样本时**才解释（没样本时 0% 无意义，不解释）。
- **候选淘汰原因逐条给了中文含义**：同篇超额是单篇霸榜保护、同事件折叠是四家媒体只算一条、
  预算已满是证据位只有 10 个。合并成一个 `dropped` 就再也答不了「该调哪一个」。

**`eval_run` 表没建。** 原想把评测跑动作落库、让 `/eval` 从库里读而不是从生成的 JSON 读。
但 JSON 存档已经能用，而且它有一个数据库给不了的性质：**跟着 git 走**——
哪一次提交对应哪一份结果是可追的。为了「看起来更工程化」把它搬进库里，
换来的是多一张表和一次迁移，换不到任何一个能多回答的问题。

## 3.29 引用的「支撑」挂错了论断，支持度因此失真（2026-08-08 修复）

用户截图问「Qwen4-Ultra 的参数量是多少」（不存在的模型）。
**回答本身是对的**：否认假前提，并说明证据里真实存在的是 Qwen3.8-Max。
但三条引用底下的「支撑」文字**完全相同**，而且是那句**否认**——
支持度也因此只有 0.15 / 0.27 / 0.50。

### 根因：`claim_for` 取的是第一条提到该证据的论断

有据可查的否认必然**以一条笼统论断开头**——「检索到的内容中没有名为 X 的模型」，
证据挂 E1..E10；具体事实跟在后面，各自只挂一条。取第一条匹配的结果是
**每一条引用都拿到那句否认**，而 `score_citations` 随后拿每段原文去和
「什么都不存在」这句话打分——**没有任何段落能支撑它**。

同一道题两次运行的实测，同样的证据：

| 挂上的论断 | 支持度 |
|---|---|
| 「检索到的内容中没有名为 Qwen4-Ultra 的模型」 | 0.146 / 0.267 / 0.496 |
| 「Qwen3.8-Max 的参数量为 2.4 万亿」 | 0.000 / 0.824 / 0.998 |

**这个数报的是「哪条论断被挂上了」，不是「这段原文支撑得怎么样」。**

### 修法：最窄的论断胜出

一条只点名一段原文的论断，对那段原文的陈述强度高于一条点名十段的。
并列时保持模型给出的顺序，所以结果确定、重跑不会变。
空文本永远不顶替真实论断——空的「更窄」，但会把解释清空还看着像改进。

修完重问同一题：**0.999 / 0.961 / 0.996**，而且 [2] 拿到的是**另一条**论断
（「27B 紧凑版本」）——因为那才是点名它的最窄论断。回答正文一字未变。

### 如实记一条：历史数据修不回来

已存的 698 条 `rag_citation` 保留旧的 `claim_text` 与旧分数。
原始 `claims` 数组没有落库，**旧的挂载关系无法重算**——
重跑支持度只会拿同一句错的论断再打一次分。新答案起效，旧答案带着旧数字。

## 3.30 看板上两个数是错的：延迟少算了一段，成本混进了评测（2026-08-08 修复）

用户截图 `/ops`，两个数经不起看：**阶段占比加起来 122.7%**、
**问答 159 次却有 416 次生成调用**。

### ① 122.7% 不是显示问题，是延迟真的少算了一段

第一反应是「中位数相除本来就不该加起来等于 100%」，于是把占比改成
**按每次请求算再取中位数**。改完**还是 122.7%**——因为算术从来不是问题。

真正的原因：**`total_ms` 在生成之后就盖了戳，而支持度打分排在它后面**。
那是一次 reranker 往返，中位数 2.3s，**完全落在「端到端延迟」之外**。
两个后果，第二个才是它暴露出来的方式：p50 少报约 2.3 秒，
以及某一个阶段被一个不包含它的总数去除。

读者要等支持度打分打完才看到分数，所以它算。`total_ms` 移到所有阶段之后。
实测一次真实提问：`total_ms` 9547ms ≥ 各阶段合计 7876ms，支持度 1506ms 已在内。

**教训**：占比加起来超过 100% 时，先怀疑分母，不要先去改分子的算法。
我第一版改的正是分子。

### ② 62% 的「RAG 问答生成」成本是评测

`llm_usage` 里 `rag_answer` 有 **416 行**，而真实提问只有 **159 次**——
差的 257 次是评测跑的。`_record_answer_usage` 在 `if persist:` 之外，
于是 `persist=False` 的评测照样计入成本表。

评测调用同一个生成器、同样的 prompt、**花一样的钱，所以必须记**；
但它不是「这个站跑起来花了多少」，混在一起只会朝着好看的方向失真。
现已按 `serving=persist` 分记为 `rag_answer_eval`，页面单独一行。

**这和 §3.23 ① 是同一科**：评测污染了用来衡量它的东西。上一次是评测读自己的缓存，
这一次是评测算进生产成本。

**历史数据不迁移**：已有的 416 行无法区分哪次是评测，硬猜等于编。新数据起效。

### ③ 一个自找的小坑，值得记

psycopg 会**扫描整个查询字符串**找占位符，`--` 注释也不例外。
我在 SQL 注释里写了「summed to 122.7%」，于是 `%.` 被当成畸形占位符，接口 500。
**而我第一次修它的方式，是在同一个字符串里写注释解释这个问题——
把那两个字符原样引了一遍，再次触发。** 解释已挪到 Python 注释里。

## 3.31 多轮对话跑通了四次，还是"没有多轮对话"（2026-08-10 重做）

后端 08-09 就能正确解析「它」并带上上文，`rag_query.conversation_id` 在写、
改写在跑、`/rag/conversations/{id}` 在返回整段。**读者仍然反馈了四次「看不见连续对话」。**

这不是沟通问题，是我把「功能可用」当成了「功能存在」。
**对使用的人来说，一个跑通但看不见的功能与不存在无法区分。**

### 前两次修的是症状

页面结构是「表单在上 / 一条答案在下 / 历史在最下」——一张搜索结果页。
它没有第二轮可以待的位置，所以第二轮占了第一轮的位置：
提交追问时执行 `setAnswer(null)` 来腾出地方显示进度，
**上一轮在按下提问的那一瞬间消失。**

我修了两次：第一次把清屏改成保留（加 `pending` 状态），
第二次修了随之而来的第二个 bug（进行中的那轮被切片切掉，最新答案还是会消失）。
两次都是在同一个错误结构上打补丁——`answer` 这个"当前答案"的槽位一直在，
下一次编辑还会再破一次。

### 这次删掉的是槽位本身

`turns` 只增不减，且是决定渲染内容的唯一依据。没有"当前答案"这个变量，
也就**没有东西可以被下一轮覆盖**。正在回答的问题是另一个值，
渲染在 transcript 之后而不是取代它。

前端测试锁的正是这个结构（`AskPanel.test.ts`）：不允许出现 `setAnswer(`，
`setTurns([])` 全文只能有一处且必须在「换个新话题」里。
锁行为的测试上次没拦住这个 bug，因为行为对了、结构还是错的。

### 顺带修掉的两个真缺陷

**① 命中缓存的那一轮会从对话里消失。** `_from_cache` 命中后直接 return，
不落 `rag_query`。刷新后这轮不见了是明面上的；更隐蔽的是
**再下一轮的改写会读到一份有洞的 transcript**——「它」指的那轮不在里面。
现在命中后照样落库，原答案 permalink 记在 `metrics.cache.replayOf`。

**② 分享出去的答案是死胡同。** `_as_conversation` 不返回 `conversationId`，
所以 permalink 页面渲染得出答案，却没有可以接着问下去的线索。

### 中间件缓存这一层（读者点名要的）

`ahr:rag:v1:thread:{id}`，TTL 2h。每轮追问原本都在请求路径上跑一次五表 join，
只为取回至多六条短字符串，而它每轮只变一次。

**Postgres 仍是事实来源**——缓存冷或被清空只多一次查询，最坏是改写少看到一行，
而这条退化路径与"改写供应商不可用"完全相同，早就有兜底。
缓存里只存「检索实际发出的问题 + 被引文档标题」：§11 禁止把上一轮答案当事实，
缓存是这条规则最容易被悄悄绕开的地方，存进去的东西里没有模型写的句子，
后一轮就没有可洗白的来源。

实测：三轮对话「最近千问的动态有哪些」→「那它的性能表现怎么样」→「它的上下文长度是多少？」
三轮 `retrieval_plan.question` 分别解析为原句 / 千问Qwen3.8-Max的性能表现 / 千问Qwen3.8-Max的上下文长度，
刷新后三轮完整读回；一次 exact 命中在新会话里正确落库并带 `replayOf`。

### 历史由「单轮」改为「对话」

线程里可续的单位是整段对话。平铺的单轮把同一句「那它呢」列三遍，
每条都脱离了它在追问什么，而且没有任何可以点开继续的东西。
`GET /rag/threads` 按 `conversation_id` 聚合，标题取**第一问**——
那是读者完整打出来的一句，后面的都被代词替换掉了。

## 10. 未消费的 Outbox（一条需要如实描述的架构现状）

2026-08-10 本次复核时，`outbox_event` 有 **1807 行，`published_at` 全部为空**，最早一条是 2026-08-01。
也就是说**没有任何消费者**——写入路径完整，读取路径不存在。

这不影响正确性：下游加工走的是 `_pending_items` 轮询，
而 3.12 已经让采集在写入新 revision 时把条目重开为 PENDING。
但文档里「ADR-007 用数据库 Outbox 保证一致性」这句话，
描述的是一个**只写不读**的表。对外（尤其是面试）应当这样说：

> Outbox 表与事务写入已实现，消费者未实现；当前一致性由「让数据过期的那段代码
> 负责标记过期」+ 轮询保证。引入消费者的前提是有一个真正需要异步解耦的下游，
> 目前没有。

**无界增长已处理（2026-08-08）**：`ingestion/retention.py` 加了 14 天保留期，
由 scheduler 自己每天跑一次——有界增长是运行期性质，应该归给那个本来就常驻的进程，
而不是归给一条要有人记得在服务器上装的 cron。

保留规则里有一条**为将来准备的守卫**：只要 `outbox_event` 里出现过任何
`published_at IS NOT NULL` 的行，删除条件就自动收窄成「只删已发布的」。
否则等哪天真接上消费者，这个清理任务会安静地吃掉它的积压。
实测：3 天窗口会删 1208 行（回滚未真删），当前 14 天窗口删 0 行。

写入路径的注释也改了。原文写的是「outbox 行与业务写同事务提交，
所以下游 enrichment 不会漏掉文档」——**这句话的后半段不成立**：
真正保证不漏的是同一段代码里把 `enrichment_state` 重开为 PENDING 的那条 UPDATE，
而不是这张没人读的表。
