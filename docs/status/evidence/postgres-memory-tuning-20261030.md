# Postgres 内存调优：一个负结果，和它挖出的三个根因（2026-10-30）

> 生产 `47.76.83.52`，v0.1.35（`80875be`）。所有测量都在生产库上只读完成。
> 对应方案：[`../../design/rag-optimization-plan.md`](../../design/rag-optimization-plan.md) R0-a。

## 结论先说

1. **调优没有带来预期的提速。** 按「内存不够」的判断改了 7 个参数并扩大容器上限，复测反而慢了；
   在同一会话里交替对照后，**稀疏检索快了 36%，稠密检索基本不受这些参数影响**。参数保留。
2. 「瓶颈是内存」这个判断**不完整**。真正的原因是三个结构问题，调参数解决不了：
   - 稠密检索是**全表精确扫描**，7.4 万个 4 KB 向量存在大字段存储区（TOAST），读盘的 72% 花在这里
   - 三路召回是**串行**的，而 `spec/04` 要求并行；总耗时 ≈ 稠密 + 稀疏
   - 578 MB 的 HNSW 向量索引**扫描次数为 0**，从未被用过
3. 基准测试本身有一个设计漏洞（线上语料实时变化，结果指纹无法对比），已修并验证。

## 改了什么

| 参数 | 调优前 | 调优后 |
|---|---|---|
| postgres `mem_limit` | 640 MB | 1024 MB |
| `shared_buffers` | 128 MB | 256 MB |
| `effective_cache_size` | 4 GB（默认值，超过容器上限） | 768 MB |
| `work_mem` | 4 MB | 16 MB |
| `maintenance_work_mem` | 64 MB | 256 MB |
| `random_page_cost` / `effective_io_concurrency` | 4 / 1 | 1.1 / 200 |
| `jit` | on | off |

其余容器按实测峰值收紧，所有上限之和 3,168 → 3,328 MB（物理内存 3,623 MB）。PR #80。

## 基准测试：90 道黄金题，只测数据库阶段

`scripts/bench_retrieval.py`：预先算好查询向量、不调精排和生成，只计规划、稠密、稀疏、时间通道与融合。

| 第 2 轮（热缓存） | 调优前 | 调优后 | 变化 |
|---|---:|---:|---:|
| 总耗时 p50 / p95 | 15.2 / 22.7 s | 19.3 / 27.2 s | +27% / +20% |
| 稠密 p50 | 8.9 s | 11.4 s | +28% |
| 稀疏 p50 | 6.0 s | 7.4 s | +23% |
| 时间通道 / 融合 p50 | 12 / 105 ms | — | 不是瓶颈 |
| 缓存命中率 | 76.6% | 80.0% | 变好 |
| 读盘量 | 63.1 GB | 53.4 GB | −15% |

调优前**第 2 轮不比第 1 轮快**（15.2 s vs 14.7 s）：内存够的话第二轮应该明显变快。90 个问题读了约 65 GB，
而整张分块表才 1.6 GB——同样的数据被反复读。查询进行中抓到的等待事件是 `IO/DataFileRead`。

**这张表不能直接说明调优有害。** 复测是部署后立刻跑的，采集和处理进程刚重启、正在追补积压，与检索
争抢 2 个 CPU 和磁盘。所以接着做了两个排除负载影响的对照。

## 对照 1：稠密检索的核心查询，五种参数组合

同一会话、预热后逐一 `SET`，3 道题 × 2 轮，`EXPLAIN (ANALYZE, BUFFERS)`：

| 参数组合 | 中位 | 执行计划 |
|---|---:|---|
| 现配置（jit off, rpc 1.1, ecs 768MB） | 9,841 ms | Limit → Gather Merge×2 → Sort → Seq Scan |
| 只开 jit | 9,912 ms | 同上 |
| 只改回 `random_page_cost=4` | 9,671 ms | 同上 |
| 只改回 `effective_cache_size=4GB` | 9,483 ms | 同上 |
| 全部改回旧值 | 9,576 ms | 同上 |

**五种都在 9.2–9.9 s，计划完全相同。** 这几个参数对稠密检索没有影响。

## 对照 2：新旧参数交替运行

同一会话、10 道题 × 2 轮、每轮交换先后顺序，每组 20 次：

| | 旧参数 | 新参数 | 变化 |
|---|---:|---:|---:|
| 稠密中位 | 15.5 s | 18.3 s | +18% |
| **稀疏中位** | **12.8 s** | **8.2 s** | **−36%** |

这次绝对值偏高，说明测试时服务器负载重。稀疏检索的改善幅度大且方向一致，最可能来自 `work_mem`：
全文检索的位图扫描在内存不够时会退化成有损模式、需要回表逐行复查。稠密的 +18% 与对照 1 矛盾，
视为噪声。**只调整会话级规划参数，`shared_buffers` 与容器内存在两组之间相同。**

## 根因 1：稠密检索是全表精确扫描，且向量在大字段存储区里

`retrieval.py` 注释写明：HNSW 在 `ef_search=800` 时仍会漏掉最多 10% 的精确前 20，所以稠密检索用精确
扫描（`+ 0` 让规划器不走索引）。语料 4 万分块时这条路径是 2.0–2.4 s，7.4 万分块时约 9 s——数据翻倍、
耗时翻四倍，因为工作集从放得进缓存变成了放不进。

| 测量 | 值 |
|---|---|
| 活跃且有向量的分块 | 74,454 |
| 大字段存储区（TOAST）大小 | 768 MB |
| 基线第 2 轮读盘构成 | **大字段存储区 72%**、表 27%、索引 2% |

每个 1024 维向量约 4 KB，超过行内存储阈值，存在 TOAST 表里：**每读一个向量都要多查一次 TOAST 索引、
再读两三个数据块**。一次稠密检索要这样读 7.4 万次。

## 根因 2：三路召回是串行的

`service.retrieve` 依次调用 `dense_search`、`sparse_search`、`temporal_search`，共用一个连接。
基线总耗时 15.2 s ≈ 稠密 8.9 s + 稀疏 6.0 s。`spec/04` 流程图要求「并行多路召回」，
`handbook/17` 第 42 行也写成了「并行召回」——**文档与代码不符**，本次已更正为「依次召回」。

## 根因 3：HNSW 索引从未被用过

```
idx_chunk_embedding  扫描次数=0  上次使用=从未
idx_chunk_fts        扫描次数=7678
```

统计从 10-29 新机恢复数据库后开始计，其间有线上提问和两次 90 题 × 2 轮的基准测试，带时间窗的问题
规划器也没有选它。但它占着 578 MB 磁盘和缓存，每写入一个分块都要更新它，换机恢复时重建它用了 27 分钟。

## 基准测试的漏洞与修复

**调优前自己的两轮之间，90 题里只有 79 题结果一致**——线上实时入库，20 分钟内语料就变了。所以
「调优前后结果指纹 78/90 一致」证明不了任何事。修复：`bench_retrieval.py` 加 `--corpus-cutoff`，
把语料冻结在一个时刻（`service.retrieve` 原本就支持）。验证：冻结到 `2026-10-29T00:00Z` 后，
6 道题各跑两次，**6/6 完全一致**。

## 我判断错的地方

| 当时的判断 | 实际 |
|---|---|
| 「库内存是最大的延迟瓶颈」 | 只对了一部分；主要是精确扫描 + TOAST + 串行，调参解决不了 |
| 「`jit` 对毫秒级查询是纯开销」 | 稠密检索是秒级扫描，实测开关 JIT 没有差别；关掉无害，但理由写错了 |
| 方案 R0-b「`halfvec` 把 578 MB 索引减半」 | 稠密检索根本不用这个索引，减半它对检索速度没有帮助 |
| 「调优前后结果指纹一致就说明行为没变」 | 在线上库上必须冻结语料才成立 |

## 决定

- **新参数保留**：稀疏检索明确变快，读盘减少，稠密不受影响，没有证据显示有害
- 方案 R0-b 改为**二值量化粗排 + 全精度精排**（精确性用黄金集逐题验证）
- 新增 R0-c **三路召回并行**（按规格）、R0-d **删除未使用的 HNSW 索引**（需 ADR）
