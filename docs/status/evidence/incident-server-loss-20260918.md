# 事故复盘：生产服务器到期消失，从转储重建

- 日期：2026-09-18 发现 / 2026-09-19 恢复完成
- 影响：站点完全不可用约 1 天
- 数据损失：**内容零损失**；仅丢失 9/16–9/19 的 RAG 提问记录
- 恢复用时：从拿到新机 IP 到站点恢复约 3 小时

---

## 1. 发生了什么

旧机 `47.242.229.41`（阿里云香港，租用，到期不可续）在 2026-09-18 到期后消失。
表现是 ping 100% 丢包、22/80/443 全部不应答 —— 不是宕机，是**实例连同磁盘一起被回收**。

最后一次成功连接是 2026-09-17 12:37 UTC。

## 2. 手上还剩什么

| | 有没有 | 说明 |
|---|---|---|
| 数据库转储 | ✅ | 本机 `D:\Backups\AI Hot Radar`，8 份，最新 2026-09-16 |
| 代码 | ✅ | GitHub |

| 域名 | ✅ | DNSPod，A 记录指向已死的旧 IP |

## 3. 根因

**`.env` 从未异地备份。**

`server-migration-runbook.md` 第 1 节第 ① 条就写着「`.env` —— 最重要的一件，先做」，
但那份手册是 2026-09-12 写的**计划**，到期前没有执行。手册写了不等于做了。

数据库有每日 `pg_dump` + 计划任务异地拉取，所以数据没事；`.env` 不在任何自动流程里，
所以它是唯一真正丢失的东西。

## 4. 一个被证伪的恐惧

事故前我反复强调：`LLM_CREDENTIAL_MASTER_KEY` 丢了，数据库里的供应商密钥就永远解不开。

**实际查证后不成立。** 从 9/16 的转储里直接读出那一行：

```
singleton_key | base_url           | api_key_ciphertext
1             | env://LLM_BASE_URL | NULL
```

代码的取值逻辑是 `api_key = env_api_key if ciphertext is None else _decrypt_credential(...)`，
密文为 NULL 就走环境变量。ADR-0033 删掉了写入密钥的控制台，所以生产**从未**把密钥加密入库。

**教训**：按设计文档推断风险，不等于核实了生产的实际状态。ADR-0032 描述的机制存在，
但 ADR-0033 之后没有任何数据走过它。应该早一步去查那一行。

## 5. 恢复过程中卡住的两件事

### 5.1 安全组：一个不存在的问题

新机开通后测 80/443 显示「不通」，一度判断需要进阿里云控制台开安全组，
而机主没有控制台访问权限。

**实际是误判**：当时机器上**没有任何程序监听这两个端口**，「不通」只是没人应答。
查证后 `ufw` 是 `inactive`、`iptables INPUT` 策略 ACCEPT 且零规则，
Caddy 起来之后从外网直接就通了。**全程没有动过安全组。**

**教训**：端口扫描的「关闭」有两种含义 —— 被防火墙拦，或没有监听。
在没有服务监听时做的端口测试，不能用来判断防火墙。

### 5.2 证书：多地验证与 DNS 缓存

DNS 改到新 IP 后，Caddy 仍然签不到证书：

```
During secondary validation: 47.242.229.41: Timeout during connect
```

Let's Encrypt 使用**多视角验证**。主验证点已经成功（日志里有 `served key authentication`），
但次级验证点的解析器仍缓存着旧 IP。此时两台权威 NS（`ken.dnspod.net` / `hyman.dnspod.net`）
早已返回新 IP —— 问题不在权威记录，在缓存。

等待旧记录 TTL（600s）过期后重启 Caddy，一次成功。

**教训**：`certificate obtained` 失败时，先分清是「权威记录没改对」还是「缓存没过期」。
前者要改配置，后者只能等。查权威 NS 能立刻区分这两种情况。

## 6. 恢复结果

恢复后数量反而增加，是因为**采集游标也在转储里**：服务起来后从 9/16 的水位线继续，
把空窗期各信源发布的内容正常抓了回来。这是「内容零损失」的原因。

`pg_restore --exit-on-error` 退出码 0，全程零错误，耗时 3 分 47 秒。
