# M4 RAG 实现方案

上级规格：`AHR-RAG-400`（时间与事件感知 RAG）、`AHR-API-500` §4、`AHR-ARCH-200` §3
决策记录：ADR-0015（稀疏通道复用 Postgres）、ADR-0016（父块自适应阶梯）
评测方案：[m4-rag-evaluation.md](m4-rag-evaluation.md)
状态：**M4 完成**。B1–B9 九轮评测、SSE 流式、p50/p95 全部落地；
仅 token 级流式留作待办（需改 prompt 契约，见变更记录）

## 0. 一句话方案

**时间感知 + 事件感知的混合检索**：小块召回、父块生成、Story 去重、句级引用、证据不足即拒答；不引入新中间件，复用 M1–M3 已经建好的 `source` 分层、`story` 聚类和 Postgres 索引。

参考的外部企业级 RAG 有 16 个环节、5 套存储。本项目**刻意收敛到 8 个环节、2 个中间件**，理由不是"做不动"，而是它们解决的是「用户上传 PDF 文档库」的问题形态，而本项目是「每小时变化的多源资讯流」——两者在语料、查询形状和时间语义上都不同。逐条取舍见 `AHR-RAG-400` §13 与本文第 9 节。

## 2. 全流程

```
【离线】content_revision
   → 结构感知分块 (chunking.py)          ✅
   → 上下文前缀 (context.py)             ✅
   → bge-m3 1024 维 → pgvector HNSW      ✅
   → tsvector GIN（V001 已建，无需迁移）  ✅ 见 ADR-0015
   → story / report（M3 产物，直接复用）  ✅

【在线】question
   → ① Planner        冻结 RetrievalPlan
   → ② 多路召回        TEMPORAL_SQL | KEYWORD_FTS | VECTOR_PASSAGE | VECTOR_STORY_ITEM
   → ③ 硬过滤 + RRF 融合 + 受控 boost
   → ④ Rerank         bge-reranker-v2-m3
   → ⑤ 父块阶梯 + Story 折叠 + 证据选择
   → ⑥ 生成           编号证据 [E1..En]，SSE 流式
   → ⑦ 引用绑定        服务端反查，不信任模型输出的 URL
   → ⑧ 三层校验 / 拒答 → rag_query + rag_citation 落库
```

## 3. 服务边界

`AHR-ARCH-200` §3 锁定：`ai-service` 负责 Embedding / Rerank / 回答生成，`core-api` **明确不做** Embedding 计算。

| 职责 | 归属 |
|---|---|
| `POST /rag/queries`、SSE 端点、限流（匿名 3/min、20/day）、审计 | `core-api` |
| Planner、召回、融合、精排、父块、生成、校验 | `ai-service` |
| `rag_query` / `rag_citation` 落库 | `ai-service`（生成方即事实来源）|

`core-api` 对 SSE 做**转发**而非重新组装：事件序列 `plan → retrieval → delta → citation → done` 由 `ai-service` 产生。客户端断开时 `core-api` 必须向下游传播取消并记录 `client_cancelled`（`AHR-API-500` §4）。

## 4. ① Planner：不可变执行契约

输出结构见 `AHR-RAG-400` §3，落 `rag_query.retrieval_plan`（V001 就预留了这一列）。**冻结后下游只能记录降级，不能改写问题语义**——这条约束是可测的：校验 plan 在管线前后哈希一致。

### 时间解析是本项目的第一类需求

外部方案的语料是静态上传文档，没有这一层；本项目每小时在变，时间解析错等于答案错。

| 表达 | 解析 | 来源 |
|---|---|---|
| 「最近 / 近期」无跨度 | 7 天，**且在回答开头明确声明** | 规格 §3 |
| 「本周 / 本月」 | 按用户时区（默认 `Asia/Shanghai`）| 规格 §3 |
| 无时间词的「发生了什么」 | 30 天 | 规格 §3 |
| 历史解释型 | 不强制时间窗 | 规格 §3 |

**必须复用 `apps/web/src/lib/datetime.ts` 同一套时区语义**：全站曾整体渲染 UTC（比北京时间慢 8 小时，下午的资讯显示成上午、跨 16:00 UTC 后归到错误日期）。时间窗解析踩同一个坑会产生**看起来完全正常的错答案**。

另外 `rag_query` 必须记录**语料截止时间**。不记录的话，今天正确的归档回答明天就静默变错——`GET /rag/answers/{id}` 要求返回「解析时间范围、检索时间」正是为此。

### 何时不拆子问题

`comparison`、`timeline` 拆；简单问题不拆（规格 §13）。拆解会成倍放大延迟与 token 成本，且对单实体问题没有收益。

| 通道 | topK | 线上 `service.retrieve` | 评测 `eval/runner.rrf_retriever` | 说明 |
|---|---:|---|---|---|
| `VECTOR_PASSAGE` | 60 | ✅ | ✅ | `content_chunk.embedding <=> query_vec`，HNSW 余弦 |
| `KEYWORD_FTS` | 40 | ✅ | ✅ | `content_chunk.search_vector`，GIN 索引，OR + 文档频率筛词 |
| `TEMPORAL_SQL` | 40 | ❌ **未接入** | ✅ 有时间窗时启用 | `temporal_search()` 已实现，只有评测在调 |
| `VECTOR_STORY_ITEM` | 30 | ❌ 未实现 | ❌ 未实现 | Story/Item 层语义，无代码 |
| `GRAPH_LITE` | 20 | ❌ | ❌ | 按规格 §12 属 RAG-V1，刻意不做 |

### `TEMPORAL_SQL` 的评测/线上分叉

`service.retrieve` 的 `channels` 只有 `dense` 和 `sparse`；`eval/runner.py` 的
`rrf_retriever` 默认 `use_temporal=True`，在计划解析出时间窗时会加进第三条通道。
`fusion.DEFAULT_WEIGHTS` 里那条 `temporal: 0.15` **在线上永远匹配不到任何通道**。

**这是本文档 2026-08-04 那条「评测配置必须绑定线上路径」记的同一个形状，第二次发生。**
当时 B7 评测跑过、报告写过、状态标了完成却从未接进 `service.py`，
补救是加测试锁住**重排后处理的调用与顺序**
（`test_rag_dimensions.py::test_the_served_pipeline_applies_every_evaluated_dimension`）。
那条测试锁的是行为，**没有任何一条测试锁通道构成**，所以坑换了个位置又踩了一次。

量级比 B7 小：B3 报告实测独立时间通道只贡献 **+0.004 Recall**，
真正起作用的是把时间窗当**过滤器**加在稠密/稀疏通道上（这一条线上有）。
但方向是确定的——**B3 以来每一轮检索评测的绝对值都对应一个线上没有跑过的配置**，
而「差多少」至今没有数字。

处理方式二选一，**不接受第三种（继续不写）**：

1. **补测**：跑一轮 `use_temporal=False` 的 B13，若差异在噪声内，
   则删掉 `DEFAULT_WEIGHTS` 里的 `temporal` 键并记录「三通道评测的结论对双通道成立」；
2. **补接**：把 `temporal_search` 接进 `service.retrieve`（实测 dense 42ms / sparse 24ms
   量级，延迟可忽略），然后重跑 B13 确认数字。

无论选哪条，都要补一条断言**线上通道集合 == 评测通道集合**的测试。

topK 数值来自规格 §5，**标注为待评测标定**——规格同时写明「实际参数必须用评测集调优，不能作为永恒常量」。

### 稀疏通道为什么不需要 Elasticsearch

冒烟测试的失败是：问 `MXFP4` 稠密召回了 `NVFP4`。实测索引现状：

```
MXFP4 在 content_chunk.search_vector 中精确命中  30 个分块
NVFP4                                          67 个分块
```

**正确答案本来就躺在 V001 就建好的 GIN 索引里。** 完整论证见 ADR-0015，含 CJK 分词的已知缺口。

### 并行与降级

四通道并行，单通道超时不失败整次请求，降级记入 `retrieval` SSE 事件的 `degradedChannels` 与 `rag_query.metrics`。**降级必须可见**——静默降级会让评测把"通道挂了"误读成"策略无效"。

## 6. ③ 融合、硬过滤与受控 boost

先硬过滤（`status=PUBLISHED`、时间窗、排除实体、版权、语言），再 RRF：

```
rrf(d) = Σ_channel  weight(channel) / (60 + rank_channel(d))
```

**只吃排名不吃分数**：`ts_rank_cd` 不是 BM25，与向量余弦分不可比；RRF 让这件事无关紧要（ADR-0015 §决策 3）。

受控 boost（规格 §6，幅度已锁定，不得与同一信号重复计分）：

| 信号 | 幅度 |
|---|---:|
| 一手来源 | +0.08 |
| 时间窗内且含明确 event time | +0.05 |
| 直接命中目标实体为主语 | +0.05 |
| 重复转载 | −0.10 |
| 观点内容用于事实问题 | −0.15 |

融合后最多 100 条进精排。

## 7. ④⑤ 精排、父块与证据选择

### 精排

`bge-reranker-v2-m3`（硅基流动），输入原始问题 + 子问题 + 候选，输出 `relevance / directness / temporal_fit / source_fit`（规格 §6）。模型必须可配置且版本化。

**reranker 是否进 MVP 由评测决定**：若 B4 相对 B3 的 nDCG@10 提升 < 3% 而 p95 延迟翻倍，就不进。精排后保留 24 条。

### 父块自适应阶梯（ADR-0016）

按 token 预算自上而下取第一个装得下的粒度：

```
① 整篇 revision ≤ PARENT_BUDGET  → 父块 = 整篇      （覆盖实测 69.3% 的文档）
② 否则 顶层小节 ≤ PARENT_BUDGET  → 父块 = 该小节
③ 否则                           → 父块 = 命中块 ±1 兄弟块，硬封顶
```

`heading_path` 为空的分块（实测 **33.5%**）从 ① 直落 ③，不存在未定义状态。

**父块由查询派生，不落表、不额外嵌入**：`content_chunk` 已有 `content_revision_id` / `ordinal` / `heading_path` / `token_count`，父块是一条按 `ordinal` 排序的区间查询。

### 两级去重

| 层级 | 折叠什么 | 依据 |
|---|---|---|
| 父块提升 | **同文档**多个分块塌缩成一个父块 | ADR-0016 §4 |
| Story 折叠 | **同事件**最多 1 个主来源 + 2 个提供新增信息的独立来源 | 规格 §7 |

这两级分别修掉冒烟测试的发现 ①（llama.cpp 单篇占满 top-3）和 ②（Anthropic 事件三家媒体各占一位）。

### 证据选择不是取分数最高的前 N 条

规格 §8 是一个覆盖优化问题：

```
maximize: query_coverage + source_diversity + claim_directness
          + primary_source_ratio − redundancy
subject to: token_budget, time_range, citation_eligibility
```

最低证据规则（规格 §8）：`fact_check` 至少 1 个直接一手证据或 2 个独立权威二手证据；`comparison` 每个对象至少 2 个可比事件，否则**标注不对称**而非假装对称；`timeline` 每个时间节点必须有来源。

最终证据 6–12 条。

## 8. ⑥⑦⑧ 生成、引用绑定与校验

### 生成

证据带稳定编号 `[E1]…[En]`，模型输出结构见规格 §9（`answer_markdown` + `claims[].evidence_ids` + `certainty` + `limitations`）。SSE 流式下发 `delta`。

### 引用绑定：服务端反查

**在发送 `citation` 事件前从数据库解析 passage ID，不转发模型伪造的 URL**（`AHR-API-500` §4 原文）。前端只拿服务端解析出的 `{number,title,url,publishedAt,sourceTier}`。

### 三层校验（规格 §10）：**三层都跑，且第 ③ 层自 2026-08-09 起参与决定**

| 层 | 规格要求 | 现状 |
|---|---|---|
| ① 格式 | 引用编号存在、无孤立 URL、时间格式正确 | ✅ `bind_citations` + `check_invariants`，编造的编号被剥掉 |
| ② 覆盖 | 每个可验证事实主张至少一个引用 | ✅ 线上保证「至少一条引用否则拒答」；句级覆盖率由评测量（0.9069）|
| ③ 支持度 | cross-encoder / NLI 判断证据是否蕴含主张 | ✅ **低于阈值的引用被移除**，见下 |

第 ③ 层此前的状态是「算了、落库了、页面上有徽章，但不影响任何决定」：
`refused` 在打分之前就已确定，分数不改变任何输出。
后果可量化——门控前全库 729 条已打分引用中 **11.11% 低于阈值**，
即每 9 条展示给读者的来源就有 1 条，打分器判定它不支持所配论断，
**而系统知道这件事，仍然把它当作来源呈现**。

现在 `unsupported_numbers` 选出低分引用，`answer.drop_citations` 把它们从正文、
引用列表和 `limitations` 中一并移除并重编号，被移除的条数写进 `limitations` 告诉读者。

**只移除，不升级为拒答。** 这条边界是数据定的，不是保守：

- 剥离本身就足以关闭 `AHR-QSO-700` §8 的「无引用存在但不支持结论」——
  引用不再展示，缺陷就不存在了。**升级到拒答买不到任何额外的门禁分。**
- 而升级有明确代价：**有据可查的否认天然难以被蕴含打分认可**
  （3.29 实测同样三段挂否认句只有 0.15 / 0.27 / 0.50）。
  实测否认型回答 **29.41%** 的引用低于阈值，断言型只有 10.22%——
  无差别升级最先打掉的正是 3.13 刻意设计的「拒答给出路」，
  并威胁当前 **0.0000** 的误拒率。

因此 `refused` 仍由**剥离前**的引用集决定（`refused = not text or not citations` 排在打分之前），
且 `unsupported_numbers` **永不清空列表**：全部低分时保留最强的一条并在 `limitations` 说明。
实测 161 条已回答查询中，33 条含弱引用、**0 条全部为弱**，这条兜底是廉价保险而非常见路径。

规格 §10 的其余失败策略（「少量未支持句 → 删改后再校验一次」的**改写**分支、
「核心结论无证据 → 返回部分答案 + 明确缺口」）仍未实现，当前只做删除不做改写。

> **尚未重跑生成侧评测。** 门禁 #9 由构造关闭（低分引用不再展示），
> 但这个改动对 `story_coverage` / `citation_coverage` / `over_refusal_rate`
> 的影响**没有数字**。按 §14，prompt 与管线变化必须跑回归——
> 这一轮 90 题 GEN 是下一步的第一件事，在它跑完之前不得宣称 M4 达标。

### 四条硬不变量

`answer.py::check_invariants` 在落库前断言，任一条违反即整体转为拒答：

1. 答案中每个 `[n]` 都能解析到本次的引用记录；
2. 每条引用的分块都在本次 prompt 的证据集里；
3. 引用数为 0 的回答必须标记为拒答；
4. 空回答不得不标记为拒答。

> **更正（2026-08-09）**：本清单此前把第 3 条写成「每个被引用分块的 `body_text` 是其
> `content_revision` 正文的逐字子串」，代码里没有这条运行时断言。
> 该性质**由构造保证而非由断言保证**：上下文前缀只加在嵌入输入、没有写进 `body_text`
> （`context.py`），`load_evidence` 直接取 `body_text` 原文，
> 覆盖它的是分块层的 `test_chunk_quality.py::test_the_passage_survives_verbatim`。
> 构造保证比运行时断言更强也更便宜，但**它不在这个函数里**，
> 把它列进「落库前断言的四条」会让读者以为线上每次都在验。

## 9. 对外部方案的取舍

| 外部环节 | 本项目 | 理由 |
|---|---|---|
| ① MinIO + Kafka | 不做 | ADR-007 用数据库 Outbox 替代 MQ；且本项目无文件上传 |
| ② DocMind / OCR | 不做 | 语料是 HTML/RSS/Markdown，无版式问题（规格 §13）|
| ③ 表格拆到单元格 | 不做 | 表格非核心语料，触发条件见规格 §13 |
| ④ ES + Neo4j | **不做** | ADR-0015：索引已在 Postgres 里 |
| ⑥ LLM 推荐切块 + 人工确认 | **改为按内容类型选 profile** | 500+/天自动流式入库、M5 前无鉴权，**结构上不可能有人在回路里** |
| ⑦ Parent/Child 双层 | **改为三级自适应阶梯** | ADR-0016，固定双层对 33.5% 无 heading 的分块无定义 |
| ⑧ LLM 生成关键词 + 假设问题 | 已有确定性廉价版；假设问题落 **Story 层**而非 chunk 层 | 前缀由元数据合成，0 次 LLM 调用；Story 比 chunk 少两个数量级 |
| ⑨ PGVector | 相同 | — |
| ⑪ GraphRAG | 先 Graph-lite（RAG-V1）| **`story` 聚类已经是不花 LLM 钱的跨文档实体归并** |
| ⑫ RAPTOR | 不做 | **`story` + 日/周/月 `report` 已是按事件与时间的抽象层**，比无监督聚类更贴合资讯语义 |
| ⑬⑭⑮⑯ | 采纳，规模减半 | 4 通道而非 5，环节 8 个而非 16 |
| **（缺）评测** | **90 题黄金集 + 6 阶段基线** | 外部方案 16 个环节里没有一个是评测 |

本项目额外要求、外部方案没有的四件事：**时间是第一类检索维度**、**信源可信度分级**、**拒答强制**、**引用必须可回原文核对**（版权约束：能读全文 ≠ 能公开转载）。

### B1 基线改变了后续优先级

完整报告：[`docs/status/eval/m4-rag-eval-B1.md`](../status/eval/m4-rag-eval-B1.md)

1. **`recent_updates` 是最弱类别（Recall@10 0.619、MRR 0.468），而它是本产品最高频的问法。**
   最差两题的首个命中排在第 16、17 位。原因是**稠密向量里没有时间**——"最近"
   在嵌入空间几乎不携带信息，检索退化成"关于该实体的任意内容"。
   因此把 `TEMPORAL_SQL` 从"辅助通道"提为**独立的第 4.5 步**，先于 reranker。

2. **MXFP4 的失败被 `fact_check` 的 0.9556 掩盖了**：单题 Recall@20 只有 0.33，
   正确答案排第 4，分数比一篇讲相反格式（NVFP4）的文档还低 0.042。
   配对的 NVFP4 题却是满分第 1 位——失败是**单向**的。这坐实了稀疏通道的必要性。

3. **拒答不能靠相似度阈值**：可答题最低 0.5778，不可答题最高 0.7205，重叠 0.1427。
   最高的不可答题是"llama.cpp b10999 版本修了什么"（语料里有 b10211–b10240 三十个
   连续版本）。拒答必须由下游的支持度校验判定，第 9 步的设计据此收紧。

### B2 又改了一次优先级

完整报告：[`docs/status/eval/m4-rag-eval-B2.md`](../status/eval/m4-rag-eval-B2.md)

1. **稀疏通道按预测修好了 MXFP4 类失败**（R@20 0.33 → 1.00，排名 4 → 1），
   并救回 3 道题里稠密**完全没召回**的 item。`fact_check` 类 R@20 做满 1.0000。

2. **朴素轮转合并让总体每项指标都变差**（R@10 0.8045 → 0.7637）。
   最刺眼的是 RAG-GOLD-002：纯稀疏 R@20 0.67 排第 1，纯稠密 0.33 排第 17，
   **并集反而是 0.33** —— 交错无条件给弱通道一半名额，好结果被挤出去了。
   **因此 RRF 由"验证权重"升级为必需项**，理由是数字而不是惯例。

3. **`recent_updates` 是唯一被稀疏拖累的类别**（R@20 0.7733 → 0.6933），
   因为 `ts_rank_cd` 既无 IDF 也无时效。这让 `TEMPORAL_SQL` 更紧迫。

4. **中文缺口 52.1 个百分点**（稀疏：ASCII 题 0.5798 / 纯中文 0.0588），
   15 道零命中题全是纯中文。但稠密通道对中文只低 4.9 个百分点——
   缺口在通道边界内，不在系统层。ADR-0015 的触发条件据此**修正为系统级**。

### 稀疏通道的实现约束（实测得出，不是设计假设）

- `plainto_tsquery` 把词 **AND** 起来，自然语言问句这样查**命中 0 条**。必须 OR。
- 全部 OR 又会被常见词淹没，因为 `ts_rank_cd` **没有 IDF**。
- 因此按**语料实测的文档频率**筛词（默认丢弃 df > 15%）。
  附带好处：不需要停用词表，一条规则同时服务中英文，还能丢掉
  「model」「release」这类任何停用词表都不收录、但在本语料里毫无区分度的词。
- 分词交给 Postgres 自己做，query 与 index 天然一致；
  中文连写会成为一个 df=0 的 lexeme 被丢弃——通道不假装能切中文词。

## 12. 多轮对话：四层各自承担什么

多轮的后端在 2026-08-09 就跑通了，读者却四次反馈「没有多轮对话能力」。
原因不在检索链路，在**页面没有能容纳第二轮的位置**——
表单在上、答案在下、历史在最下，是一张搜索结果页的结构；
提交追问时为了显示进度会清空当前答案，于是上一轮在按下提问的瞬间消失。
**一个跑通但看不见的功能，对使用的人来说与不存在无法区分。**

| 层 | 承担 | 关键约束 |
|---|---|---|
| 前端 | `turns` 只增不减，是渲染的唯一依据 | 不存在"当前答案"这个槽位，因此**没有东西可以被下一轮覆盖** |
| 后端 | `/rag/conversations/{id}` 按时序返回整段；`/rag/threads` 列出对话 | `/history` 返回的是全站单轮记录，是另一个问题 |
| 数据库 | `rag_query.conversation_id` + V020 局部索引 | 该列 V001 就存在，Phase C 之前无人写入 |
| 中间件缓存 | `ahr:rag:v1:thread:{id}`，TTL 2h | Postgres 仍是事实来源；缓存冷/被清空只多一次查询，不会答错 |

### transcript 为什么可以缓存，证据为什么不可以

每轮追问都要读 transcript，而它**每轮只变一次**——这是值得缓存的形状。
更关键的是失败模式已经有兜底：改写器在供应商不可用时就退回"按原样提问"，
所以一份少一行的 transcript 只会让改写差一点，不会让答案错。
证据没有这个性质，因此 `ANSWER_TTL` 只有 1 小时且绑定语料指纹。

缓存里**只放两样东西**：检索实际发出的问题，和被引文档的标题。
§11 禁止把上一轮答案当作事实，而缓存正是这条规则最容易被悄悄绕过的地方——
存进去的东西里没有任何模型自己写的句子，后一轮就没有可以洗白的来源。

写入时机在 `_persist` 之后：**数据库领先缓存是安全方向**，反过来则是缓存声称了一轮不存在的对话。

### 命中缓存的那一轮，此前会从对话里消失

`_from_cache` 命中后直接 return，不落 `rag_query`。后果有两个，第二个更隐蔽：

1. 刷新页面时这一轮不见了（`load_thread` 按 `conversation_id` 查，查不到）；
2. **再下一轮的改写会读到一份有洞的 transcript**——「它」指向的那轮不在里面。

缓存要省的是三次供应商往返，不是那条记录"读者问过什么"的行。
现在命中后照样落库并接进 transcript，原答案的 permalink 记在
`metrics.cache.replayOf`（检索轨迹挂在那一行上，这一轮没有自己的轨迹，因为没跑检索）。

语义近邻还有一个附带问题：命中的是一个 0.97 相似但**不同**的问题。
落库前会把 `question` 与 `retrieval_plan.question` 改回本次实际提问，
否则读者会在自己的历史里看到一句自己没写过的话，
而 `load_turns` 恰好就是读这个字段去拼下一轮的 transcript。

## 13. 已知风险

| 风险 | 缓解 |
|---|---|
| 中文精确检索缺口（`智谱` 命中不了 `智谱发布`）| 黄金集设 ≥5 题量化；差距 > 10 个百分点则评估 zhparser（ADR-0015）|
