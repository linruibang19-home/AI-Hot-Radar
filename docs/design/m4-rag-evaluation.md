# M4 RAG 评测方案：黄金集、指标与门禁

上级规格：`AHR-RAG-400` §14、`AHR-ROADMAP-800` M4、`AHR-QA-700`
状态：黄金集已建（90 题）；B1–B9 检索评测、生成侧评测、延迟评测、权重网格均已跑过

## 1. 这些测试数据是干什么用的

**唯一目的：让每一个 RAG 设计选择变成可判定的，而不是可辩论的。**

RAG 的每个环节都有多种"看起来都对"的做法——要不要加稀疏通道、RRF 权重多少、reranker 值不值得那笔延迟、父块预算取 1500 还是 2500、HyDE 开不开。没有评测集时，这些只能靠感觉决定，而感觉在检索问题上系统性地不可靠：冒烟测试里挑三个问题、看回答"挺像样"，会同时掩盖同文档霸榜、同事件重复、精确词召回失败三个真实缺陷——这三个正是本项目实测撞到的。

所以评测数据有四个具体职责：

| 职责 | 没有它会发生什么 |
|---|---|
| **① 建立基线** | 无法判断任何改动是提升还是退化。「加了 reranker 感觉好多了」不是结论 |
| **② 定量归因** | 检索差还是生成差？Recall@20 高但 groundedness 低 = 生成在编；Recall@20 低 = 白优化 prompt |
| **③ 标定参数** | `AHR-RAG-400` §5 明确要求 topK、RRF 权重、boost 幅度「必须用评测集调优，不能作为永恒常量」 |
| **④ 防回归** | 语料每小时在变、prompt 会反复改。没有回归，昨天修好的今天会静默坏掉——本项目已经踩过五次同类静默错数据 |

第 ② 条是最容易被跳过、代价最大的一条。它决定优化力气往哪儿花。

**对简历项目的额外意义**：「我加了稀疏通道，中文精确匹配题的 Recall@20 从 0.52 到 0.79」是可追问、可复现的工程结论；「我上了 GraphRAG」接一句"提升多少"就没法回答了。参考的外部方案 16 个环节里**没有一个是评测**，这是差距最容易拉开的地方。

## 2. 黄金集构成

`AHR-RAG-400` §14 要求六类各不少于 15 题；`AHR-ROADMAP-800` M4 要求 80+ 题。取 **6 × 15 = 90 题**同时满足两者。

| # | 类别 | 题量 | 考什么 | 必须包含的刁难样本 |
|---|---|---:|---|---|
| 1 | `recent_updates` 近期变化 | 15 | 时间解析 + Story 去重 | 「最近」不给跨度；跨月边界；同事件多家报道 |
| 2 | `timeline` 时间线 | 15 | event time 与 published time 分离 | 后续报道纠正前序事实；补报道日期早于事件 |
| 3 | `comparison` 比较 | 15 | 子问题分解 + 证据对称 | 一方证据明显更多；一方语料里根本没有 |
| 4 | `fact_check` 事实核验 | 15 | 精确 token + 一手来源门控 | **MXFP4 / NVFP4 型近邻混淆**；传闻 vs 官方确认 |
| 5 | `explainer` 解释 | 15 | 父块扩展与背景完整性 | 答案跨多个小节；答案在无 heading 的正文里 |
| 6 | `abstention` 空答案与诱导 | 15 | **拒答**是否可靠 | 语料里不存在的模型名；诱导性前提（"XX 已开源"实际没有）；只能部分回答 |

### 三类必须设计进去的对抗样本

1. **中文精确匹配题（≥5 题）**。ADR-0015 记录了已知缺口：Postgres `simple` 配置按空白/标点切 CJK，`智谱` 命中不了 token `智谱发布`。**这一缺口必须被量化而不是被假设不重要**——若中文精确题 Recall@20 比英文精确题低 10 个百分点以上，触发引入 zhparser 的评估。
2. **无 heading 文档题（≥5 题）**。33.5% 的分块 `heading_path` 为空，父块阶梯对它们从 ① 直落 ③。这条分支不测就等于没实现。
3. **过期答案题（≥3 题）**。同一问题在语料更新后正确答案会变。用于验证 `rag_query` 是否记录了语料截止时间——不记录的话，归档的回答明天就静默变错。

### 标注规范

实际落地的字段见 [`data/golden/README.md`](../../data/golden/README.md)。
与本节初稿的两处差异，都是实现时改的：

- **锚点是 `relevant_items`（`content_item`）而不是 `relevant_chunks`**。
  分块一变 chunk id 全废，而 §14 恰恰要求"分块变更必须跑回归"。
- `expected` 与 `must_cite_source_tier` 未实现——Planner 的 entity/type 断言
  需要另一套标注，尚未建。

**`asked_at` 必须固定**，否则时间类题目的答案随运行日期漂移，评测不可复现；
它同时是**语料快照时点**（见 `snapshot_window`）。
**相关文档必须人工标注**，这是 90 题里最费时的部分，也是整套评测唯一不能自动化的部分。

## 3. 指标与它们各自回答的问题

| 指标 | 回答的问题 | 阶段 |
|---|---|---|
| Planner entity / time / query_type accuracy | 问题被理解对了吗 | Planner |
| **Recall@10 / Recall@20** | 相关证据**进入候选集**了吗 | 召回 |
| MRR、nDCG@10 | 相关证据**排在前面**了吗 | 融合 / 精排 |
| Story coverage | 涉及的事件都被覆盖了吗（而非同一事件重复占位）| 折叠 |
| primary-source@5 | 前 5 条里有几条一手来源 | 门控 |
| citation completeness / correctness | 每个事实主张都有引用？引用真的支持它？ | 生成 |
| groundedness | 有没有编造语料里没有的内容 | 生成 |
| answer relevance | 答了问题还是答了别的 | 生成 |
| **abstention accuracy** | 该拒答时拒了吗，不该拒时误拒了吗 | 拒答 |
| p50 / p95 延迟、token 成本 | 这套复杂度付得起吗 | 全链路 |

**Recall 与 MRR 的分工不可合并**：Recall 低说明召回漏了，再怎么调 reranker 都是白费；Recall 高而 MRR 低说明排序有问题，该动融合权重和 reranker。这就是第 1 节「定量归因」的具体含义。

**abstention accuracy 单列**：拒答是锁定约束（LLM 输出不是可信事实）。一个在诱导题上从不拒答的系统，其他指标再高也不能发布。

## 4. 分阶段基线（这是执行顺序的依据）

每一步只改一个变量，跑同一套 90 题，留下前后对比：

| 步 | 配置 | 预期主要受益指标 | 用途 |
|---|---|---|---|
| **B0** | 纯 SQL/时间过滤 | — | 下界。证明检索确实需要语义 |
| **B1** | 纯稠密（现状）| Recall@20 | **主基线**。之后所有改动都跟它比 |
| **B2** | B1 + 稀疏 FTS | fact_check 类 Recall | 验证 MXFP4 类失败被修复 |
| B2 补 | **纯稀疏单跑一遍** | — | 归因：分不清"稀疏带来了什么"和"合并方式改变了什么" |
| **B3** | B2 + RRF 融合 | MRR、nDCG@10 | 验证融合权重 |
| **B4** | B3 + reranker | nDCG@10、primary-source@5 | **验证 reranker 是否值那笔延迟** |
| **B5** | B4 + 父块阶梯 | groundedness、answer relevance | 验证上下文完整性 |
| **B6** | B5 + Story 折叠 | Story coverage | 验证同事件不再重复占位 |
| **B7** | B6 + 时效融合 | `recent_updates` MRR | 补回 B4 在该类上的退化 |
| **B8** | 融合权重网格 | Recall@40 | 权重不能是常量（§5）|
| **B9** | B7 + `directness`/`source_fit` | `explainer` / `timeline` | 补齐 §6 的四个维度 |

> B5/B6 的收益**不在检索指标上**，见 §5.5：它们改变模型读到什么，不改变排序。
> 用 Recall/nDCG 验证它们等于用错了尺子。

> **B8 的判据是 Recall@40，不是 MRR，这是刻意的。** 重排候选数固定为 40，
> 而重排只重排、不引入文档——融合没送进前 40 的东西，下游谁也看不见。
> 所以融合的全部可测贡献就是「送进去多少答案」。
> 实跑印证了这个选择：网格里融合前 MRR 差 5.9 个点的两组配置，
> 接上重排后差 0.0004。**用 MRR 调融合是在替下游调参。**

`AHR-ROADMAP-800` TASK-M4-001 明写：「先测 baseline，再加 reranker；**不得只展示几个主观示例宣布有效**」。B1 必须在 B4 之前落纸。

若某一步的提升不显著（例如 B4 相对 B3 的 nDCG@10 提升 < 3% 而 p95 延迟翻倍），**该组件就不进 MVP**——这正是评测存在的意义，它有权否决一个组件。

## 5. 发布门禁

`AHR-RAG-400` §14 与 M4 验收标准。具体阈值在 B1 基线跑出后确定（先定阈值再看数据会导致把阈值定成刚好通过），但以下四条是**硬门禁，与数值无关**：

1. **所有事实引用可跳回 passage 和原文**（M4 验收原文）；
2. **每个 `[n]` 都能解析到真实 `rag_citation` 行**，无悬空引用；
3. **每条 `rag_citation.content_chunk_id` 都在本次 prompt 的证据集里**，无凭空来源；
4. **每个被引用分块的 `body_text` 是其 `content_revision` 正文的逐字子串**，无合成证据。

第 4 条能成立，是因为上下文增强前缀只加在嵌入输入、没有写进 `body_text`（见 ADR-0016 §3）。它是可执行的断言，不是承诺。

## 5.5 生成侧评测

检索侧评测（B1–B4）看不见生成的任何东西：Recall 和 nDCG 衡量的是相关文档有没有
进候选集，完全不涉及**产出的答案是否被这些文档支持**。
B5 父块与 B6 折叠尤其如此——它们改变的是**模型读到什么**和**读到哪些来源**，
不改变排序，所以无论它们工作正常还是彻底坏掉，检索指标一动不动。

| 指标 | 怎么算 | 回答什么 |
|---|---|---|
| **groundedness** | 交叉编码器给（主张，被引段落）打分 | 引用真的支持这句话吗 |
| **citation coverage** | 带引用标记的句子占比 | 有多少事实陈述是无出处的 |
| **citation precision** | 被引文档落在黄金集 `relevant_items` 里的比例 | 答案是不是"读起来对、引错了" |
| **story coverage** | 被引事件数 / 相关事件数 | **B6 折叠是否腾出了位置**而不是丢了信息 |
| **refusal rate** | 不可答题中拒答的比例 | 该拒的拒了吗 |
| **over-refusal rate** | 可答题中拒答的比例 | **反向错误**：全都拒答的系统在拒答指标上满分且毫无用处 |

groundedness 用交叉编码器而非 LLM 裁判：§10 允许「NLI/cross-encoder 或受控 LLM」，
而交叉编码器已经在管线里、不新增供应商、且产出的正是
`rag_citation.support_score` 这一列当初定义出来要装的东西。

### 已知局限（写在前面，不等被问）

- **`must_not_claim` 只做子串匹配**。「证据中未涉及 Qwen4-Ultra」这样的**否认**
  也会被计为提及。因此它只作为**待人工复核的标记**，不作为判定；
  严格信号是 `refused`。
- **support_threshold = 0.30 尚未标定**。报告里同时给出均值与达标率，
  阈值等有依据时再动。
- 评测运行 `persist=False`：90 次问答不应每跑一次就往 `rag_query` 里灌 90 行合成数据。

## 6. 回归机制

`AHR-RAG-400` §14：**任何 prompt、embedding、reranker、分块或融合权重变化都必须跑回归评测，并记录 `eval_run_id`**。

- 评测结果落 `docs/status/eval/m4-rag-eval-<eval_run_id>.md`，与配置快照一同提交；
- `rag_query.metrics` 记录单次查询的通道命中、耗时与降级情况，使线上问题可回溯到具体通道；
- 语料每小时变化，因此**黄金集的 `relevant_chunks` 会因重新分块而失效**——分块逻辑变更时必须重新标注，这一成本要计入任何改分块的决定。
