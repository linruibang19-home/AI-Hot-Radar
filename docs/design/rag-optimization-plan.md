# RAG 优化方案：先让它变快，再让它变准

> 2026-09-21 起草。基线数据全部来自**当前生产**（239 次真实提问）与
> [RAG 调优实验纪要](../status/evidence/rag-tuning-log.md)，不是估算。

---

## 0. 先看用户实际经历了什么

| | 实测 |
|---|---:|
| 总延迟 **p50** | **10 794 ms** |
| 总延迟 **p95** | **15 748 ms** |
| 检索 p50 | 4 331 ms |
| 最慢一次 | **167 351 ms** |
| 样本 | 239 次（ANSWERED 234 / REFUSED 7） |

**没有人会等 11 秒。** 这是整条链路上最伤体验的一件事，而且它和 2026-08-04 那次
LAT 评测（p50 10 521 ms）相比几乎没变——**p95 还从 13 875 退步到 15 748**。

单次详细拆解（新版 `stage_ms`）：

```
generate        8 364 ms
numeric_audit   6 006 ms   ← 从未被评估过它防住了什么
retrieval       5 920 ms
  └ sparse      3 010 ms   ← 2026-08-04 测的是 24 ms
  └ rerank        817 ms
support           236 ms
```

**两个异常立刻可见**：`numeric_audit` 占 6 秒；`sparse` 从 24 ms 涨到 3 秒，
**125 倍**——语料从 4 140 分块涨到 37 449，而稀疏通道走的是 Postgres 全文索引。

## 阶段一：延迟（直接决定体验）

### 1.1 给 `numeric_audit` 一个判据，然后决定留还是删

**这是投入产出比最高的一件事**：它占约 24% 的延迟（实测 6 秒），
而**它拦下过什么，从来没人量过**。

做法照搬 B4 的路子——**判据先立，结论后到**：

1. 对黄金集 90 题各跑一遍「开 / 关」两个变体，语料快照固定
2. 逐题比对：审计**改写**了哪些数字、**哪些改写是对的**
3. 判据：

> 若「被审计纠正且纠正正确」的题数 < 3/90，则删除该阶段。
> 若 ≥ 3，保留但改为**仅在答案含数字时触发**（当前是无条件触发）。

**两种结果都是好结果**：删掉直接省 24% 延迟；留下则第一次有了它存在的证据。

### 1.2 把 `sparse` 涨了 125 倍这件事查清楚

24 ms → 3 010 ms 不是正常的规模增长。需要先确认是哪一种：

- `search_vector` 的 GIN 索引是否还在、是否被用上（`EXPLAIN ANALYZE`）
- B2 实现的「先量每个词的文档频率再筛词」是否在 37 449 分块上变成了全表扫描
- 是否缺少针对 `df` 统计的物化/缓存

**3 秒里大概率藏着一个索引问题，而不是一个算法问题。** 先量，再改。

### 1.3 三路召回并行

当前 `dense` / `sparse` / `temporal` 是顺序执行。三路互不依赖，
**并行后检索耗时降到三者的最大值而不是总和**。按现测数据约省 1–2 秒。

### 1.4 那次 167 秒要有解释

单次 167 秒说明**没有端到端超时**。无论根因是什么，都应该有一个硬上限
（建议 30 秒）并在超时时返回已有的部分结果或明确的失败，
而不是让用户对着转圈等两分半。

**阶段一预期**：p50 从 10.8s 降到 **4–5s**，p95 从 15.7s 降到 **8s 以内**。

## 阶段二：中文检索缺口（这是个中文产品）

> **2026-09-24 复测，本节前提已过时。** 纯稀疏通道对纯中文题 R@20 已是 0.3438（B2 为 0），判据「> 0.30」已满足——ADR-0018 的 bigram 修好了它，只是 B13 当时只量了端到端。系统层按生产配置也没有中文缺口（纯中文 0.9062 / 含英文 0.8986，纯中文仅 8 题）。新发现的问题是 bigram 碎片在 IDF 排序下压过专名，但尝试的修法在 P0 专项集上退化，未上线。详见[调优纪要](../status/evidence/rag-tuning-log.md)「ZH」一节。下文保留 09-21 起草时的原文。

B2 实测的数字至今没有被修过：

| 问题类型 | 稀疏通道 R@20 |
|---|---:|
| 含 ASCII 专名 | 0.5798 |
| **纯中文** | **0.0588** |

**差 52.1 个百分点。** ADR-0015 当时设的 10 个百分点触发线被远远突破。

根因很明确：Postgres 的 `simple` 分词器不切中文词，
「量化的是哪个模型」整串变成一个 lexeme，`df=0`，被丢掉。
**通道不假装能切中文词——这是诚实的设计，但代价一直没还。**

B13 试过中文 bigram，端到端 ±0.0000（负结果，已归档）。所以下一个候选不是再试一次 bigram，而是：

1. **`pg_bigm` 或 `zhparser` 扩展**——真正的中文分词，而不是在应用层模拟
2. 若扩展不可用，则**承认稀疏通道只服务 ASCII 专名**，
   把中文查询的召回责任完全交给稠密通道，并在 Planner 层显式分流

**判据**：纯中文问题的 R@20 从 0.0588 提到 **> 0.30**，
且 ASCII 组不退化超过噪声底（±0.02）。

## 阶段三：可信度（所有阈值的前提）

### 3.1 先把 19 道模型标注的黄金题人工复核了

`annotation.method: model_assisted` / `reviewed_by: null`。

**在这之前，任何基于新集设的阈值都不可信**——用模型标注的答案去校准模型，
是拿自己的输出当真值。这一条卡着下面所有事。

工作量：19 题，每题核对「答案是否正确、引用是否支撑」。**半天。**

### 3.2 双轨评测：区分「模型退步」和「语料变了」

语料每天在涨（6 851 → 6 947 只用了两天）。旧黄金集的答案会随语料漂移，
而 B14 已经证明**同样的输入会给出不同的结果**（±0.02 噪声底）。

做法：`rag-eval --set regression`（冻结语料快照）与 `--set fresh`（当前语料）双跑。
两者背离时才需要人介入。

### 3.3 RAG-GOLD-088：支持度门控为什么没拦住编造

v4-flash 编造了一个「Apache 2.0 许可证」。门控的设计是移除低支持度引用，
但**编造的内容若被一段看似相关的证据「支撑」，分数可能并不低**。

这一条需要的是**复现 + 定位**，不是直接改阈值。

## 优先级与理由

| 顺序 | 做什么 | 为什么排这里 |
|---|---|---|
| **1** | `numeric_audit` 判据（1.1） | 唯一一件「两种结果都是好结果」的事，且占 24% 延迟 |
| **2** | `sparse` 3 秒定位（1.2） | 大概率是个索引问题，改完立竿见影 |
| **3** | 19 题人工复核（3.1） | 半天，且卡着所有阈值工作 |
| **4** | 三路并行 + 超时（1.3 / 1.4） | 工程改动，风险低 |
| **5** | 中文分词（阶段二） | 收益最大但工作量也最大，前面做完再动 |
| **6** | 双轨评测（3.2） | 长期基础设施 |

**先做 1–4，p50 应该能从 10.8s 降到 5s 以内。** 这是用户能立刻感觉到的差别，
也是面试时最好讲的一段：**「我把 p50 从 10.8 秒降到 5 秒，方法是先量出
一个从未被评估过的阶段占了 24%，然后给它定了一个可证伪的判据。」**

---

## 不做什么

- **不做 MCP 接入**：包装层的前提是里面的东西足够好，当前 p50 10.8s 不适合对外
- **不再试中文 bigram**：B13 已证伪，端到端 ±0.0000
- **不动融合权重**：B8 负结果——网格的改进会被重排完全抹平
