## 0. 第一轮做完了什么

09-21 的方案以「先让它变快，再让它变准」为主线，随 v0.1.30–v0.1.34 上线：

| 项 | 结果 | 出处 |
|---|---|---|
| 数值审计 | 无需修改时只回 ok，审计均值 3,875 → **998 ms**，配对 36 次无漏纠 | ADR-0036 |
| 稠密检索 | 无时间窗时先排序再连接，生产 11.3 s → **2.0–2.4 s**，167 题结果逐条一致 | v0.1.30 |
| 稀疏检索 | 先走 GIN 索引再连接，生产最坏 13.4 s → **0.8 s**；高频词问题仍 5–10 s | v0.1.31（#69） |
| 评测泄漏 | 按提问时间冻结语料，引用准确率 0.5673 → 0.6888（旧数字是低估） | 调优纪要 FROZEN |
| 中文检索 | **系统层无缺口**：纯中文 0.9062 / 含英文 0.8986。但纯中文只有 8 题，只够说明「没看到缺口」 | 调优纪要 ZH |
| 引用锚点 | 引用挂到真正支持论断的分块，段落级达标 0.9173 → 0.9748 | ADR-0035 |
| 逐句支持 | 逐句删除误删率高（准确率 ≤26%），不上线；改为按句选锚点 | ADR-0037 |
| 规划器 | 正则 vs LLM：R@20 0.8998 vs 0.8908，LLM 每问多 0.8 s，**维持正则** | 调优纪要 PLANNER |
| 发布门禁 | 接入 CI，门槛单一来源 `release-gate.json` | ADR-0038 |

**第一轮没做完的**：19 道模型标注的黄金题仍未人工复核（`data/golden/pending/`，`reviewed_by: null`）；
RAG-GOLD-088 编造许可证的问题未复现定位。

## 1. 现在的问题（2026-10-30 实测）

| 问题 | 证据 |
|---|---|
| **线上又变慢了** | 近 30 天未命中缓存的提问 p50 **19.4 s** / p95 **29.3 s**（n=7，样本小但方向明确）；9 月是 10.8 s |
| **语料五周近翻倍** | 内容 7,392 → 12,515，分块 39,983 → 74,163，库 1,658 → 2,861 MB |
| **数据库内存配置与机器不符** | `shared_buffers` 128 MB，而向量索引 578 MB、全文索引 156 MB；`effective_cache_size` 默认 4 GB，容器只有 640 MB；`random_page_cost` 4（机械盘默认）；缓存命中率 93.8% |
| **规格与实现有缺口** | `spec/04` §3 的 `RetrievalPlan` 定义 13 个字段，代码只实现 6 个：`subqueries`、`source_tiers`、`content_types`、`answer_format` **从未出现在代码里**——而这正是规格 §12 列为 RAG-V1 必做的「比较分解、一手来源门控」 |
| **没有任务级能力** | 只能问一句答一句；跨多篇、多时间点、多实体的情报需求要用户自己拼 |
| **没有线上反馈** | 库里没有反馈表，线上提问的好坏无从得知 |

## 2. 目标：面向 AI 开发者的技术情报助理

产品定位（README 与 GitHub 简介）：「**做你的贴身 AI 热点资讯助手**」。用户是 AI 开发者与技术决策者，
痛点不是缺资讯，而是**信息过载、需要结论而非资讯、关键变更被淹没、决策需要出处**。

四个业务场景，按价值排序：

| 场景 | 用户的话 | 产出 |
|---|---|---|
| **依赖变更排查** | 「我们用 OpenAI Assistants API 和 vLLM，最近有没有会影响我们的弃用或破坏性变更？」 | 影响清单：变更、截止日期、原文链接 |
| **技术选型调研** | 「给客服场景选个便宜的中文长上下文模型，看最近三个月」 | 对比表，每格带引用，缺失项标明 |
| **关注点持续追踪** | 「DeepSeek 发新模型或 vLLM 发大版本就告诉我，附上和上一版的差别」 | 定向推送 |
| **事件核查** | 「听说 GPT-6 发布了，真的吗？」 | 有据可查的确认或否认（现有 RAG 已能做） |

第一个场景最能体现差异：数据源本来就在——62 个 GitHub Release 源、12 个官方 changelog、
`openai-deprecations`。别的资讯产品是「看新闻」，这里是「盯住你依赖的东西有没有变」。

## 3. 路线

**关系：Agent 的能力上限由 RAG 决定。** 一个情报任务要检索 5–10 次，单次检索慢则 Agent 不可用；
检索不能按来源类型过滤，变更排查就做不了。所以 R0–R4 按「Agent 需要什么」排序。

### R0 性能地基

**R0-a 数据库内存调优**（进行中，分支 `perf/postgres-memory-tuning`）

| 参数 | 原值 | 新值 | 来源 |
|---|---|---|---|
| postgres `mem_limit` | 640 MB | 1024 MB | 待基准测试标定 |
| `shared_buffers` | 128 MB | 256 MB | 待基准测试标定 |
| `effective_cache_size` | 4 GB | 768 MB | 实测标定（须小于容器上限） |
| `maintenance_work_mem` | 64 MB | 256 MB | 实测标定（10-30 恢复时建向量索引用了 27 分钟） |
| `random_page_cost` / `effective_io_concurrency` | 4 / 1 | 1.1 / 200 | 云盘为 SSD |
| `jit` | on | off | 毫秒级查询不需要 JIT |

内存从用量远低于上限的容器挪出（ai-service、web、pipeline、caddy），所有上限之和 3,328 MB，
不超过物理内存 3,623 MB 减系统预留。两条约束已写成测试（`test_prod_compose.py`）。

验收：90 道黄金题只测数据库阶段（`scripts/bench_retrieval.py`），调优前后**每题结果指纹一致**，
且稠密 / 稀疏阶段耗时下降、缓存命中率上升。

**R0-b 向量半精度量化**（需 ADR-0039 + Flyway V028）

`embedding vector(1024)` → `halfvec(1024)`，向量索引 578 MB → 约 290 MB（pgvector 0.8.7 已支持）。
做法：新增列与索引并行存在 → 双读对比 → 切换 → 删除旧列。

验收：黄金集 R@20 与切换前的配对差异落在 **±0.02 噪声底**内（实测标定，B14）；索引体积减半。

### R1 检索工具层（需 ADR-0040）

把一体化的 `service.retrieve`（`service.py` 1,827 行）拆成可单独调用的工具，现有问答改为组合这些工具：

| 工具 | 输入 | 输出 |
|---|---|---|
| `search_corpus` | 查询、时间窗、厂商实体、来源层级、内容类型、条数 | 带分数和来源的证据段落 |
| `get_item` | 内容 ID | 正文、发布时间、来源、所属事件 |
| `get_entity_timeline` | 实体、时间窗 | 按时间排列的事件与条目 |
| `get_source_changes` | 信源（或仓库）、起始时间 | 该信源在此之后的 changelog / release 条目 |
| `verify_claims` | 论断与证据 ID | 支持度、数字审计结果（复用现有门控） |

每个工具：Pydantic 输入输出 schema、超时、有界重试、trace 记录（`AGENTS.md` 第 9 条）。

验收：现有问答改走工具层后，黄金集四项指标与改前配对差异在 ±0.02 内——**重构不能改变行为**。

### R2 补齐规格缺口（RAG-V1，`spec/04` §3 §12）

| 能力 | 规格字段 | 做法 | 来源 |
|---|---|---|---|
| 比较 / 时间线分解 | `subqueries` | 对比类按实体拆、时间线类按时间段拆，子查询并行检索后合并 | 规格规定（§13「多子问题并行：比较/时间线采用」） |
| 一手来源门控 | `source_tiers` | 按 primary / authoritative_secondary / secondary 过滤 | 规格规定 |
| 内容类型过滤 | `content_types` | 变更排查只看 `api_update` / release / changelog | 规格规定 |
| 检索不足时改写重搜 | — | 精排后首条分数低于阈值时改写一次重搜，再决定是否拒答 | 阈值待评测标定；已知可答题首条中位数 0.901、不可答 0.076 |
| 查询向量缓存 | — | 同一问题不重复调嵌入 | — |

验收：对比类、时间线类 R@20 提升，其他四类不退化超过 ±0.02。

### R3 结构化产出与呈现

- `answer_format`（规格规定）：`comparison_table`、`timeline`，新增 `change_list`（变更清单）
- **先出来源再出答案**：精排完成即推送来源列表，答案随后流式输出（总耗时不变，等待感下降）
- 所有结构化产出仍走现有的引用绑定、支持度门控与数字审计

### R4 评测与闭环

- **情报任务评测集**：约 30 个任务，四个场景各若干，**人工标注期望结论与必含证据**；补足纯中文题
  （ZH 节指出只有 8 题）
- 指标：任务完成率、结论可核验率、每任务耗时与花费
- **用户反馈**：答案下的 👍 / 👎 与「引用不对」，写入新表，进入黄金集候选池（人工复核后才入集）
- 先把第一轮遗留的 19 道模型标注题人工复核掉

### A1 技术情报助理 Agent（需 ADR-0041）

在 R1 工具层之上：**规划 → 调工具执行 → 判断证据是否充分（不足则补搜）→ 组织结构化产出 → 校验引用**。

| 设计 | 内容 | 来源 |
|---|---|---|
| 步数上限 | 8 步 | 待评测标定 |
| 花费上限 | 每任务 token 预算，超出即带着已有证据收尾并标明不完整 | 待评测标定 |
| 状态 | 任务与每一步存 PostgreSQL（PostgreSQL 是唯一事实源，ADR-0005） | 规格规定 |
| 呈现 | 独立「任务模式」，实时显示「正在查 XX…」；不替代即时问答 | — |
| 校验 | 最终产出逐条走现有门控；**没有证据的结论不输出** | 规格规定（§9–§10） |
| 模型 | DeepSeek（官方端点，ADR-0032）；工具调用走结构化输出，解析失败按现有修复流程 | 规格规定 |

**与规格的关系**：`spec/04` §3 规定 `RetrievalPlan`「冻结后不能改变问题语义」。Agent 会多次检索，
看起来与之冲突。处理方式：**Agent 工作在任务层，每一次工具调用都生成自己的冻结 `RetrievalPlan`**，
单次检索的契约不变。这一点写进 ADR-0041。

**框架**：`handbook/17` §7 写明了引入 LangGraph 的触发条件（可暂停恢复、人工审批、补偿事务）。
A1 是有界循环、无人工审批，**不满足条件**，先用手写状态机；到 A2/A3 出现审批流程时再按条件评估。

### A2 关注点持续追踪（RAG-V2「个性化建议」，需 ADR）

关注列表挂在**已确认的邮件订阅**上，由用户显式填写（厂商、模型、仓库），不做推断画像。
新内容入库时匹配关注点 → 命中则生成与上一版的差异摘要 → 走现有 SMTP 链路。

`handbook/17` §4.3 写明「没有长期用户记忆是主动边界」，原因是没有账号与同意机制。
A2 必须在 ADR 里先定：同意方式、保留期限、退订即删除。

### A3 信源运维 Agent（排在最后）

信源静默失效会直接造成情报遗漏（`openai-news` 曾 37 天无产出未被发现）。诊断步骤高度重复：
抓页面 → 看跳转链 → 读 robots 里的 sitemap → 找 RSS → 用真实适配器试抓。Agent 产出修复建议
与实测证据，**进人工审批队列，不直接改线上配置**。指标：有效信源覆盖率、故障到修复的时长。

## 4. 约束与成本

| 约束 | 影响 |
|---|---|
| 2C4G / 40 G | 内存上限测试约束总和；磁盘按 +38 MB/天约 3–4 个月写满，R0-b 量化也能缓解 |
| DeepSeek 预付费、余额薄 | 只测数据库的基准测试**不花钱**；90 题生成评测约 ¥2.5；情报任务评测按 30 任务 × 约 10 次调用估算，跑之前先查余额 |
| 延迟 | 即时问答目标 p50 < 8 s；任务模式可接受 30–90 s，但必须展示进度 |
| 流程 | `AGENTS.md`：每次一张任务卡、改检索策略先写 ADR、配对评测过门禁才上线 |

## 5. 顺序

| 顺序 | 内容 | 简历上能讲的 |
|---|---|---|
| 1 | R0-a 内存调优 | 定位到配置与机器不符（缓存参数 4 GB 对 640 MB 容器），按基准测试调优，结果逐题一致 |
| 2 | R0-b 半精度量化 | 向量索引减半，召回变化落在噪声底内 |
| 3 | R1 工具层 | 把 1,800 行的检索流程重构为带 schema 的工具，行为不变有评测证明 |
| 4 | R2 + R3 | 补齐规格里定义了却从未实现的分解、来源门控与结构化产出 |
| 5 | R4 | 任务级评测集与用户反馈闭环 |
| 6 | A1 | 有工具、有循环、有预算、有校验的情报 Agent，与一次性检索做任务级对比 |
| 7 | A2、A3 | 持续追踪与信源运维 |

## 6. 不做什么

| 能力 | 理由 |
|---|---|
| 联网搜索兜底 | 破坏「每句话都能回到入库原文」的可核验性；需付费搜索 API；现网段被部分站点封 |
| 长报告式深度研究 | 一次几十次调用，余额与延迟都不允许；已有定时日报 |
| 完整 GraphRAG | `spec/04` §13：先 Graph-lite，图实验显著提升且成本可控才引入 |
| 第三方中转站 | ADR-0032：只接官方兼容端点；中转站可能替换模型，会让评测失去可追溯性 |
| 整体迁移到 LangChain / LangGraph | `handbook/17` §7 的触发条件未满足 |
